# ADR-0008: Security model: secrets, Data API token, file:// download guard, MCP exposure

## Status
**Accepted** at gate 1 (2026-10-04, tag `plan-approved-v1`), amended the same day for the Cloudflare Tunnel front (see Amendments). Proposed in Phase A (2026-10-03).

## Context
Four facts from upstream drive this ADR (verified at `cli-v3.7.1` unless noted):
1. **E2EE is on for the user's account.** The headless service can only read notes if it holds the master password. `findMasterKeyPassword` reads the `encryption.masterPassword` setting first (`upstream:packages/lib/services/e2ee/utils.ts:142-153`).
2. **Secrets are plaintext on Linux.** `secure: true` settings (`sync.9.password`, `encryption.masterPassword`) fall back to the profile `database.sqlite` because keytar is only used on Windows/macOS. In the browser they live in the OPFS database.
3. **The Data API token travels in the query string.**
   - `?token=` is the only accepted form (`upstream:packages/lib/services/rest/Api.ts:249`). CORS is `*` (`upstream:packages/lib/ClipperServer.ts:165-175`).
   - **The CLI logs every request URL including the token** (`upstream:packages/lib/ClipperServer.ts:215`: `Request: ${request.method} ${request.url}`) to stdout and to `<profile>/log-clipper.txt`, which `command-server.ts` always attaches.
4. **`POST /notes` downloads media referenced in the body** from `http:`, `https:`, `file:` and `data:` URLs (`upstream:packages/lib/services/rest/routes/notes.ts:518`, `downloadMediaFile` at :260-293; `file:` is copied with `fsDriver().copy`). `PUT /notes/:id` does **not** download (it is a plain `Note.save`, :545-590). Upstream MCP `create_note`/`update_note` also call `Note.save` directly (`upstream:packages/lib/services/ai/tools/global/createNote.ts`).

LLM-controlled text reaches our MCP tools, so treat every tool argument as hostile.

A fifth fact since gate 1: 5. **The HTTPS front is Cloudflare Tunnel** (ADR-0006). Cloudflare terminates TLS at its edge, so it sees the plaintext HTTP traffic between the browser or MCP client and `web` (S6).

## Decision
### Assets and where they live
| Asset | Lives in | Protection |
|---|---|---|
| Sync password, E2EE master password | podman/docker **secrets** (`/run/secrets/*`, tmpfs) → piped into the CLI with `joplin config --import` on **stdin** (never argv, never env of child processes, never a file in the image) → profile DB (plaintext, upstream limitation) | profile volume `0700`, non-root uid. The user is told plainly that the profile volume holds plaintext secrets and decrypted notes. Recommend an encrypted disk. |
| Data API token (`api.token`) | generated by the supervisor (32 random bytes) **on every CLI start**, written via `config --import` | never leaves the headless container's network namespace (CLI binds `127.0.0.1`, `upstream:packages/lib/ClipperServer.ts:280`). Rotation makes tokens that leak into `log-clipper.txt` useless after the next restart. The CLI starts with `server start --quiet`. The supervisor redacts `token=` in every line it relays, and truncates `log-clipper.txt` at each start. |
| MCP bearer token, Data API gateway token | secrets | ≥ 32 bytes, constant-time compare, never logged, separate from `api.token` |
| Cloudflare Tunnel token | podman secret `cf_tunnel_token` → cloudflared `TUNNEL_TOKEN_FILE` | never an env value or a compose literal; only the `cloudflared` container mounts it |
| Cloudflare Access service token (optional, `/mcp`) | the MCP client's own config (headers `CF-Access-Client-Id`/`-Secret`) | never stored by us; `web` redacts the secret header in logs and strips Access headers before the Joplin Server (ADR-0002 rules 3 and 7) |
| Server session id (`X-API-AUTH`) | browser memory/OPFS; passes through the proxy | Caddy access log filters `X-Api-Auth`, `Authorization`, `Cookie` and the `token` query parameter |
| Decrypted notes | browser OPFS (origin-scoped); headless profile DB | origin isolation (below); volume permissions |

### Guard against the `POST /notes` file:// exfiltration path
- **Our code never sends a body to `POST /notes`.**
  - Creating a note means `POST /notes` with metadata only (`title`, `parent_id`, `is_todo`, `todo_due`), then `PUT /notes/:id {body}`; or upstream MCP `create_note` (which uses `Note.save`).
  - A unit test asserts that the Data API client refuses `POST /notes` payloads containing `body`, `body_html`, `image_data_url` or `base_url`. A negative control proves the guard is what blocks it.
- **Body sanitizer** for every body written through MCP:
  - Image/link targets may only be `:/<32-hex resource id>`, `#anchors` or (flag `MCP_ALLOW_REMOTE_LINKS`, default off) `https:`.
  - It rejects (does not silently rewrite) `file:`, `data:`, `http:`, `javascript:`, protocol-relative `//` targets and HTML `<img src=…>`/`<a href=…>` with those schemes. The error names the offending target so the LLM can correct itself.
- **Attachments** (`attach_file` tool) take **content** (base64, size-capped) and a filename, and never a path. They are uploaded with `POST /resources` multipart.
- **Network backstop.** The headless container has no route to anything except the `web` container's internal proxy listener (ADR-0006). Even a missed case can't fetch attacker URLs or post data anywhere but the user's own Joplin Server.
- **Data API gateway (opt-in, ADR-0003):** by default it rejects `POST /notes` bodies that reference `file:` URLs. `GATEWAY_ALLOW_FILE_URLS=true` turns the check off for trusted local scripts.

### MCP exposure
- Off the host by default: published only on the `web` container's `/mcp` route when `MCP_PUBLIC=true`.
- **Bearer token required** (`Authorization: Bearer`). `Origin` is validated: requests carrying an `Origin` not in `MCP_ALLOWED_ORIGINS` are rejected (DNS-rebinding defence the MCP spec requires).
- **Per-token rate limit** (default 60 tool calls/min, 10 writes/min). Request bodies are capped at 10 MiB.
- **Destructive tools** (`delete_note`, `delete_notebook`, `delete_tag`) go to the trash. Permanent deletion needs `MCP_ALLOW_PERMANENT_DELETE=true` and carries `destructiveHint: true`.
- **`MCP_READ_ONLY=true`** removes all write tools from `tools/list`.
- **Audit log:** one line per write call with the tool, ids and result. No note content or arguments are logged.

### TLS front: Cloudflare Tunnel (gate 1)
- **What Cloudflare can see** (stated plainly to the user as limitation L17):
  - the web bundle, the Joplin Server **login password** the web app sends to `/joplin-server/api/sessions`, and the `X-API-AUTH` session id;
  - sync payloads only as E2EE ciphertext (note content, titles and resources stay encrypted), plus item ids, sizes and timing;
  - the MCP bearer token and **decrypted note content** in MCP requests and responses (MCP returns plaintext);
  - gateway traffic, if the user enables the gateway. Through the tunnel, gateway clients must use `Authorization: Bearer`; the `?token=` form is for LAN clients only, because query strings reach Cloudflare's request logs.

  Users who don't accept this for MCP can keep `MCP_PUBLIC=false` and reach `/mcp` only from the same host (`http://127.0.0.1:8080/mcp`), or use the existing-reverse-proxy alternative.
- **Client IP:** only `CF-Connecting-IP` from cloudflared's fixed address is trusted (ADR-0002 rule 4). Cloudflare rejects a client-supplied `CF-Connecting-IP` (error 1000) and strips a client-supplied `X-Real-IP` (S6).
- **cloudflared's reach:** it sits on `frontend` only. It can reach `web` and the internet, never the `backend` network, the supervisor or the CLI.
- **Optional Cloudflare Access on `/mcp`:** a Service Auth policy with a service token, validated by cloudflared (`access.required`) before the request reaches `web`. It is defence in depth: the bearer token, the Origin check and the rate limits stay mandatory, and Access never replaces them.
- **No challenges on API paths:** Bot Fight Mode, "Under Attack" and managed challenges would turn sync and MCP calls into challenge pages. The zone-settings checklist (ADR-0006) keeps them off for this hostname. This removes a Cloudflare protection, which the bearer token, the server's login limiter (now keyed per real client) and our MCP rate limits replace.

### Web origin
- The origin that serves the bundle serves **nothing else** that renders user-controlled content:
  - No Joplin Server pages.
  - No published notes: `/joplin-server/shares/*` is a 302 to the server's own public URL (ADR-0002).
  - No MCP UI.
- **Headers:**
  - COOP `same-origin`, COEP `credentialless` (default) or `require-corp`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`.
  - `Cache-Control: no-cache, no-transform` on static files and `no-store, no-transform` on `/joplin-server/*`, `/mcp` and `/api`, so no front caches API data or rewrites the HTML (Cloudflare's Email Obfuscation injected a script into HTML without it, S6 T5).
  - The upstream CSP `<meta>` in `index.html` stays unchanged. We don't add a header CSP that could conflict with it. Tightening it is an upstream proposal.

### Containers
- **Both containers:**
  - non-root
  - read-only root filesystem, `tmpfs` for `/tmp`
  - `--cap-drop=ALL` and `no-new-privileges`
  - memory limits
- **Separate network namespaces:** no shared pod. In a pod, `127.0.0.1:41184` would be reachable from the `web` container.

## Alternatives considered
- **Reuse upstream as-is (expose the CLI Data API port to the LAN with its token).** The CLI can't bind anything but `127.0.0.1`. Even if it could, the token would travel in query strings through proxies and logs, and `POST /notes` would be reachable with untrusted bodies. Rejected.
- **Keep secrets only in env vars.** They are visible in `podman inspect` and inherited by child processes. Secrets plus stdin import is strictly better.
- **Wipe secrets from the profile at shutdown.** A crash leaves them anyway, the server process needs the master password while running, and the decrypted notes in the same DB are just as sensitive. Rejected in favour of volume-level protection.
- **Sanitize by rewriting bodies instead of rejecting them.** Silent rewriting hides prompt-injection attempts from the user. Rejecting is explicit and testable.
- **A dedicated "bot" Joplin account that only receives shared notebooks** (least privilege, no access to the user's master password). This is a real option, but it limits MCP to shared notebooks and adds sharing/PPK complexity. It was an open question for the user (Q8); at gate 1 the user chose the full account, so it is not the default.

## Consequences
- MCP note creation takes two Data API calls (`POST` metadata, `PUT` body) or one upstream MCP call. That is negligible.
- Restarting the CLI rotates the Data API token, so the gateway and MCP re-read it from the supervisor, not from disk.
- Some legitimate LLM writes, such as embedding a remote image URL, are refused unless the user enables `MCP_ALLOW_REMOTE_LINKS`.

## Upgrade impact
- If upstream stops downloading `file:` URLs, adds header-based tokens, or redacts the request log, our guards become redundant but stay harmless. The contract test `SEC-file-url-download` tells us when the upstream behaviour changes.
- **Upstream-first proposals:**
  1. Restrict `POST /notes` media protocols for non-clipper callers, or behind a setting.
  2. Accept the token in an `Authorization` header.
  3. Redact `token=` in `ClipperServer` request logging.
  4. An `api.bindHost` setting.

## Verification
- **S3** evidence: secrets via stdin import, token in `log-clipper.txt`, `--quiet` behaviour.
- **S4** evidence: MCP over HTTP with the CLI (`create_note` with a `file:` image creates no resource). **M10 reproduced the exfiltration path:** `POST /notes` with `![x](file:///tmp/fixture.txt)` produced a resource whose bytes equal the local file.
- **Backlog:**
  - M1-AC14 and M3-AC7 (no secret in argv/env/logs, integration)
  - M3-AC8 (token rotation and log redaction, integration)
  - M4-AC7 and M4-AC8 (file:// negative test plus a positive control; no body on `POST /notes`)

## Amendments (2026-10-04, gate 1)
- **Cloudflare Tunnel is the HTTPS front.** Added fact 5, the "TLS front" section (what Cloudflare sees, client-IP trust, cloudflared's reach, optional Access on `/mcp`, no challenges on API paths), the tunnel token and Access service token as assets, and the `no-store`/`no-transform` header rule. Evidence: `docs/spikes/S6-cloudflare-tunnel.md`.
- The gateway's `?token=` form is for LAN clients only; through the tunnel, clients use `Authorization: Bearer`.
- Q8 resolved: the headless service uses the user's full account; the bot-account mode stays an alternative, not the default.

## Amendments (2026-10-04, MCP exposure)
- **User decision (L17, STATUS 2026-10-04):** publish `/mcp` through the Cloudflare Tunnel behind Cloudflare Access **plus** the bearer token, so cloud MCP clients (claude.ai connectors) can reach it. The user accepts that Cloudflare can read the MCP bearer token and the decrypted note content MCP returns. This replaces the earlier Q7 default for the user's deployment. **The product default for others stays opt-in** (`MCP_PUBLIC=false`): "MCP exposure" above describes the shipped defaults, and the user's deployment overrides them in its own `.env`.
- In that deployment, Access is a required outer layer. The bearer token, the Origin allow-list, the rate limits, the trash-by-default rule and the `POST /notes` guards stay mandatory and unchanged.
- **Open (O4):** if claude.ai connectors can only authenticate through OAuth (Access as the authorization server) and can't send our static bearer token, accepting a validated Access JWT in place of the bearer token on the tunnel path is a relaxation of this ADR. It needs the user's explicit approval and a further amendment, and is not assumed here.
- Verification: M4-AC18, M5-AC14, M5-AC11 step 5 (all with negative controls).
