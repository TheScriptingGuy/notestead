## Planner decisions
- **D1. Account: `e2eeAccount`, unlocked first.**
  - `headlessService` needs an E2EE account. The supervisor runs `e2ee decrypt --force`, which exits 1 on a plain account, so the service never reports ready (ADR-0003 A1; the non-E2EE case is an open architect item in STATUS).
  - It is also the user's real configuration (E2EE on), and it makes every test prove that the web app's own uploads are encrypted (M2-AC3 cycle 1 checks the server copy).
  - L18: nothing syncs before the master password, so every test runs `openUnlockedWebApp` (configure, banner, `unlockE2ee`, then the first seeded note is in the list) before it changes anything.
- **D2. "One headless sync" is `syncHeadlessOnce(stack, headlessService)`, the restart of the test's own service.**
  - The M1 supervisor syncs only in its start cycle. The restart rotates the Data API token, which `syncHeadlessOnce` re-registers, and the `dataApi` probe reads the token at call time.
  - `headlessService` is a per-test compose project, never `stack.defaultHeadless`. So the M2-S2 specs are **not disruptive** under ADR-0007 A3: they stay in the parallel `chromium` project, and `M2-S1-SER-04` keeps passing (its read-only fixture has exactly this call).
  - M3's manual trigger replaces the restart inside `syncHeadlessOnce` without changing callers (STATUS, "Before M3/M4").
- **D3. "One web sync" is `syncWebOnce`: one press of the side menu's `Synchronise`, after the UI change, that completes.** Completion means all of these: the button was idle (`Synchronise`, not `Cancel`) before the press; the context's network log has a `GET /joplin-server/api/items/root:/:/delta` with status 200 **after** the press; the button is idle again; the sync report has `Completed:` and no `Last error:`. Upstream runs `update_remote` before `delta` (`Synchronizer.ts:415`), so a delta after the press means that sync's upload ran after the change. The app's own automatic syncs may run as well; they don't change the outcome.
- **D4. "Reflected exactly" (M2-AC3, M2-AC4).** For each operation, after one web sync and one headless sync:
  - the REST fields named by the AC equal what was typed or chosen in the UI;
  - the **id stays the same** across operations (an edit is an update, a rename is not a new item);
  - **the old value is gone** (no note with the old title, no folder or tag with the old name);
  - **no conflict copy** (with `include_conflicts=1`, Finding F1);
  - exactly one item of each test-made name exists.

  One cycle per M2-AC3 operation (4 cycles), so each is checked in its own state. M2-AC4 uses 2 cycles: creation (ids captured), then the changes (same ids).
- **D5. Timezone (M2-AC5).** From M2-S2, the `webApp` context has `timezoneId` from a new option fixture `webTimezone`, default `Europe/Amsterdam` (the user's zone, gate-1 Q9), for every test. The test picks the due epoch first, computes its Amsterdam wall-clock digits with `Intl` and an explicit `timeZone` (host-independent; the Pi's own zone doesn't matter), types those digits, and asserts `todo_due === epoch`. An in-page control asserts the page's resolved zone is `Europe/Amsterdam`. Sensitivity run S6 (context in `UTC`) must fail on `todo_due`.
- **D6. The NEG timing (M2-AC5, L1): real time, a due time 2 to 3 minutes ahead, a window anchored to it.**
  - An init script (`installNotificationSpy`, on the context before the app loads) counts, in every frame: `new Notification(…)`, `Notification.requestPermission(…)` and `ServiceWorkerRegistration.prototype.showNotification(…)`. Each document gets a random `docId`, so a reload (which would reset the counters) is detected.
  - The due time is `nextWholeMinute(now, 150 s)` (`datetime-local` has minute precision): 150 to 210 s ahead. The test fails with a harness message if fewer than 60 s remain when `Save alarm` is pressed.
  - After the first cycle, `holdsFor` runs until **due + 30 s**: every probe reads the spy in every frame and fails on any count above 0, on a missing spy in the main frame, or on a changed `docId`. 30 s grace: an alarm fires at the due time (desktop's `AlarmService` sets a timer to it), so 30 s covers timer drift and a slow Pi many times over. The strategy's "absence over a window" rule applies, anchored to the due time.
  - **Positive control of the spy:** after the window, the test constructs `new Notification('nst-spy-control')` in the main frame and the count must become 1. The harness spec `M2-S2-SPY-01…03` proves the spy on a plain page (counting, reload detection, a same-origin iframe).
  - **Not `page.clock`:** it replaces `Date` and the timers in the app page (the sync scheduler, the debounced saves, the database worker's messaging), so the test would no longer observe the real app. And on web the alarm driver is a no-op (`services/AlarmServiceDriver.web.ts`), so faked time would show nothing more. Real time costs at most about 3 minutes, inside a test that runs two sync cycles anyway.
  - Upstream documents L1 itself: on web, `Save alarm` shows the alert `Warning: The due-date has been saved, but showing notifications is not supported by Joplin Web.` (`Note.tsx:1220`, a literal, not translated). The test asserts that text exactly.
- **D7. The `e2eeAccount` seed extras are opt-in:** `e2eeSeed: { notes, extras: true }`. With extras, the "other device" also seeds:
  - a to-do `Notestead todo <tag>` with `todo_due = seedTodoDue` (a fixed future epoch);
  - the tag `nst-seed-<tag>` on note 1;
  - a note `Notestead attachment note <tag>` with a text attachment `nst-seed-<tag>.txt` whose sha256 the test knows.

  The default (`{ notes: 1 }`) is unchanged, so M1-S7 and M2-S1 keep their exact seeds (M2-AC2 compares the three seeded bodies byte for byte, and the attachment would change a body). The extras are validated by `M2-S2-SEED-01` and used by M2-AC4 (the device-made tag must survive the web app's tag changes untouched). The attachment is there for M2-S3. ADR-0007 §Fixtures says the fixture seeds these; A2 says QA adds them when a story first asserts on them, which is now. The opt-in is recorded as an open question for the architect (non-blocking).

## How to run
The specs need the **real upstream bundle** in the `web` image (as M1-S7 and M2-S1). `NOTESTEAD_WEB_ARTIFACT` takes the artifact **directory**.

```sh
export NOTESTEAD_WEB_ARTIFACT=~/joplin-web-app-work/ci-evidence/37285783648/extracted/web-bundle-v3.7.21
# E2E: M2-S2 only (Pi: ~4 min stack start when the images exist; then about 8 to 12 min per AC test). One worker locally.
corepack yarn playwright test tests/e2e/m2-s2 tests/e2e/harness
# E2E: everything (M1-S7 and M2-S1 regression: the page objects, fixtures and notesTitled change)
corepack yarn playwright test
# Harness unit tests and the serial rule
corepack yarn jest tests/unit/harness tests/integration/harness
node --test --test-concurrency=1 --test-reporter=spec tests/acceptance/m2-s1/serial-rule.test.mts
```
- `NOTESTEAD_KEEP_IMAGE=1` keeps the images a run builds. Later runs reuse them with `NOTESTEAD_WEB_IMAGE=localhost/notestead-web:stack-test NOTESTEAD_HEADLESS_IMAGE=localhost/notestead-headless:stack-test NOTESTEAD_DEVICE_IMAGE=localhost/notestead-test-device:3.7.1`. **The device image must be rebuilt after `device.mjs` changes** (WO-7): it copies `device.mjs` in at build time.
- **Traces:** never pass `--trace on`. The `webApp` fixture records its own trace (Node 24 trace-merge workaround, M1-S7 F2, standing).
- **Logs:** QA's logs go under `test-results/verify/m2-s2/` (gitignored); each ends with `# duration … s; exit <code>`.
- **Timeouts:** each M2-S2 AC spec sets `test.describe.configure({ timeout: 25 * 60_000 })`. M2-AC3 has five headless starts (up plus four restarts), and on x64 one restart took up to about 90 s (W1). Each test records a `cycle` annotation per sync cycle (web and headless durations) for W1.

### Disruptive tests (ADR-0007 A3)
No M2-S2 test stops, restarts or reconfigures a shared service. Every headless sync restarts the test's **own** `headlessService` (D2). The harness specs only read. All specs run in the parallel `chromium` project, and `M2-S1-SER-04` must still pass.

### NEG window (M2-AC5)
From the save of the due date to **due + 30 s**, where the due time is 150 to 210 s after it is computed (D6). The first cycle (one web sync and one headless sync, about 40 to 90 s on the Pi) runs inside the window, so the remaining hold is usually 1 to 2 minutes. If the cycle takes longer than the due time, `holdsFor` makes at least one probe; the counters cover the whole document's life, so one probe after due + 30 s still proves the absence. The test asserts `Date.now() >= due + 30 s` at the end of the window. Sensitivity S6 proves the window catches a notification at due + 5 s.

## Findings (planning, 2026-10-21, from the upstream source at the pin and the CLI 3.7.1 install)
- **F1 (harness defect, existing; fixed here).** `notesTitled` (`tests/e2e/support/dataApi.ts`) calls `GET /notes` without `include_conflicts=1`. CLI 3.7.1's Data API excludes conflicts by default (`packages/headless/node_modules/@joplin/lib/services/rest/routes/notes.js:464-466`: `deleted_time = 0`, `is_conflict = 0` unless asked). - **F8 (focus race; `7dd0930`) is accepted.**
  - Where it applies: `NoteScreen.waitSettled` runs only for a **new** note or to-do. It waits for the editor frame, then for the page's focus owner to stay the same for 10 polls of 100 ms.

    - In M2-AC4 stray keys could reach note 1's body unnoticed. WO-19 adds a data check that note 1 is unchanged, which closes that gap.
