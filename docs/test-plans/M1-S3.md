# Test plan: M1-S3 CI skeleton

- **Story:** `docs/backlog/M1.md` § M1-S3 (M1-AC8, M1-AC9, M1-AC27). **ADRs:** 0007, 0009. **Owner:** ci-cd-specialist.
- **Branch:** `feat/M1-S3-ci-skeleton`. **Owner of this plan:** qa-specialist.
- **Runner:** the repo-level `node:test` acceptance suite (`tests/acceptance/m1-s3/`), black-box through `corepack yarn check:workflows`, as in M1-S1 and M1-S2 (`docs/testing/strategy.md` §3).
- **Status at RED:** only M1-AC8 can be tested before the first push. M1-AC9 and M1-AC27 run only on GitHub Actions and are blocked on the user's approval of the repo rename and first push (O2). They are **PENDING-CI**, with the verification procedure below. There are no local stand-in tests for them.

## How to run
```sh
node --test --test-concurrency=1 --test-reporter=spec 'tests/acceptance/m1-s3/*.test.mts'   # ~1 min on the Pi once actionlint is cached
```
- Every command's output, exit code and duration is logged to `test-results/acceptance/m1-s3/<label>.log` (gitignored, redacted).
- The suite needs no containers. It needs the network once, if `check:workflows` downloads actionlint on its first run (see the contract).

## Command contract (binding for the implementation)
`corepack yarn check:workflows [--dir <workflows-dir>]`: a root script. ADR-0009 says the logic lives in `packages/**` (A2: `packages/web-build` or a private `tooling` workspace), and the workflows only call it. Exit 0 when there are no findings, non-zero otherwise. Tests always pass absolute paths.

**Which files it checks**
- `<workflows-dir>`: default `<repo>/.github/workflows`. Every `*.yml` and `*.yaml` directly in it.
- The composite actions next to it: `<workflows-dir>/../actions/**/action.{yml,yaml}`. Only the `sha-pin` rule applies to them.
- If `<workflows-dir>` has no workflow file, or doesn't exist, the check fails and names the directory. A vacuous pass is not allowed.
- `<workflows-dir>` may sit outside any git repository; the tests use a temp tree. actionlint then needs the files as explicit arguments: without them it fails with "no project was found" (verified with 1.7.12).

**What it checks.** Each finding is one line that names the file and the offending value or job id and ends with the rule ID in brackets, actionlint style: `<file>[:line:col]: <message> [<rule>]`. Line and column numbers are welcome but not required. Every finding in every file is reported, not only the first.

| Rule | Fails when |
|---|---|
| actionlint (its own rule IDs, e.g. `[job-needs]`) | actionlint reports anything for a workflow file. Its output is passed through, and its non-zero exit fails the check. |
| `[sha-pin]` | A `uses:` value, in a step or a job (reusable workflow), in a workflow or a composite action, is none of:<br>- local: `./…`<br>- `docker://<image>@sha256:<64 lowercase hex>`<br>- `<owner>/<repo>[/<path>]@<40 lowercase hex>` (a full commit SHA)<br>Tags (`@v7`), branches (`@main`), short SHAs and `docker://` tags all fail. `actions/*` and `github/*` get no exemption. Parse the YAML: quoted values and trailing `# vX.Y.Z` comments are valid. |
| `[permissions]` | A job (including a job that calls a reusable workflow with `uses:`) has no `permissions:` of its own, or its `permissions:` is not a mapping; `{}` is fine. Also fails on `write-all` or `read-all` anywhere, at job or workflow level. The message names the job id. |
| `[pull-request-target]` | A workflow triggered by `pull_request_target` checks out PR-controlled code: an `actions/checkout` step whose `with.ref` or `with.repository` contains `github.event.pull_request.head`, `github.head_ref` or `refs/pull/`. Forbidding `pull_request_target` outright is also acceptable; the tests only require these two cases to fail. |

**actionlint (binding)**
- **One pinned version** for the Pi and CI, committed in one place along with the sha256 of each linux release tarball (amd64 and arm64). Not in `upstream/joplin-version.json`: that file holds upstream Joplin versions only. QA validated the fixtures with **actionlint 1.7.12**, the latest release on 2026-10-04; the release checksum verified for linux_arm64.
- **Binary resolution:**
  1. If `ACTIONLINT` is set, use that binary.
  2. Otherwise use a pinned binary that the script manages itself. Recommended: download the release asset for the host architecture, verify the committed sha256, and cache it outside the repo (for example `~/.cache/notestead/tools/actionlint-<version>/`). This keeps the Pi and CI on the same code path (ADR-0009).

  The ci-cd role file's `~/joplin-web-app-work/tools/` is fine for manual runs. The tests don't rely on it, and on a fresh machine with network access `check:workflows` must work with no setup.
- **Missing or wrong binary:**
  - A missing binary fails and names the path (T06).
  - Before linting, the script prints the version it will run, e.g. `actionlint 1.7.12 (<path>)` (T01).
  - A binary that reports any other version fails, naming the version it found (T07). This also covers an `ACTIONLINT` override.
- **Determinism:** the external linters actionlint shells out to must be pinned or disabled, so a tool that happens to be on `PATH` can't change the result. `ubuntu-24.04` runners ship a `shellcheck`; the Pi has none.
  - shellcheck: either download a pinned shellcheck the same way and pass `-shellcheck=<absolute path>` (recommended), or disable it with `-shellcheck=`. Record the choice in the worklog.
  - pyflakes: pass `-pyflakes=` unless a workflow gains `shell: python` steps.
  - T08 plants a fake `shellcheck` first on `PATH` that flags every script. The valid fixture must still pass.
- **No suppression:** if `.github/actionlint.yaml` or `.yml` exists, it has no `ignore:` entries (T11). The script never passes `-ignore`.

**The repository's workflows (T10–T12):**
- `.github/workflows/ci.yml` and `.github/workflows/web-bundle.yml` exist and pass `check:workflows` with its defaults.
- Every job in them declares least-privilege permissions. For these two workflows that means **no write scope at all**: checkout needs `contents: read`, and artifact upload and the cache need no `GITHUB_TOKEN` scope.

- `tests/fixtures/m1-s3/workflows/invalid/<rule>--<case>.yml.fixture`: 14 cases. The prefix is the rule expected to fire. Each case is the valid fixture plus the edits declared in `tests/acceptance/support/workflows.mts` (`workflowCases`), and T00 checks this byte for byte, so each NEG differs from the positive control only in its defect.

- The `.fixture` suffix and the path outside `.github/` keep GitHub, Dependabot, Renovate and code scanners from treating the fixtures as live workflows. The tests copy them into a temp `<tmp>/.github/{workflows,actions/setup}` tree and delete it afterwards.

## Verification procedure for M1-AC9 and M1-AC27 (CI only, PENDING-CI)
This runs once the user has approved the rename and the first push (O2) and the orchestrator has pushed. QA doesn't push, doesn't touch tokens and doesn't change GitHub settings.

**What the workflows must provide for this procedure.** These are requirements on `ci.yml` and `web-bundle.yml`. The lead can check them statically before the push.
1. **`ci.yml`, on push and on pull_request:** a matrix over `ubuntu-24.04` and `ubuntu-24.04-arm`. Each leg runs:
   - `corepack yarn install --immutable`, `corepack yarn lint`, `corepack yarn test`
   - `corepack yarn check:workflows`, `corepack yarn check:pin` and `corepack yarn check:no-upstream-copy`
   - the acceptance suites: `corepack yarn test:acceptance`, i.e. `tests/acceptance/**/*.test.mts`, which covers the M1-S1, M1-S2 default and M1-S3 suites. Run it with both reporters, `--test-reporter=spec --test-reporter-destination=stdout --test-reporter=junit --test-reporter-destination=test-results/junit/acceptance-<arch>.xml`.
2. **Uploads, always (`if: always()`, not only on failure).**
   - What: `test-results/**`, including the JUnit files and the per-command logs under `test-results/acceptance/**`, which the harness already redacts.
   - Artifact name: `test-results-<workflow>-<runner>`.
   - Why always: QA needs the passing evidence too.
3. **Job summary.** Each leg writes the acceptance totals (tests, pass, fail, skipped, todo, cancelled) and the names of any failed tests to `$GITHUB_STEP_SUMMARY`. QA can then read results without downloading artifacts.
4. **`web-bundle.yml` on `ubuntu-24.04`: run T90 itself and upload its output.**
   - The build runs **as T90**:
     ```sh
     NOTESTEAD_BUILD_OUT=$RUNNER_TEMP/web-bundle-out NOTESTEAD_BUILD_WORK=$RUNNER_TEMP/web-build-work \
       node --test --test-reporter=spec --test-reporter-destination=stdout \
         --test-reporter=junit --test-reporter-destination=test-results/junit/m1-s2-t90.xml \
         tests/acceptance/m1-s2/optin/ac5-build.optin.mts
     ```
   - It then prints `cat $RUNNER_TEMP/web-bundle-out/SHA256SUMS` and uploads **that directory** as the bundle artifact. There is no second `build` call. The `NOTESTEAD_BUILD_OUT` seam was added to T90 in this story.
   - The cache key includes the hash of `upstream/joplin-version.json`. The first run is a cache miss, so T90 runs the full build. A cache, if any, may speed up later runs but must not skip T90 on the run used as evidence.
5. **`web-bundle.yml`, a `verify-artifact` job** (`needs:` the build), on both `ubuntu-24.04` and `ubuntu-24.04-arm`: downloads the artifact, prints its `SHA256SUMS`, and runs `sha256sum -c SHA256SUMS`.
6. **The arm64 leg of `ci.yml`: a NEG step for the T90 interlock.**
   - Command: `corepack yarn test:optin:build`, with `NOTESTEAD_ALLOW_ARM64_WEB_BUILD` unset and a 120 s limit.
   - The step passes only if that command exits non-zero **and** its output contains `Refusing to start the ~43-minute native arm64 web build`.
   - Not on x64: there the same command would start the real build.

## Interpretations and findings (for the architect / orchestrator)
1. **Who writes `check:workflows`.** ADR-0009 puts check scripts in `packages/**`, which CLAUDE.md assigns to the senior engineer. The ci-cd specialist owns `.github/**`. The root `package.json` script entry is shared ground too. The orchestrator needs to route `check:workflows`, its pinned tool metadata and the root script either to the senior engineer or to the ci-cd specialist for this story.
2. **"Least privilege" is checked mechanically only as far as it can be:** permissions on every job, no `*-all`, and no write scope in the two M1-S3 workflows (T11). Whether a later workflow's write scopes are needed (release, images) is a review question for those stories. T11's no-write rule applies only to `ci.yml` and `web-bundle.yml`.
3. **`docker://` actions must be pinned by digest** (they are third-party code, like actions). `container:` and `services:` images are not covered by M1-AC8 (see Out of scope).
4. **Determinism over completeness:** shellcheck findings count only if shellcheck is pinned (recommended). Otherwise it is disabled, because an unpinned shellcheck makes CI fail where the Pi passes.

## Requirements on the implementation (seams)
- `ACTIONLINT=<path>` overrides the binary (T06, T07). The script prints the actionlint version it runs (T01).
- `--dir <abs path>` works outside a git repository (explicit file arguments to actionlint).
- Rule IDs exactly `[sha-pin]`, `[permissions]`, `[pull-request-target]`, with the file name, the offending value or job id, and the rule ID on one line.
- Nothing is written into the repo. Downloads and caches go outside it (the tests assert `git status` is unchanged around T12).
- Recommended: parse with a maintained YAML library under an AGPL-compatible licence (for example `yaml`, ISC), so quoted values, comments and flow style are handled.

## Out of scope
- Image pinning for `container:` and `services:` (M1-S8 `e2e.yml` decides; QA recommends digests), `persist-credentials: false`, impostor-commit detection (a SHA that isn't on the action's repository; this needs the network, consider zizmor later), `workflow_run` artifact poisoning, and secret handling in fork PRs. All of these are reviewed by the lead and revisited in M5 (release pipelines).
- Contract, E2E and container jobs (M1-S4…S8 add them to `ci.yml` and `e2e.yml`).
- Publishing, signatures and release smoke tests (M5, `tests/release/**`).
