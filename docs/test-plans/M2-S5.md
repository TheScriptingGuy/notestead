## Findings (planning, from upstream at the pin and the current artifact)
- **F1. What upstream's "profile is newer" check reads.** It reads the `version` table of the web app's own SQLite database in OPFS and compares it with the migration list **compiled into `app.bundle.js`**. It never reads `bundle-manifest.json`.
  - `upstream:packages/lib/JoplinDatabase.ts:386-415`: `existingDatabaseVersions` is the literal `[0 … 41]` plus one entry per element of `migrations` (`upstream:packages/lib/services/database/migrations/index.ts`: 13 entries, `migration42` … `migration54`). So the bundle's latest version is 54. A profile whose version is not in the list throws `Unknown profile version. Most likely this is an old version of Joplin, while the profile was created by a newer version. Please upgrade Joplin at https://joplinapp.org and try again.\nJoplin version: …\nProfile version: <p>\nExpected version: <e>`.
  - It runs in the startup task `buildStartupTasks/openDatabase` (`upstream:packages/app-mobile/utils/buildStartupTasks.ts:263-265`). `root.tsx:293` logs `Startup failure during task: buildStartupTasks/openDatabase`; `root.tsx:447` calls `alert(\`Something went wrong while starting the application: ${error}\`)` (a browser dialog on web), sets `appState` `error`, and the app renders only `Startup error.` (`root.tsx:726-727`).
  - **Consequence for the harness:** the expected refusal logs exactly the line WS-1 treats as a browser SQLite startup failure (`tests/e2e/support/webSqlite.ts` `startupPattern`). The NEG needs a scoped tolerance (D6), never the blanket `allowSqliteFailures`.
- **F2. Older and newer bundles in the minor.** Latest migration per upstream tag (from `migrations/index.ts`): `v3.7.1` 49; `v3.7.2` … `v3.7.18` 53; `v3.7.19` … `v3.7.21` 54. So a real in-minor older bundle with a lower database version exists (`v3.7.18`, 53). In the reference clone, `release-3.7`'s head **is** the pin (`v3.7.21`): there is no "next pin" to build.
- **F3. The service worker is network-first for every same-origin GET** (`upstream:packages/app-mobile/web/serviceWorker.ts:145-196`; `skipWaiting`/`claim` at `:43-44`): it fetches, caches the response in the Cache Storage cache `v1` when it is `ok`, same-origin, and the path ends in `.js|.css|.wasm|.json|.ttf|.html|.png` or the type is `text/html` (`cache.put` is not awaited); a network error, or a same-origin response that is not ok, is answered from `v1`. The cached copy carries the COOP/COEP headers the worker added, so an offline load stays cross-origin isolated (OPFS SQLite needs it).
  - Our `web` serves the bundle with `Cache-Control: no-cache, no-transform` and Caddy's ETag (`deploy/web/Caddyfile`, `handle` block), so the worker's `fetch` revalidates every time. A redeployed bundle is therefore seen on the next online load, as ADR-0005 Decision 4 says.
  - **A changed `serviceWorker.bundle.js`** is found by the page's own `register()` call; the worker installs, `skipWaiting()`s and `claim()`s, and the page script reloads the page itself on `updatefound` (`serviceWorker.ts:272-280`). So an upgrade that changes the worker costs one extra, upstream-initiated reload.
- **F4. Migration 54 is the AI chat tables** (`chat_conversations`, `chat_messages`, `upstream:…/migrations/54.ts`). The web bundle never queries them (`ChatConversation`/`ChatMessage` are used only by `services/ai/*`; the served `app.bundle.js` has no `chat_conversations ORDER BY`). A bundle that lacks migration 54 therefore runs normally on a profile it creates itself.
- **F5. A recovered profile adds another welcome notebook to the account.** `upstream:packages/lib/WelcomeUtils.ts` saves the welcome folder and notes with fresh ids on every fresh profile (`buildStartupTasks.ts:485-486`). The runbook's "clear site data and re-sync" is a fresh profile, so each recovery uploads a second copy of upstream's welcome notebook (L14). **Brief for the architect** (L5/L14 wording) and for the SE's runbook (R1): tell the user to delete the duplicate. The tests record it (annotation `added-after-recovery`) and assert that nothing else is added.
- **F6. The rollback runbook does not exist yet.** ADR-0005 Decision 4 states its browser steps ("sync first, roll back, then clear site data and re-sync"; lost: unsynced local edits, the local E2EE password entry, installed plugins). M5-AC9 puts the full runbook in `deploy/README.md` (M5-S4, SE). M2-AC16 tests "the rollback runbook's 'clear site data and re-sync' step", so the browser part must exist now: requirement **R1**.
- **F7. Playwright 1.59's offline emulation reaches service workers in Chromium** (`node_modules/playwright-core/lib/server/chromium/crServiceWorker.js`: `updateOffline()` on every worker target while `serviceWorkers` is `allow`). Not taken on trust: `H-OFF-01` proves it against the web container's access log.
- **F8. Nothing in M2-S5 needs to disrupt a shared service.** Every test runs its own `web` container (`extraWebs`, M2-S6 D3) of the image under test, so "redeploying `web`" never touches the stack's shared `web`. There is still no `*.serial.spec.ts` in the suite; C3 is latent and is fixed by D9 before the first disruptive spec arrives (M2-S12a's M2-AC22 NEG is the next candidate).

## Interpretations (for the orchestrator)
- **I1. "Setting the context offline"** is Playwright's `context.setOffline(true)` on the app's context (F7). The proof that nothing reached the server while offline is the test's own `web` container's access log.
- **I2. "Notes readable from OPFS"** means: offline, the seeded notes' titles show in the list, a seeded note's body shows in the viewer, and the OPFS database holds that body (data level). The server is unreachable during that read, so OPFS is the only source.
- **I3. Bundle B** is the AC's second option, "a fixture rebuilt with a changed `bundle-manifest.json`": the served bundle A with test markers added (D2), described by its own `bundle-manifest.json` whose entries for the changed files differ from A's. "The next pin" does not exist (F2); running M2-AC16 with a real previous-pin artifact as A on a pin-bump PR is an M6 item (brief below).
- **I4. "An older bundle whose database version is lower"** is bundle **O**: the served bundle A with its newest migration removed from the compiled migration list (D3). Its database version is 53, exactly that of the newest older 3.7 release (`v3.7.18`, F2). **Alternative not chosen:** a real `v3.7.18` web build. It needs a `web-bundle.yml` input for another ref and a user-approved dispatch, or the 43-minute arm64 build, and the overlay's expected-file check would have to accept an older `public/`. O exercises the identical upstream code path (F1) on every commit on both runners at no build cost. **The orchestrator may ask the user to confirm I4** (recommended answer: accept O; revisit if upstream ever changes how the version check works).
- **I5. "Redeploy `web`"** is: stop the test's own `web` container and start a new container of **the same image** on **the same host port** (same origin, so the same OPFS, service worker and Cache Storage), serving bundle B or O through a read-only mount over `/srv/www` (the M2-S6 D2/D3 mechanism). Only the bundle bytes differ, as in a real upgrade where only the bundle changes.
- **I6. "Clear site data"** is Chromium's per-site "Delete data": the test closes the app's tab, then calls CDP `Storage.clearDataForOrigin({ origin, storageTypes: 'all' })`. The harness proves its effect each time (D7). The runbook (R1) tells the user to close the tab first too.
- **I7. "Recovers all synced data, verified by data comparison":**
  - every note and folder in the REST snapshot **S0**, taken after "sync first", is in the recovered web profile (its title for every item, its body for the test's own notes, read from the OPFS database) and is unchanged in REST;
  - the server gains nothing but upstream's welcome notebook (F5) and no conflict copy;
  - an edit made **after** S0 and never synced (Z) is gone. That is the runbook's "what is lost", and it is also the proof that the profile really was cleared.

## Planner decisions
**D1. The bundles (worker-scoped fixture `testBundles`, built once per worker, removed at worker teardown):**
- **A** = the exact tree the stack's `web` serves: `podman cp <stack web>:/srv/www` (the same copy as M2-S6 D2 step 1; one shared function `copyServedTree`).
  - **Self-check:** every file of A equals its entry in `NOTESTEAD_WEB_ARTIFACT/bundle-manifest.json` (path and sha256), with none missing and none extra. If `NOTESTEAD_WEB_ARTIFACT` is unset, the fixture fails with the M2-S6 instruction (never a skip).
- **B, B2 and O** are copies of A, each with its own changes (D2, D3) and its own `bundle-manifest.json` written **beside** the tree, never inside it: A's manifest with the changed files' `sha256`/`size` replaced and `notestead.testBundle` set to `B`, `B2` or `O`. That manifest is the oracle for "serves bundle B".
- Location: `test-results/e2e/m2-s5-bundles/<worker>/{a,b,b2,o}` and `{b,b2,o}.bundle-manifest.json`. Modes 0644 for files and 0755 for directories (the container user 65532 reads them).
- **Never committed:** these trees hold upstream's bundle (D1 of M2-S6: upstream bytes only under `test-results/`, deleted at teardown). `check:no-upstream-copy` runs in WO-9.

**D2. B and B2 (the upgrade).** Each marker is a fixed string plus the worker's random nonce `N`:
- `environment.js` (our overlay's file) gains one final line, `globalThis.notesteadTestBundle = 'B-<N>';` (B2: `'B2-<N>'`). It executes, so the running page proves which bundle it started from.
- `app.bundle.js` gains a final line `/* notestead-test-bundle B-<N> */` (B2: `B2-<N>`). It does not execute; it makes upstream's own bundle differ, so the bytes the worker cached prove the app bundle was fetched again.
- **B2 only:** `serviceWorker.bundle.js` gains a final line `/* notestead-test-bundle B2-<N> */`. That is a worker update (F3), as a real pin bump that changes the worker would make.
- Everything else is byte-identical to A (self-check).

**D3. O (the downgrade): A minus its newest migration.**
- The expected numbers come from upstream source at `web.commit` (the M2-S6 D1 lookup, never committed): `base` = the last element of the `existingDatabaseVersions` literal in `packages/lib/JoplinDatabase.ts` (41); `n` = the number of entries in `packages/lib/services/database/migrations/index.ts`'s exported array (13). A's latest version is `base + n` (54), O's is `base + n - 1` (53).
- **Locating the list in the minified `app.bundle.js`** (two independent anchors, both must agree):
  1. the single occurrence of `<v>.default[<x>-<base+1>]` (here `b.default[e-42]`, the `migrations[targetVersion - 42]` lookup) gives the variable `<v>`; in the same module, `<v>=<wrap>(<req>(<id>))` gives the module id of the migration index;
  2. module `<id>`'s body holds exactly one array literal of `n` entries of the form `<name>.default`, assigned to the module's `default` export.
- O removes the **last** entry of that array (the `migration54` import), and nothing else. `environment.js` gains `globalThis.notesteadTestBundle = 'O-<N>';` as in D2.
- **Self-check:** exactly one anchor match and one array, `n` entries before and `n - 1` after, the diff to A only in that array and in `environment.js`. A failure throws with what was found (counts, never bundle text). After a pin bump this is the first thing to fail, loudly, for the planner to rule on. The pure function is unit-tested on synthetic strings (`tb-*`).
- O's code is otherwise the pinned code. F4 is why it starts normally on a profile it creates itself.

**D4. Redeploying `web` mid-test** (an extension of `extraWebs`, M2-S6 D3):
- `extraWebs.redeploy(web, { mountDist })`: stops and removes `web` (its log kept), then starts a new container of the image under test on **the same port**, with the new mount, and waits until `GET /` is 200 (60 s, `failFast` on exit). It returns the new `ExtraWeb`; the origin string must be equal (asserted inside). A port taken in between: the helper throws "port <P> was taken during the redeploy" (a **HARD STOP** for the executor, never another port: the origin must not change).
- `extraWebs.accessLog(web)`: that container's access-log entries so far, parsed (`method`, `uri` without query, `status`, time), from the JSON lines Caddy writes on stdout. Query strings are never kept (redaction rule). Pure parser unit-tested (`al-*`).
- Each M2-S5 test starts its **own** `web` (`extraWebs.start({ role: 'web-extra', port, mountDist: testBundles.a })`). The shared stack's `web` is never stopped, so every M2-S5 spec is in the parallel `chromium` project and none is `*.serial.spec.ts`.
- `role` gains no new value; the containers carry the run label, so the sweep removes them.

**D5. Browser state probes** (`tests/e2e/support/swState.ts`, all read in the app's page or a same-origin probe page, values only, never note text):
- `swController(page)`: `navigator.serviceWorker.controller?.scriptURL` (or `null`);
- `swCacheKeys(page)`: the paths in Cache Storage `v1` (`[]` if absent); `swCachedDigest(page, path)`: sha256 and size of the cached response body (`crypto.subtle`), or `undefined`;
- `cacheableLoadPaths(network, origin)`: every same-origin GET of the online load whose status was 200 and whose path or type matches upstream's caching rule (F3, the rule restated as a constant with its citation);
- `bundleMarker(page)`: `globalThis.notesteadTestBundle ?? null`.

**D6. The expected refusal is tolerated narrowly** (WS-1 stays on for everything else):
- `app.expectProfileRefusal(reason)` (on `WebApp`/`AppContext`) records an annotation `expect-profile-refusal` and, from then on, records that context's browser dialogs (message and time) and **accepts** them (an `alert` must be closed or the page blocks).
- At `finish`, a `startup` failure (`Startup failure during task: buildStartupTasks/openDatabase`) is excused only when a recorded dialog that `parseProfileRefusal` accepts (F1 text, with `Profile version` and `Expected version` as integers) follows it within 10 s. Every `step` (`rc= -1`/`rc= 10`) and `save` failure still fails the test; so does an unexplained startup failure.
- Pure decision function `excusedStartupFailures(failures, lines, dialogs)` and `parseProfileRefusal(message)`, unit-tested (`ws-r-*`, `pr-*`).
- Dialogs are listened to **only** after `expectProfileRefusal`, so M2-S1's own `waitForEvent('dialog')` is not disturbed.

**D7. Clearing site data** (`clearSiteData(app)` in `tests/e2e/support/localProfile.ts`):
1. close the app page (the app's worker releases its OPFS handles, as `opfsPaths` does);
2. open a probe page at `<origin>/manifest.json`; CDP `Storage.clearDataForOrigin({ origin, storageTypes: 'all' })`;
3. reload the probe and **prove** the effect (bounded 30 s, `waitFor`): no service-worker registration (`navigator.serviceWorker.getRegistrations()` empty), Cache Storage empty (`caches.keys()` empty), the OPFS listing empty (the `opfsPaths` walk). Anything left: the helper throws, naming what survived;
4. close the probe. The caller then opens a new page.

**D8. Data snapshots and comparison** (`tests/e2e/support/snapshot.ts`, pure parts unit-tested `sn-*`):
- `restSnapshot(dataApi)`: every note (`id,title,body,parent_id,is_todo,todo_due,todo_completed,is_conflict,deleted_time,updated_time`, `include_deleted=1`) and folder (`id,title,parent_id`), paged until `has_more` is false; bodies kept as sha256 only.
- `compareSnapshots(s0, s1)`: `missing` (in S0, not in S1), `changed` (field-wise, values never printed, only the id and field names), `added` (in S1 only) and `conflicts` (`is_conflict = 1`). Failure messages are value-free (M2-S2 r1 C4).
- The web side of the comparison reads the OPFS database **once** (`localDatabaseFiles(app)`: the main database file through a probe page while the app page stays open, exactly as `expectStoredLocally` reads it with `openProbe`/`readDatabaseFiles`) and searches that one read with `findInDatabaseFile` for every expected needle. An absence (Z) counts only when the same read found every expected needle and at least one file was read. Missing needles are reported by item id and kind (`title`/`body`), never by value.

**D9. "Not run" counts as failed (M2-S1 r1 C3).**
- A reporter `tests/e2e/support/notRunReporter.ts`, registered in `playwright.config.ts` after the redacting reporter. At `onEnd` it collects every test whose last result is `skipped` or `interrupted`. The suite has no skips by rule, and `@network` tests are filtered out before the run, so each one did not run: a `chromium` failure blocked its dependent `chromium-serial` project, or the run stopped (`globalTimeout`, `maxFailures`).
- It prints `NOT RUN (counts as failed): <n> test(s)` and one line per test (project, file, title), writes `test-results/e2e/not-run.json` (`{ count, tests: [{ project, file, title, status }] }`), and returns `{ status: 'failed' }` from `onEnd` when `n > 0`.
- The serial rule in `docs/testing/strategy.md` §4 changes from "accepted, since the run is already red" to "counts as failed and is listed by name".
- **Pure part** `notRunTests(suite)` unit-tested (`nr-*`). **Integration proof** `H-NR-01` runs real Playwright on a throwaway config with two browserless projects, the second depending on the first.
- **ci-cd (optional, not blocking):** show `not-run.json` in the e2e job summary (CC-NR).

**D10. L20 (the tie, user decision 2026-11-13; ARCHITECTURE §9).** The M2-S6 D9 rule applies unchanged: a qualifying failure (only `rc= -1`/`rc= 10`; shape A, B or WS-1-only; `web-sqlite.json` attached; nothing else failing in that test) is an occurrence. It is recorded with the test, `rc`, statement kind, database and whether startup failed (`node tests/harness/tools/scan-l20.ts test-results/e2e`), and **never re-run to get green**. The **third** occurrence in one local Playwright invocation, or on one arm64 runner, is a **HARD STOP**; x64 counts and never blocks. M2-S5 starts the app about 12 times per run. **The expected refusal of M2-AC16-02 is not an occurrence** (no `rc` line; D6 excuses it).

**D11. Bounds.** App start: `appStartTimeoutMs` (3 min) per start, the offline one included. The cache filling before going offline: 60 s (`expect.poll`). A redeploy until ready: 60 s. Access-log reads: 30 s. The refusal dialog: `appStartTimeoutMs`. "The app does not open" (the NEG): `holdsFor` 10 s after the refusal. The OPFS reads: 30 s. Specs use `longSpecTimeoutMs`.

## Requirements on the implementation
- **R1 (SE): the browser part of the rollback runbook**, in `deploy/web/README.md` under the heading `## Rolling back the web app` (M5-S4 later moves or links it into `deploy/README.md`). It is ADR-0005 Decision 4 as user steps, matching what `M2-AC16-02` does:
  1. sync in the web app (so nothing is lost);
  2. redeploy the previous `web` image by its digest;
  3. close every tab of the web app;
  4. delete the site's data in the browser (Chromium: site settings → "Delete data"; Firefox: "Clear cookies and site data"; Safari: Website Data → Remove);
  5. open the web app again, sign in, enter the master password, and sync.

  What is lost: unsynced local edits, the stored E2EE master password entry, installed plugins (reinstall them). And F5: a second copy of upstream's welcome notebook appears in the account; delete it. Link ADR-0005. Tested by `U-AC16-RB-01`.
- **No product code change is expected.** The upgrade and offline paths are upstream's service worker plus our `Cache-Control: no-cache` (F3). If an E2E test fails on a product fact, the executor records it for the orchestrator: our files (`deploy/web/Caddyfile` headers) go to the SE, upstream behaviour is reported and never worked around.
- **The SE never edits `tests/**`.** Disagreements go under `## Disputes`.
- **Architect (briefs, not blocking):**
  - F5: L5/L14 wording ("each recovery adds another welcome notebook");
  - ADR-0005 Decision 4 can point to `deploy/web/README.md` §"Rolling back the web app" until M5-S4;
  - M6: on a pin-bump PR, run M2-AC16 with A = the previous pin's artifact and B = the new one. That needs an optional `NOTESTEAD_UPGRADE_FROM_ARTIFACT` in the harness (QA, M6) and the previous artifact in the bump workflow (ci-cd).
- **ci-cd (optional):** CC-NR, the job summary line from `not-run.json`.
