## `check:workflows` contract (M1-AC30 to M1-AC32)
Additions to M1-S3's contract (`docs/test-plans/M1-S3.md` §Command contract). Same output format (`<file>:<line>:<col>: <message> [<rule>]`), file paths relative to the tree root, exit 1 on any finding.
- **`[yaml-alias]`** (only if the engineer chooses to reject aliases instead of resolving them): any alias (`*name`) in a workflow or action file. If aliases are resolved instead, `[sha-pin]` and `[permissions]` must apply to the resolved job or step and name it (the job id for a job; the job id for a step).
- **`[workflow-shape]`:** a job, a step (workflow or composite action) that is not a mapping, after alias resolution. Reported with the job id. Never skipped. actionlint's own `[syntax-check]` does not count.
- **`[forbidden-trigger]`:** `pull_request_target` or `workflow_run` in `on:` in any form (scalar, sequence, mapping), naming the trigger. Replaces `[pull-request-target]`; the two M1-S3 fixtures `pull-request-target--head-{sha,ref}-checkout` now expect `[forbidden-trigger]` (their file names are kept for traceability). An allow-list, if one is added, starts **empty** and names files, through an ADR-0009 amendment (A7); `--dir` fixture trees must not be able to match it by file name alone.
- **`[local-action]`:** a step `uses: ./<path>` with neither `<root>/<path>/action.yml` nor `action.yaml`. The root is the repo root, or for `--dir <tree>/.github/workflows` the `<tree>`. A found action is checked with the composite-action rules, and its findings name the action file (relative path); some line also names the workflow file and the `./<path>`.
- The final summary line names the rules it ran (`[sha-pin] [permissions] [forbidden-trigger] …`); no test depends on its wording.

## M1-AC33 contract (seams in `.github/scripts/pinnedTools.ts`)
The tests declare this contract (`PinnedToolsContract`), so a missing seam fails each test, not the type check.
- `pinned-tools.json`: each `assets.<arch>` gains **`binarySha256`**, the sha256 of the extracted binary (the `member`), 64 lowercase hex. Cross-check on the Pi (arm64), computed by QA from the cached binaries: actionlint 1.7.12 `ac0323433c2853ec3fb978c611430c5b3dc5d43c58d1a1ec031b00ab572beb60`, shellcheck 0.11.0 `127f13925eadd52c341bca0ebaf9ab0dbd78c6468f30a8f262a528bf8de47546`. The x64 values must come from the release tarballs (lead verifies).
- `export const downloadTimeoutMs = 120_000`.
- `resolveTool(name, tool, log, env = process.env, deps = {})` with `deps.fetch?: (url, { signal }) => Promise<{ ok, status, arrayBuffer() }>` (default: global `fetch`) and `deps.deadline?: (ms) => AbortSignal` (default: `AbortSignal.timeout`). The download is bounded by `deps.deadline(downloadTimeoutMs)` **whatever the fetch does** (a fetch that ignores its signal, or a stalled body, still fails when the signal aborts); the error carries the offline hint (`set ACTIONLINT=<path> … to run offline`) and says it timed out.
- The managed binary (cached or fresh) is hashed **before it is ever executed** (the version check runs it). A mismatch is an error naming the path and `sha256`; a fresh mismatching binary is not left in the cache. A pin without `binarySha256` fails, naming the field. `ACTIONLINT`/`SHELLCHECK` overrides keep the version check only (unchanged).

## Interpretations and decisions
1. **M1-AC33 "under fake timers".** No mock clock reaches `AbortSignal.timeout`. The test injects the deadline signal and fires it itself, which is the fake-timer equivalent (time is controlled by the test, nothing waits); it also checks that the production default is 120 000 ms with `AbortSignal.timeout`.
2. **M1-AC33 is a unit test under node:test**, not Jest: `pinnedTools.ts` uses `import.meta`, which ts-jest (CommonJS) cannot compile. The file lives in `tests/acceptance/m1-s8/` so `ci.yml`'s acceptance step runs it on both architectures without a workflow change.
3. **M1-AC30's rule ID** is the engineer's choice between resolution and rejection; the tests accept either, and require `[workflow-shape]` for non-mappings in both cases.
4. **"Traces are uploaded on failure"** is read as: on failure and on success alike (strategy §7: evidence always), but only through the gate.
5. **Shellcheck scope:** tracked shell scripts outside `docs/` (the spikes' scratch scripts are the architect's evidence, not shipped or run by CI).
