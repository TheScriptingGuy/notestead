## Findings (planning, from upstream at the pin and the plugin at 2.1.2)
**P1. Enabling plugin support, and the install-from-file flow.**
- The setting is `plugins.pluginSupportEnabled`: default `false`, `autoSave`, Mobile only (`upstream:packages/lib/models/settings/builtInMetadata.ts:1448-1459`).
- While it is off, the Configuration screen's **Plugins** section shows upstream's `EnablePluginSupportPage` with a button **"Enable plugin support"** (`upstream:packages/app-mobile/components/screens/ConfigScreen/ConfigScreen.tsx:529-541`, `…/plugins/EnablePluginSupportPage.tsx:119`).
- Once it is on, the section shows the plugin list (`PluginStates`) and, under the **"Advanced settings"** accordion, a button **"Install from file"** (`ConfigScreen.tsx:503-528`, `{ advanced: true }` at `:526`; accordion at `:684-695`; `canInstallPluginsFromFile()` is true on web, `…/plugins/PluginUploadButton.tsx:27-29`).
- On web the button creates a hidden `<input type="file">`, clicks it, and registers the chosen `File` as a read-only virtual file `/tmp/<uuid>` (`upstream:packages/app-mobile/utils/pickDocument.ts:25-67`). This is the same picker as M2-AC7a's "Attach file", so Playwright's `filechooser` works.
- The virtual path has no extension, so the extension becomes `.jpl` unless the browser says `application/javascript` (`PluginUploadButton.tsx:55-67`). `PluginService.installPlugin` then copies the file to `pluginDir/<id>.jpl` (`upstream:packages/lib/services/plugins/PluginService.ts:678-713`, `destPath` at `:704`), and the button saves `plugins.states` with `defaultPluginSetting()`, which means enabled (`PluginUploadButton.tsx:78-82`).

**P2. Where the plugin is stored, and the reload.**
- The web file system is **OPFS**, under the directory `joplin-web` (`upstream:packages/app-mobile/utils/fs-driver/fs-driver-rn.web.worker.ts:158`).
- `pluginDir` is `/app//plugins` and `cacheDir` is `/app//cache` (`upstream:packages/app-mobile/utils/buildStartupTasks.ts:180-184`; `getAppDirectoryPath()` is `/app/`, `fs-driver-rn.web.ts:217-219`). The `.jpl` is extracted to `cacheDir/<id>/` (`PluginService.ts:321-375`).
- `plugins.states` is a database setting (`builtInMetadata.ts:1419-1427`). Both are local to the browser profile, and **neither syncs**.
- **On reload:** `PluginRunnerWebView` loads only when plugin support is on (`upstream:packages/app-mobile/components/plugins/PluginRunnerWebView.tsx:147-157`). `loadPlugins` runs every `.jpl` in `pluginDir` that `plugins.states` enables (`upstream:packages/lib/services/plugins/loadPlugins.ts:61-64`, `PluginService.ts:481-563`). So an installed plugin survives a reload, and is lost with "clear site data" (as ADR-0005 already says).

**P3. Where the plugin runs.**
- **In nested sandboxed iframes, not in a worker.** The runner is an `ExtendedWebView` (`webviewInstanceId='PluginRunner2'`). On web, that is a sandboxed `srcdoc` iframe (`upstream:packages/app-mobile/components/ExtendedWebView/index.web.tsx:118-125`).
- Inside it, each plugin gets its own `srcdoc` iframe with `sandbox="allow-scripts allow-modals"` (`upstream:packages/app-mobile/components/plugins/backgroundPage/startStopPlugin.ts:29-79`; `upstream:packages/lib/utils/dom/makeSandboxedIframe.ts:11-26`).
- On web the script text is passed in directly (`upstream:packages/app-mobile/components/plugins/PluginRunner.ts:53-60`). `window.joplin` is the API proxy (`…/backgroundPage/initializePluginBackgroundIframe.ts:12`).
- Plugin `console` output reaches the page through these frames. **The harness never treats a console line as readiness.**

**P4. `platforms: ["desktop"]` plugins: installed, but marked incompatible and never run (not refused).**
- `installPlugin` performs **no compatibility check** (`PluginService.ts:678-713`). The upload succeeds and the `.jpl` is stored.
- `runPlugin` throws `Plugin "<id>" was disabled: This plugin doesn't support Joplin Mobile.` (`PluginService.ts:626-631`, the text from `describeIncompatibility` at `:594-617`). `loadAndRunPlugins` logs `Could not load plugin` and goes on (`:560-563`).
- The web build runs as `AppType.Mobile` (`PluginService.ts:582-584`; `minVersionForPlatform.ts:6-23`), so `["desktop"]` is unsupported. A manifest without `platforms` also defaults to `["desktop"]`, unless its id is on upstream's short allow-list (`…/utils/isCompatible/getDefaultPlatforms.ts`).
- **In the UI:** the installed card shows an **"Incompatible"** chip, and pressing it shows that message (`…/ConfigScreen/plugins/InstalledPluginBox.tsx:34-36`, `…/PluginBox/PluginChips.tsx:57-71`).
- So **NEG 2 asserts "marked incompatible and not run"**, which is one of the two outcomes the AC allows.

**P5. `views.menus` on web: registered without error, rendered nowhere (L2 confirmed).**
- `joplin.views.menus.create` adds a `MenuController` with no platform check (`upstream:packages/lib/services/plugins/api/JoplinViewsMenus.ts`), so the plugin's `setupMenu` does **not** throw. Its `main()` would otherwise stop before the scheduler starts (plugin `src/index.ts:25-50`).
- app-mobile renders plugin views only as:
  - `noteToolbar` commands in the note's action menu (`upstream:packages/app-mobile/components/screens/Note/Note.tsx:1327`, `:1462-1468`);
  - `editorToolbar` buttons (`upstream:packages/app-mobile/components/EditorToolbar/utils/allToolbarCommandNamesFromState.ts:47`).

  Nothing renders `menu` or `menuItem` views.
- **The plugin's menu:** "Repeating Todos", at Tools, with the commands "Update All Recurrence Information", "Update Overdue To-Dos" and "Reschedule Overdue To-Dos to Today" (plugin `src/gui/menu.ts`, `src/core/commands.ts`). It must therefore be absent.
- **Its `noteToolbar` button** "Open Recurrence Dialog" (`src/gui/toolbar.ts`) **does** appear in the note's action menu. This is the **positive control** for NEG 1, and the harness's signal that the plugin is running.

**P6. How the plugin decides "repeating", and how it reschedules (plugin 2.1.2).**
- **The recurrence** is stored in the note's **`user_data`**, under the plugin's id as namespace and the key `recurrence` (plugin `src/core/database.ts:41`, `:96-108`). The value is `RecurrenceData` (`src/model/recurrence.ts:51-68`, `recurrenceToObject` at `:314-333`).
- **The format** is upstream's `{ [pluginId]: { recurrence: { v: <RecurrenceData>, t: <ms> } } }` (`upstream:packages/lib/models/utils/userData.ts:31-50`).
- **A tag titled `recurring`** is only an index: the sweep visits tagged to-dos only (`database.ts:43`, `:140-175`, `:237-254`).
- **Completion:** when a tagged to-do with `enabled: true` has `todo_completed ≠ 0` and `todo_due ≠ 0`, `processTodo` does the following (`src/core/recurrence.ts:197-242`):
  - it sets `todo_due` to `getNextDateAfter(due, now)`: the first step of the interval after the old due date that is also after now (`src/model/recurrence.ts:221-238`, day step `next.setDate(initial.getDate() + step)` at `:163`, in the browser's local time);
  - it sets `todo_completed` to 0;
  - it resets sub-task checkboxes;
  - it writes the recurrence back.

  It never creates a new note. So for a due date in the future, the new due date is **exactly one local calendar day later, at the same wall-clock time**.
- **What triggers it:**
  - `workspace.onNoteChange`, which upstream fires **only for selected notes** (`upstream:packages/lib/services/plugins/api/JoplinWorkspace.ts:113-125`);
  - a safety-net sweep every `updateFrequency` seconds, **default 30** (plugin `src/core/timer.ts:98-113`, `src/core/settings.ts:31-40`).

  A to-do ticked in the note list is not selected, so on web **the sweep advances it within about 30 s**.
- **Seeding through REST is possible:** the headless REST `PUT /notes/:id` passes any non-read-only field, `user_data` included, to `Note.save` (`upstream:packages/lib/services/rest/routes/notes.ts:543-575`, `…/utils/readonlyProperties.ts`). The seed is checked by reading `user_data` back (step 0 of M2-AC9-01). `POST /notes` copies only known fields (`notes.ts:105-172`), so `user_data` goes in by `PUT`.

**P7. The repository install on web: direct cross-origin fetches from the browser, not through our proxy.**
- The **Plugins screen fetches the repository as soon as it is shown**, whatever the user does: `PluginStates` mounts `useRepoApi`, whose effect runs `repoApi.reinitialize()` (`…/ConfigScreen/plugins/PluginStates.tsx:90`; `…/plugins/utils/useRepoApi.ts:24-46`).
- **The URLs** (`upstream:packages/lib/services/plugins/RepositoryApi.ts`):
  - **Mirror probe** (`:31-57`): `GET <base>/.gitignore`. It tries, in order, `https://raw.githubusercontent.com/joplin/plugins/master`, `https://cdn.staticaly.com/gh/joplin/plugins/master`, `https://ghproxy.com/https://raw.githubusercontent.com/joplin/plugins/master`, `https://cdn.jsdelivr.net/gh/joplin/plugins@master` and `https://raw.fastgit.org/joplin/plugins/master`, and stops at the first that answers.
  - **The manifests:** `GET <base>/manifests.json` (`:117-118`).
  - **Releases:** `GET https://api.github.com/repos/joplin/plugins/releases` (`:151-165`). This is fetched on web too, but not used there.
  - **The plugin:** `GET <base>/plugins/<id>/plugin.jpl`, because "On web, downloading from a release is blocked by CORS" (`:169-185`). It is downloaded with the browser's `fetch` (`upstream:packages/app-mobile/utils/shim-init-react/index.web.ts:54-60`; `downloadPlugin` at `RepositoryApi.ts:243-262`).
- **These requests go straight from the browser (through upstream's service worker) to GitHub and the mirrors.** They do not pass our same-origin proxy. The service worker handles every fetch and rewrites only COEP and CORP on responses (`upstream:packages/app-mobile/web/serviceWorker.ts:79-131`).
- **Under COEP `credentialless`,** CORS fetches to hosts that send `Access-Control-Allow-Origin: *` (raw.githubusercontent.com, api.github.com) are allowed.
- **Our `web` container sends no CSP** (`deploy/web/Caddyfile` sets only COOP/COEP), so nothing of ours blocks them. **No proxy or CSP change is needed.**
- **Consequence for the per-commit tests:** M2-AC9 opens the Plugins screen, so it makes these requests too, but never depends on their answers (P7a below). Only M2-AC10 needs them to succeed.

**P7a. Network policy.** The harness's network policy (`tests/e2e/support/network.ts`) flags every cross-origin request except `HEAD https://joplinapp.org/connection_check/`.
- Every M2-S4 spec names the repository prefixes with `webNetwork.allow(…)`. That is the exact list above, as `pluginRepositoryPrefixes`, each ending in `/`:
  - `https://raw.githubusercontent.com/joplin/plugins/master/`
  - `https://api.github.com/repos/joplin/plugins/`
  - `https://cdn.staticaly.com/gh/joplin/plugins/master/`
  - `https://ghproxy.com/https://raw.githubusercontent.com/joplin/plugins/master/`
  - `https://cdn.jsdelivr.net/gh/joplin/plugins@master/`
  - `https://raw.fastgit.org/joplin/plugins/master/`
- **Any other cross-origin request still fails the test.**

**P8. Plugin alarms on web.** `onNoteAlarmTrigger` never fires on web, because alarms are a no-op there (L1, `AlarmServiceDriver.web.ts`). The plugin's "reset alarm when not done" path therefore runs on web only through its 30 s sweep, and only while a tab is open (L3). That path is out of scope (see "Out of scope").

## Interpretations (for the orchestrator and the user)
- **I1, the fixture source:** the latest release (2.1.2) has no `.jpl` asset. The bytes are taken from that release's npm publish, cross-checked against the official repository (see "Fixture provenance"). **No decision is needed** unless the user objects.
- **I2, the licence:** the plugin's `LICENSE` (GPL v3) and its `package.json` (MIT) disagree. Both are compatible, so **nothing blocks this story.** The user may want to align them in the plugin repo.
- **I3, a privacy note for L2 (architect):** opening Configuration → Plugins with plugin support on contacts GitHub (raw.githubusercontent.com, api.github.com). If GitHub does not answer, the app tries up to four third-party mirrors (staticaly, ghproxy, jsdelivr, fastgit), straight from the browser (P7). This is like L15. **Brief for the architect:** add it to L2, plus P4's behaviour (an incompatible plugin installs, shows "Incompatible" and never runs) and P2's (plugins are per browser profile, not synced). The architect may also want to note it in the deploy guide's privacy section. **QA does not edit the architecture.**

**D2. The seed goes through REST, not the plugin's dialog.**
- R is created with `POST /notes { title, is_todo: 1, todo_due, parent_id }`. Then:
  - `PUT /notes/:id { user_data }`;
  - `POST /tags { title: 'recurring' }`, only after checking that no tag with that title exists (the account is fresh);
  - `POST /tags/:id/notes { id }`.
- **The seed check:** `GET /notes/:id?fields=user_data` parses through `recurrenceOf` to the seeded `v`, and `GET /notes/:id/tags` is `['recurring']`. T has no `user_data` and no tag.
- **Why REST:** it pins the exact recurrence the plugin reads, and it keeps the plugin's own dialog out of the core assertion. Setting a recurrence from the web UI is a proposal (see "Out of scope"). The format is coupled to plugin 2.1.2, which is the pinned fixture. `rec-02` names that coupling, so a fixture bump updates it on purpose.
- **Order:** seed and headless sync **before** the web app first syncs. The `recurring` tag then already exists in the web app when the plugin starts, so `findOrCreateTagId` finds it instead of creating a second one.

**D3. The oracle for the new due date is the local calendar, not the plugin's arithmetic.**
- Both seeds are due `localNoonEpoch(now, +1, 'Europe/Amsterdam')`. The expectation is `localNoonEpoch(now, +2, …)`, computed in Node with `Intl` (D10).
- Noon is never in a skipped or repeated hour. Tomorrow's noon is always in the future when the to-do is ticked, so exactly one step is taken (P6).
- The expected value is computed once, before the click. If the test starts before local midnight and the click lands after it, "tomorrow" is still the seeded day, so the oracle stays right.

**D4. The UI wait first, then one cycle, then REST.**

**D5. "The same to-do."**

## Planner ruling on HARD STOP H5 and the records R1 to R6 (2026-11-19)
### H5: a defect in the plan's check, not in upstream. NEG1 reads what the app renders, in the top frame only
**The cause, confirmed.** P5 asked for `frameHtml()` over every frame. That includes the plugin's own sandbox `srcdoc` frames (P3), whose `<script>` holds the plugin bundle and so all four labels as string literals. The check could never pass while the plugin runs. It says nothing about upstream. The executor stopped correctly.

**Option 2 (strip `<script>`/`<style>` from `frameHtml()`) is rejected.**
- Attribute values and hidden markup would still be read.
- Any future plugin frame that inlines its strings differently would trip it again.

**Option 1 is taken, with the frame scope made exact.** It works because of where a rendered menu would have to appear:
- Upstream renders every plugin view the web app shows (`noteToolbar` items, editor toolbar buttons) in the app's own react-native-web DOM, the **top frame** (P5).
- A plugin's background frame has an empty `<body>` and only scripts (`startStopPlugin.ts:52-68`).
- So if a plugin menu ever rendered, it would be in the top frame.

**NEG1, as ruled.** It replaces both `frameHtml()` assertions of plan P5/NEG1 and work-order step NEG1. The new page-object method is `JoplinWebApp.renderedTopFrame(): Promise<{ text: string; aria: string }>`:
- `text` is `page.locator('body').innerText()` of the **top frame only**. `innerText` leaves out `<script>`/`<style>` content and `display:none` elements, and never enters child frames.
- `aria` is `page.locator('body').ariaSnapshot()` of the top frame. It adds the accessible names that `innerText` misses, such as icon-only buttons with an `aria-label`.
- The executor **RECORDs** whether `ariaSnapshot()` showed any child-frame content. Neither plugin frames (scripts only, inert) nor the viewer frame hold the labels, so the result doesn't change the ruling.

## Planner ruling on the S-NEG1c HARD STOP (2026-11-20): a real harness defect in the E2EE device seed, fixed now (WO-7a)
**The mechanism, from the CLI code** (`upstream:packages/app-cli/app/command-sync.ts`; the CLI is 3.7.1, so the device image check in WO-7a step 0 confirms the option exists there):
- Each `sync` command takes a per-profile lock with `proper-lockfile`. It first checks `isLocked` and throws `Synchronisation is already in progress.` if the lock is held (`:145-149`).
- When the sync ends, `cleanUp()` calls `this.releaseLockFn_()` **without awaiting it** (`:160-165`). `proper-lockfile`'s release is asynchronous: it removes the lock directory.
- `joplin batch` runs its commands one after another in **one process**. So the second `sync` can run its `isLocked` check before the first sync's lock directory is gone.
- That is exactly the log: the first sync `Completed`, then `Synchronisation is already in progress.`, then exit 1.
- The race entered our harness with M2-S3 WO-11 (`236686d`), which made `device.mjs` sync twice in one batch. It is intermittent, and it can hit **any** run, CI included:
  - in `globalSetup` (the default account), it aborts the whole run before any test;
  - in a per-test `e2eeAccount`, it fails that test.

  So it is a harness defect, not a recorded follow-up. It is fixed before more runs (WO-7a).

**The fix: deterministic, no retry and no wait.** The second sync in the batch runs as `sync --use-lock 0`.
- That option only skips the local lock check (`:42`, `:143-158`). Inside one batch process the syncs are already sequential (batch awaits each command), and nothing else uses the device's throwaway profile, so the lock protects nothing there.
- A retry on the message would hide the race instead of removing it, and is rejected.
- The first `sync` keeps the lock.
- The batch is built by a small exported function, so the rule is tested before it is used (WO-7a).

**(1) Re-running S-NEG1c unchanged: no, not before WO-7a.** An unchanged re-run would only roll the dice again. S-NEG1c (its edit unchanged) runs after WO-7a's GREEN, on the rebuilt device image. That run also proves the device image rebuild. The failed attempt is not a sensitivity result and not an L20 occurrence. It is listed as harness failure **HF-1**, with its log.

**For the orchestrator (not M2-S4 work):** the unawaited release at `command-sync.ts:163` is an upstream defect, and a candidate upstream issue for the user.
- The headless service is not expected to be affected: it runs every `sync` as its own CLI process, at least ~30 s apart (ADR-0003).
- `proper-lockfile` treats a lock older than its `stale` time as free (the library's documented default is 10 s; this was not measured here).
- The SE may want to confirm this from the supervisor's logs. It is recorded here only.
