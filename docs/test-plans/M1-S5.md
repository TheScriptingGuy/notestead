- **Branch:** `feat/M1-S5-headless-container`. **Owner of this plan:** qa-specialist. **Implementer:** senior-engineer.

No unit tests are planned by QA here; the supervisor's state machine is M3-AC1.

## Image contract (binding for the implementation)
The tests build and run the image exactly like this. Nothing else is assumed.

- **Containerfile:** `packages/headless/Containerfile` (ADR-0009 A11: the headless image installs the workspace's own code from `yarn.lock`).
- **Build:** `podman build -f <ctx>/packages/headless/Containerfile -t localhost/notestead-headless:m1-s5-test <ctx>`.
  - `<ctx>` is a **clean copy of the repository's files**, as a fresh checkout has them: `git ls-files --cached --others --exclude-standard`. No `node_modules`, no `.yarn/cache`, no `test-results`. A build that works from the repo root but not from a clean copy fails here, and in CI.
  - The install step must see the whole `packages/headless/` directory of the context (the NEG adds `packages/headless/test-fixtures/<pkg>/` as a `file:` dependency, with its `yarn.lock` entry). A `.containerignore`/`.dockerignore` must not exclude `packages/headless/test-fixtures/`.
  - Network during the build: the npm registry, the `sqlite3` prebuilt download (GitHub releases), corepack's yarn download. Nothing else.
- **Image:** multi-arch base (ADR-0006); non-root `USER`; `node` on `PATH` (the probes run `node`); `/bin/sh` present (the start gate below); `ENTRYPOINT`/`CMD` start the supervisor with no extra arguments; `/data` exists and is owned by the image's user, so a fresh named volume mounted at `/data` inherits that owner.
- **Run** (ADR-0006 hardening and topology):
  ```
  podman run -d --init --read-only --tmpfs /tmp --cap-drop=ALL --security-opt no-new-privileges --memory 768m \
    --network <back> --ip <back>.60 --network-alias headless \
    -v <fresh volume>:/data \
    -v <file>:/run/secrets/joplin_password:ro -v <file>:/run/secrets/e2ee_master_password:ro \
    -v tests/fixtures/m1-s5/in-container:/opt/notestead-test:ro \
    -e JOPLIN_SERVER_URL=http://web:8089/joplin-server -e JOPLIN_USERNAME=<email> \
    localhost/notestead-headless:m1-s5-test
  ```
  No published port, no `--user`, no command override (except the start gate). `<back>` is `--internal`; its only other members are `web` (alias `web`, internal listener `:8089`) and the test's observer.
- **Configuration:**

  | Input | Required | Meaning |
  |---|---|---|
  | `JOPLIN_SERVER_URL` | yes | `sync.9.path` for the CLI. In the tests `http://web:8089/joplin-server`; AC15-neg uses `http://<web back address>:8099/joplin-server` (connection refused). |
  | `JOPLIN_USERNAME` | yes | `sync.9.username` (a fresh user per test) |
  | `/run/secrets/joplin_password` | yes | sync password. The file **ends with `\n`** in the tests. |
  | `/run/secrets/e2ee_master_password` | yes | E2EE master password. The file has **no** trailing newline. |

  Exactly one trailing `\n` (or `\r\n`) is stripped from a secret file; every other byte is the secret. The test values contain a space, `Δ`, `$` and `!`.
- **Supervisor HTTP:** `0.0.0.0:8090` inside the container.
  - `GET /healthz`: `503`, `Content-Type: application/json`, body `{"state":"starting"}` (more keys allowed) from the moment it first answers until the initial `sync` **and** `e2ee decrypt` have finished successfully **and** the CLI Data API answers; then `200`, `application/json`, `{"state":"ready","lastSync":"<ISO-8601 UTC, as Date#toISOString>"}`. `lastSync` is the time of the initial sync (its start or its end). Once answering, `/healthz` keeps answering.
  - If the initial sync fails, `/healthz` never reports ready. The process may keep retrying (state stays non-ready, status 503) or exit; M3-AC1 adds backoff and `degraded`.
  - Every other path: anything except a relay of the Data API (404 is the obvious answer). The gateway is opt-in and M3.
- **CLI (ADR-0003):** run only as children of the supervisor, with `--profile /data/profile` and only these commands: `config --import` (secrets and `api.token` on **stdin**), `sync`, `e2ee decrypt --force`, `server start --quiet`, `version`. No other global flags; never `--upgrade`. The Data API listens on `127.0.0.1:41184` (`api.port` = 41184).
- **Findings that matter for the implementation** (QA probes with the pinned CLI 3.7.1):
  - `joplin sync` **exits 0 when the sync failed**. With no route (`--network none`) it prints `Completed: … Last error: FetchError: request to …/api/sessions failed, reason: connect ENETUNREACH …`. With the target **refusing connections** (AC15-neg) it retries for ~2 min and prints only `Completed: 05/10/2026 18:15 (112s)`, **no error line at all** (the CLI process lived ~207 s on the Pi; upstream drops "retryable" network errors from the report, `packages/lib/Synchronizer.ts` ~L1241). Neither the exit code nor the output proves the initial sync worked; AC15-neg checks that the supervisor finds out some other way.
  - `joplin e2ee decrypt --force` exits 1 with `DecryptionWorker: cannot start because no master key is currently loaded.` when no master key was synced (nothing synced, or an account without E2EE; the latter is out of scope here).

### Start gate (M1-AC14, M1-AC15, AC15-neg)
To watch the container's processes from the very first one, these tests start the image with its own command behind a gate: `--entrypoint /bin/sh <image> -c 'while [ ! -e /tmp/.nst-watch-ready ]; do sleep 0.05; done; exec "$@"' nst-gate <image ENTRYPOINT…> <image CMD…>`. The process watcher, attached with `podman exec`, creates the file after its first sample; `exec` then replaces the shell with the image's own start command, so the process tree (`--init` as PID 1, the supervisor, its CLI children) is the same as without the gate.

### How the tests reach the Data API
The CLI's Data API exists only inside the headless container's network namespace (that is M1-AC17). Tests call it from there: `podman exec <headless> node /opt/notestead-test/data-api.mjs [--no-token] <path>`. The probe reads `api.token` from `/data/profile/settings.json` at call time (where `config --import` stores it; spike S3) and never prints it.

## Fixtures
- **Fresh user per test** (ADR-0007): admin login, `POST /api/users`, then `PATCH /api/users/:id {password, must_set_password: 0}` with a strong unique password; the test logs in once to prove it works.
- **Secrets:** `<core> Δ$x!` where `<core>` is `nst<label><24 hex>`. The watcher searches for the full value **and** the core (which survives JSON, shell or URL escaping). Written to a temp dir as `0444` files and bind-mounted read-only at `/run/secrets/*`; given to fixtures on stdin only.
- **Other device** (`tests/fixtures/m1-s5/device/`): `node:22-bookworm-slim` plus `npm install -g joplin@<cli.version>` (the spike S3 recipe; a fixture, never the image under test). `device.mjs` reads `{syncUrl, email, password, masterPassword, folder, notes}` on stdin, runs `config --import` (stdin), then one `joplin batch` with `e2ee enable --password …`, `mkbook`, `use`, `mknote`, `set … body …`, `sync`, `ls --format json` (S3: `e2ee enable` persists only inside `batch` with `sync`), then `e2ee status`, and prints the note ids. ~2 min image build once per run; ~15-20 s per test on the Pi.
- **Fixture controls (every test that seeds):** `e2ee status` says `Enabled`; the note's raw item on the server (read directly as the user) has `encryption_applied: 1` and contains neither title nor body.
- **Process watcher** (`tests/fixtures/m1-s5/in-container/proc-watch.mjs`, run with `podman exec -i`): samples `/proc` every 10 ms; needles arrive on stdin; reports processes (redacted argv, first/last seen, `fd/0` target of `--import` processes), needle hits by label only (never values), and any `/proc` file it could not read.
- **Health observer** (`tests/fixtures/m1-s5/health-watch.mjs`): one JSON line per poll (`t` = host clock, shared with the watcher).
- **Image probe** (`tests/fixtures/m1-s5/in-container/image-probe.mjs`): run in the image with `--entrypoint node`, hardened. Lists installed packages (dir, name, version, bundles deps), every `*.node` file and every `notestead-postinstall-ran` marker; for each installed `joplin` package it `require`s `sqlite3` through that package (`createRequire`), reads the binding's ELF machine, runs `select sqlite_version()` and runs `joplin --profile <tmp> version`.
- **NEG fixture package** (generated in code, never a committed `package.json`): `notestead-fixture-postinstall@1.0.0`, MIT, whose `postinstall` writes `notestead-postinstall-ran` into its own directory and into `INIT_CWD`.
- **Lockfile reader** (`tests/contract/support/lockfile.ts`): the Berry `yarn.lock` as YAML; allowed `name@version` from each entry's `resolution` and `version`; workspaces at any version. Validated against this repo's own install: 938 installed packages, 0 outside the lockfile.

### Harness validation (before RED)
As in M1-S4 (strategy §3), the suite was run against a **throwaway reference stand-in** built in `/tmp` and never committed: the device fixture image (npm-installed CLI) plus a ~50-line Node supervisor modelled on spike S3's `cycle.sh` (secrets → `config --import` on stdin with a fresh `api.token`, `sync`, `e2ee decrypt --force`, `server start --quiet`, `/healthz` on `:8090`). It was used through `NOTESTEAD_HEADLESS_IMAGE`. Logs: `test-results/verify/m1-s5/standin-*.log`.
- **`headless.test.ts`: 5/5 passed** against the stand-in (ac14 50 s, ac15 51 s, ac15-neg 280 s, ac16 48 s, ac17 52 s on the Pi). Pi timeline (ac14 watcher): `config --import` 7.7 s, `sync` 7.2 s, `e2ee decrypt` 5.7 s, then `server start` → ready ~27 s after start.
- **Sensitivity** (a stand-in variant that also runs `config sync.9.password <pw>` in argv and trusts exit codes): `ac14` failed with `{"label":"joplin_password","where":"cmdline"}`; `ac15-neg` failed with `reported ready while the sync target refused every connection: {"status":200,…"state":"ready"…}`.
- **`image.test.ts` against the same npm-installed stand-in:** `ac23-arch`, `-sqlite3`, `-version`, `-lock`, `-static` passed (so the probe works); `ac23-lock-all` failed (`get-intrinsic@1.3.0`, `http-cache-semantics@4.3.0`, `ip-address@10.7.3`, `node-abi@3.97.0` are npm's picks, not `yarn.lock`'s) and `ac23-no-other-builds` failed (`keytar/build/Release/keytar.node`). That is why both exist: `npm install joplin@3.7.1` passes `ac23-lock` alone.
- **Lockfile reader** against this repo's own install: 938 packages, none outside `yarn.lock`.
- **Harness bugs fixed during validation:** a `/proc/<pid>/environ` read is briefly denied while a process `exec`s, so the watcher now counts a file as unreadable only if no sample of the process's lifetime could read it (every CLI child's `environ` was read); requests to the server use `Connection: close` (a kept-alive socket closed during the ~20 s device run failed `ac16` with `socket hang up`); the AC15-neg window is anchored on the end of the first `sync` attempt, because with a refused target that attempt lasts ~3.5 min and a fixed 120 s window would have missed a naive supervisor.

## Interpretations (for the architect / orchestrator)
1. **AC14/AC15 run as contract tests** although tagged *(integration)*: "the secrets mounted at `/run/secrets/…`" and "any process in the container" describe the container. An integration test on a temp profile could not see the image's process tree.
2. **AC15 "until the initial sync and decrypt finish"** means *finish successfully*. A failed sync (which `joplin sync` reports with exit 0) is not finished; AC15-neg tests that. The backlog's wrong-master-password NEG (`degraded: e2ee-password`, no crash-loop) is **M3-AC5** and stays there.
3. **AC15 `lastSync`** is a scalar ISO-8601 timestamp here; M3-AC9's `/status.lastSync` object is a different endpoint.
4. **AC14 adds two ADR-derived checks:** the import's stdin is a pipe/socket (not a file holding the secret), and `podman logs` holds no secret (ADR-0008 "never logged"; M3-AC7 extends this to image layers and the profile).
5. **AC15 adds ADR-0003's command list** (public commands only, `/data/profile`, `--quiet`, `--force`, no `--upgrade`). A needed extra flag is a Dispute, not a silent change.
6. **AC17 adds** "`:8090` doesn't relay the Data API" and "no published port": the same property seen from the two other ways out of the namespace.
7. **AC23 "no npm resolution can slip in"** is checked over every installed package (`ac23-lock-all`), not only `joplin`/`@joplin/*`: `npm install joplin@3.7.1` would install the same `@joplin/*` versions and pass `ac23-lock` alone. "Install scripts run only for allow-listed packages" is checked twice: behaviourally by the NEG fixture and on the real tree by `ac23-no-other-builds` (keytar's `install` script downloads a `keytar.node` when it runs).
8. **"The allow-list sits in one reviewed place"** is not machine-checkable in general; the lead reviews it. QA checks the observable effect only.

- **Egress confinement** (`https://example.com` unreachable from `headless`): M3-AC10. The test stack already uses the `--internal` network.
- **Compose file, compose healthchecks, real-server guard, log attachment self-test:** M1-S6.
- **x64:** the contract layer isn't in CI yet (M1-S8). The suite is CI-ready (podman; multi-arch base images; the device fixture and image builds are native). Until then x64 is **PENDING-CI**.
