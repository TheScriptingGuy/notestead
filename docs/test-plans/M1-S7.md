## How to run
The walking skeleton needs the **real upstream web bundle** in the `web` image. Fixture F3 (the default of the contract and E2E image builds) has no app, and the spec refuses it with a message naming `NOTESTEAD_WEB_ARTIFACT`.

```sh
# The CI-built bundle (see §Web bundle); any verified web-bundle artifact dir works.
export NOTESTEAD_WEB_ARTIFACT=~/joplin-web-app-work/ci-evidence/37285783648/extracted/web-bundle-v3.7.21

# E2E: the walking skeleton, its NEG and the C1-R1 guard (Pi: ~4 min stack start when the images exist, ~6 min per
# walking-skeleton test; cold image builds add ~7 min). One worker (playwright.config.ts).
corepack yarn playwright test
corepack yarn playwright test tests/e2e/m1-s7          # M1-AC21 and NEG only
corepack yarn playwright test tests/e2e/harness        # C1-R1 guard on a real DOM

# Reuse a running developer stack instead of starting one (M1-AC19 reuse mode):
node tests/stack/cli.ts up                             # with NOTESTEAD_WEB_ARTIFACT set; prints JOPLIN_SERVER_URL
JOPLIN_SERVER_URL=http://127.0.0.1:<port> corepack yarn playwright test

# C1-R1 leak scan on the real login/unlock flow (contract; two inner Playwright runs, ~10 min warm)
corepack yarn test:contract --verbose tests/contract/m1-s7

# Unit tests of the harness helpers (part of `corepack yarn test`)
corepack yarn jest tests/unit/harness
```
- `NOTESTEAD_WEB_IMAGE`, `NOTESTEAD_HEADLESS_IMAGE`, `NOTESTEAD_DEVICE_IMAGE` reuse prebuilt images; `NOTESTEAD_KEEP_IMAGE=1` keeps the ones a run builds.
- **Logs and reports** (all redacted):

### NEG window
The NEG's absence check runs for **60 s**, anchored to the first sync error the web app shows (`holdsFor` in `tests/support/poll.ts`, the only kind of fixed duration the strategy allows, §3). On the Pi the positive path shows the decryption banner about 10 s after "Back" (its first sync takes ~2 s) and the title ~16 s after the master password; the app started a second sync by itself ~10 s after its first one in exploration. 60 s covers such re-syncs and is more than 4× either step. The sensitivity run (§Harness validation) proves the window catches a working proxy.

### Pixels (C1-R1 (3))
No artifact of a run holds pixels any more:
- `screenshot: 'off'` and `video: 'off'` (unchanged);
- traces are recorded by the `webApp` fixture with `screenshots: false`, so the trace has **no screencast frames** (before this story: 16 JPEG frames in the C1 trace, ~525 in a real-app trace);
- DOM snapshots and network bodies are text: the redacting reporter redacts them (registered secrets plus the derived credentials of Finding F3).
The password-field rule stays as defense in depth (a future screenshot, a manual `page.screenshot`, the HTML report's trace viewer rendering a snapshot): a secret is only ever typed into `<input type="password">`, which every renderer masks. Upstream's sync password field and master password fields are `secureTextEntry` inputs, which react-native-web renders as `type="password"` (checked before and after typing).

## Findings
- **F1 (upstream, minor UX; report upstream, no patch).** In the web app's Synchronisation settings, the "Joplin Server URL" field re-renders after its first change (the "Attention: If you change this location…" notice appears), and the field loses focus: the keys typed after that are lost. Measured per keystroke: after the first character, focus is gone every time. A user clicks the field again and types on; `typeLikeUser` does the same for non-secret text. The password fields are not affected. Proposed upstream issue: "Web app: Joplin Server URL field loses focus after the first keystroke" (app-mobile `ConfigScreen`, v3.7.21).
- **F2 (harness/tooling).** Playwright 1.59.1's trace merge (`mergeTraceFiles`, yauzl from `playwright-core/lib/zipBundle`) never finishes on **Node 24.17** once a trace entry is larger than one 64 KiB read (the real app's `trace.trace` with DOM snapshots, its bundle in `resources/`). The read stream ends without data, the merge stalls, the failing test hangs until its 10-min timeout and leaves a truncated `trace.zip`, which the redacting reporter then deletes as unredactable. Reproduced outside the runner with the same two zips: hangs on Node 24.17.0, completes on Node 22.23.3 (`node:22` container). CI uses Node 22, so this is Pi-only, but it made every failing real-app test on the Pi slow and traceless. **Fix (harness):** `use.trace: 'off'`; the `webApp` fixture records its own context trace (`tracing.start({ screenshots: false, snapshots: true, sources: true })`) and, on failure, writes it with `tracing.stop({ path })` (yazl only, no read-back) and attaches it as `trace`. The test-level step list is no longer in the trace (it stays in the reports). The M1-S6/M1-S6a self-tests (`ac20-*`, `c1-*`) read the same entries (`.trace`, `.network`) and are re-run as regression. Upstream report candidate: Playwright, "trace merge stalls on Node 24 (yauzl fd-slicer read stream)".
- **F3 (harness, C1-R1).** The leak scan of the real flow finds the **Joplin Server session id** in the trace's `resources/*.json` (the `POST /api/sessions` response body `{"id": …}`). The `X-API-AUTH` headers are redacted, but no registry knows the value, so the body keeps it. A session id is a live credential for the account until it expires. **Fix (harness, after RED):** the redacting reporter learns the values of credential headers (`X-API-AUTH`, `Authorization`, `Cookie`, the Cloudflare Access headers) from each trace's network log, before redacting anything, and redacts them in every trace entry, attachment and output file. Gated by the C1 secret feed, so `c1r1-neg` still sees them.
- **F4 (upstream behaviour, expected).** Before the master password is entered, the web app's first sync reports `Last error: … Could not encrypt item …: Master key is not loaded`: it tries to upload its own welcome notes and cannot encrypt them yet. They upload after the unlock (gate 1 Q10: the welcome notes are accepted once). The walking skeleton therefore does not assert an error-free first sync report; the NEG asserts the specific `Invalid origin` error.
- **F5 (data-level).** The aria snapshot Playwright writes into `error-context.md`, and the trace's DOM snapshots (`__playwright_value_`), carry password field **values** in clear text (the screen shows dots). Both are text and are redacted (registered secrets); `c1r1-neg` proves the channel is real and `c1r1-redacted-error-context` that it is clean.

## Interpretations (for the architect / orchestrator)
1. **"as `user1`"** (step 3) is read as "as a test user". The test uses a fresh per-test user from `e2eeAccount` (ADR-0007: a fresh user per test; E2EE turned on by another device, as on the user's real account). `user1@example.com` from `createTestUsers` has no E2EE, and sharing it would couple tests.
2. **"Run one headless sync"** (step 2) is one restart of the per-test headless service (`syncHeadlessOnce`). The M1 supervisor syncs only in its start cycle (`packages/headless/README.md`: `config --import`, `sync`, `e2ee decrypt --force`, `server start`; the loop and triggers are M3). A restart is exactly one cycle with one `sync`, through the shipped image and its documented behaviour; done means `healthy` again with a newer `lastSync`. M3 (`requestSync('manual')`, `sync_now`) can replace the helper's body without changing the test. The Data API token rotates on the restart and is re-registered at once (review M1-S6a-r1 C1-R6).
3. **"The proxy's Host rewrite disabled"** (NEG) is a second `web` container of the image under test whose `JOPLIN_SERVER_HOST` is the browser's own Host (`127.0.0.1:<its published port>`). Without `header_up Host`, Caddy passes the incoming Host through, so the server receives exactly this value; M1-S4 `ac10-c1-neg` proved that the override wins over the default. This uses the shipped image and a documented variable: **no product switch is added**, and production safety is unchanged. The stack's own `web` (and with it the headless and device paths) stays correct, so steps 1–2 run as in the positive test.
4. **"Reports a sync error"** is the side menu's sync report (`Synchronizer.reportToLines`: `Last error: …`), which the app shows after its own automatic sync. The tests do not press "Synchronise": the app starts a sync by itself a few seconds after the target is saved, and pressing the button while it runs would cancel it (the same button reads "Cancel").
5. **The decryption banner** ("Press to set the decryption password.") is the app's own signal that the sync worked and the master key arrived. Step 3 waits for it (positive), the NEG asserts its absence.
6. **Steps run as `test.step`s of one test** (`1.` … `6.`), so the report shows per-step durations and the failing step.
