## How to run
The M2-S1 specs need the **real upstream web bundle** in the `web` image, like M1-S7. `NOTESTEAD_WEB_ARTIFACT` takes the **artifact directory** (`tests/acceptance/support/webImage.mts` runs `web-build import <dir>`), not the zip.

```sh
export NOTESTEAD_WEB_ARTIFACT=~/joplin-web-app-work/ci-evidence/37285783648/extracted/web-bundle-v3.7.21

# E2E: M2-S1 only (Pi: ~4 min stack start when the images exist; ~15 min for the four tests). One worker locally.
corepack yarn playwright test tests/e2e/m2-s1
# E2E: everything (M1-S7 regression included, since the page objects and flows change)
corepack yarn playwright test

# Harness layers (seconds to a minute each; one at a time)
corepack yarn jest tests/unit/harness tests/integration/harness
node --test --test-concurrency=1 --test-reporter=spec tests/acceptance/m2-s1/serial-rule.test.mts

# Contract regression for C1-R4 and M1-S8 C2 (the leak scans; ~30 min warm on the Pi)
corepack yarn test:contract --verbose tests/contract/m1-s6 tests/contract/m1-s7
```
- `NOTESTEAD_KEEP_IMAGE=1` keeps the images a run builds. Later runs reuse them with `NOTESTEAD_WEB_IMAGE=localhost/notestead-web:stack-test NOTESTEAD_HEADLESS_IMAGE=localhost/notestead-headless:stack-test NOTESTEAD_DEVICE_IMAGE=localhost/notestead-test-device:3.7.1`.
- **Traces:** never pass `--trace on` and never set `use.trace`. The `webApp` fixture records its own trace (the Node 24 trace-merge workaround, M1-S7 F2, standing).
- **Logs and reports** (all redacted): as M1-S7, plus `network.log` (the `webNetwork` recorder, query strings removed) per failing E2E test. QA's logs go under `test-results/verify/m2-s1/` (gitignored); each ends with `# duration … s; exit <code>`.

### Disruptive tests (ADR-0007 A3)
No M2-S1 test stops, restarts or reconfigures a shared service:
- `M2-AC1` and its NEG configure only the browser profile. They use a per-test account and read the server through its API.
- `M2-AC2` restarts its **own** headless service (`syncHeadlessOnce(stack, headlessService)`, a per-test compose project), never `stack.defaultHeadless`.
- The NEG has no headless service at all.

They run in the parallel `chromium` project. The `chromium-serial` project exists from this story on for the first disruptive spec (expected in M2-S5, bundle upgrade). The guard `M2-S1-SER-04` fails if a disruptive spec is not named `*.serial.spec.ts`.

### NEG window
`M2-AC2 NEG` watches for **60 s** after upstream's stage-2 error. Window is the M1-S7 value, reused for the same reasons: on the Pi the positive path shows `Decrypted items: t / t` and the titles within about 20 s of the password (M1-S7: ~16 s), and the app re-syncs by itself about every 10 s at first. A decryption that started late would show inside the window. The sensitivity run proves that the window catches a correct password.

## Findings (planning, 2026-10-20, from the upstream source at the pin)
- **F1 (harness, M1-S7 flow; fixed here).** `unlockE2ee`'s acceptance check, `(Master password)` in the master key row, does not tell a right password from a wrong one. In `encryption-config.tsx` `renderPasswordInput`, that text shows when `masterPasswordKeys[id] || !passwordChecks.master`. After a **wrong** password saved in the key's field, `onSavePasswordClick` also sets `encryption.masterPassword` to it. `passwordChecks.master` becomes `false`, so the row shows `(Master password)` too. M1-AC21 was still sound, because its step 5 (the decrypted title) is the real proof. A shared flow must not report "accepted" falsely, though. The fix is `masterPasswordState()`: `accepted` only when the row shows `(Master password)`, `Master password:` reads `Loaded`, and upstream's invalid-password text is absent. It is `rejected` when that text shows.
- **F2 (harness, M1-S7 page object; fixed here).** `syncReport()` finds the report with `getByText(/^Completed: /)`. The report is one text element whose lines are joined with `\n` (`side-menu-content.tsx:650-670`), and `Completed:` comes after any `Created …`/`Updated …` lines. So a sync that changed items has a report that does not *start* with `Completed:`, and `syncReport()` returns `''`. M1-AC21's NEG passed only because its failing sync created nothing. The fix is to match `/\bCompleted: /` (Playwright normalises the newlines to spaces).
- **F3 (harness, M1-AC21; follow-up, not fixed here).** M1-AC21 step 3 counts `POST /joplin-server/api/sessions` → 200 in the shared `web` container's access log for the browser's Host, since the test started. In CI, workers run in parallel and every test's browser uses the same Host. So another test's login can satisfy the check. The M2-S1 specs therefore use the per-context network log for per-test evidence and the server API for the data. Proposed fix (QA, next touch of M1-S7): check the per-context network log there too.
- **F4 (upstream behaviour, documented in M1-S7 F4).** On an E2EE account, the web app's first sync reports `Last error: … Master key is not loaded`, because it cannot encrypt its own welcome notes yet. This is why M2-AC1 uses a plain account (Interpretation 1).

## Interpretations (for the orchestrator)
1. **"The test user"** in M2-AC1 is a fresh **plain** account (`plainAccount`: no E2EE, no data), not an `e2eeAccount`. With E2EE, the app's first sync ends with `Last error` until the master password is entered (F4). "A full sync completes" could then only be read loosely, or by doing M2-AC2's unlock inside M2-AC1. With a plain account, the sync report has to be error-free. The web app is then the account's only client, so `info.json` with `version` 3 on the server proves the web app's sync went through the proxy and wrote the pinned sync version. The "still 3" case on an account that already holds another client's data is asserted in M2-AC2 (before and after), so both readings of "still" are covered.
2. **"Only same-origin requests to `/joplin-server/api/*`"** means:
   - Every request to the sync target (any same-origin path under `/joplin-server/`) is under `/joplin-server/api/`.
   - No request goes to the server's own published port.
   - Every other same-origin request (bundle, service worker, manifest) is allowed.
   - Cross-origin requests fail the test, except exactly `HEAD https://joplinapp.org/connection_check/` with no query string.
   - `data:`, `blob:` and `about:` URLs are local and ignored.
   - `ws:`/`wss:` fails (the app uses none).
3. **The recorder only observes.** It does not route or abort requests. Routing would change upstream's behaviour: Playwright routes skip requests that a service worker handles, and the `connection_check` request already fails harmlessly under cross-origin isolation (S4). The control request uses `.invalid` (RFC 6761), so nothing leaves the machine.
4. **"Shows upstream's error"** (M2-AC2 NEG) is upstream's own text for an invalid master password on the encryption screen (stage 1), plus upstream's alert from its master-password field (stage 2). The banner staying up is asserted as state, not as the error.
5. **"Every seeded note"** is three notes in one folder (`e2eeSeed: { notes: 3 }`) rather than the default single note, so "every" is a real plural. To-dos, tags and attachments are seeded in M2-S2/S3 (STATUS), not here.

## Requirements on the implementation
**None expected.** M1-AC21 already syncs this bundle through this proxy. "Check synchronisation configuration" uses the same `/joplin-server/api/sessions` and items endpoints. The `connection_check` request is upstream's and is allowed by the AC. The M2-S1 E2E tests are therefore expected to **pass on the existing product**. Their RED evidence is the harness RED and the sensitivity runs (§Work orders WO-12).

If a run shows a product defect, the senior engineer may touch `deploy/web/**` and `docs/worklog/M2-S1.md` only. Examples: the configuration check fails through the proxy, a same-origin request under `/joplin-server/` outside `/api/` is needed by the app, or the proxy answers a sync request wrongly. `tests/**`, `playwright.config.ts` and the test configs stay QA's.

An **upstream** behaviour that breaks the policy goes to the orchestrator, for Known limitations or an architect decision. Example: a new cross-origin request in the bundle. It is not routed to the engineer, and the test is never weakened.
