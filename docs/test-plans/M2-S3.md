## Planner decisions
- **D1. Account: `e2eeAccount`, unlocked first, as in M2-S2 D1.**
  - `headlessService` needs an E2EE account: the supervisor's `e2ee decrypt --force` exits 1 on a plain one (ADR-0003 A1).
  - E2EE is the user's real configuration. It also makes M2-AC7 prove the realistic path: the web app encrypts the attachment before upload (FileV1, about 1.34×; S6), and headless downloads and decrypts it.
  - **No reason found to deviate.** Encrypting 100 MiB in the browser is part of what M2-AC7 must show works, and its time is measured (D7).
  - Every test runs `openUnlockedWebApp` first (L18).
  - M2-AC8 seeds two notes (`e2eeSeed: { notes: 2 }`): note 2 goes to the trash and back, and note 1 is the untouched control.
- **D2. Sync cycles reuse M2-S2 D2/D3 and the CI-M2-S2 re-press unchanged.**
  - **`syncWebOnce`:** idle first, then a press of `Synchronise`. It presses again (up to 3 presses in all) only when the button is idle again, no `delta` (200) was seen since the last press, and 3 s have passed. Done is a `delta` after the **last** press, then idle, with `Completed:` and no `Last error:`. A re-press leaves a `sync-repress` annotation.
  - **`syncHeadlessOnce`:** restarts the test's own service.
  - **M2-AC7a:** passes measured bounds through `syncWebThenHeadless(…, { webTimeoutMs, headlessTimeoutMs })`, because its waits exceed 60 s (D7).
  - **"After both sides sync"** (M2-AC6, M2-AC7b) runs in the reverse order, since the data starts in headless:
    1. the headless sync (the upload);
    2. `syncWebOnce` in the already-open web app (the download).

    Each half has a data-level check: the server's copy after step 1, and the web app's `GET …/root:/<name>:/content` through the proxy in the context's network log.
- **D3. Search (M2-AC6) through upstream's Search screen.**
  - **The note:** `Notestead search target <run>`, created through the headless Data API (`POST /notes`) in the seeded notebook.
    - Its body is `This body holds the unique word <W> for M2-AC6.`, where `W = nstword<10 hex>` is new per run and occurs **only in the body**.
    - So a hit is a full-text body match, and the result's title is never split by upstream's highlight (`NoteItem.tsx`, `displayedNoteTitle`).
  - **The query is retyped like a user until the result shows.** Upstream runs a query only when the text changes (`SearchResults.tsx`, `useQueuedAsyncEffect`), and it indexes a changed note about 10 s later (`SearchEngine.scheduleSyncTables`, called on `NOTE_UPDATE_ONE`, `root.tsx:163-166`). A synced note is then decrypted, so the first query can come before the index has it.
    - `SearchScreen.searchUntilFound` clears and retypes with real keys until the result shows.
    - **Each attempt waits up to 5 s.** A query over a few notes takes well under 1 s on the Pi, and upstream shows its progress bar only after 1 s.
    - **The total is 3 min**, an explicit timeout (it is longer than 60 s).
    - **The attempts are recorded** in a `search` annotation. Retyping is what a user does, and no assertion is relaxed.
  - **NEG, with the positive control in the same session:**
    1. After `W` has found the note, the test types one more character, `x`, so the field holds `Wx`, a word in no note.
    2. Every prefix of `Wx` up to `W` still matches the note. So the found result disappears **only when the query for `Wx` has run**, which proves the NEG query ran.
    3. Then none of the account's notes is listed. Each title comes from REST (`/notes?include_conflicts=1&include_deleted=1`, the welcome notes included), and is checked with the same scoped locator that found the positive.
    4. Results never refresh without a change of text, so this is an immediate check, not a window.
  - **Data level:**
    - REST has the note.
    - The server's `<id>.md` is encrypted, without `W` or the title in clear.
    - The web app downloaded `<id>.md` through `/joplin-server/api/`.
    - The opened result shows `W` in the note viewer: it is the right note, decrypted.
- **D4. Attachments uploaded in the web UI (M2-AC7a).**
  - **The upload control:**
    1. The note screen's `Actions` → `Attach...` (`Note.tsx:1347`) opens upstream's menu `Choose an option` (DialogManager `showMenu`, test id `prompt-dialog`).
    2. `Attach file` runs `pickDocument`. On web it creates a hidden `<input type="file" multiple>`, appends it and calls `click()` (`utils/pickDocument.ts`, web branch).
    3. Playwright intercepts that as a `filechooser`, because the click carries the user activation of the real menu click.
    4. `setFiles(path)` gives the file by path. Playwright 1.59.1 passes **local paths** to a local browser (`playwright-core/lib/client/elementHandle.js`, `convertInputFiles`), so the 50 MB buffer limit does not apply and the browser reads the file itself.
    5. The chooser must report `isMultiple() === true`, which is upstream's input.
  - **Files are generated at test time from a per-test seed** (`tests/e2e/support/testFiles.ts`, fixture `testFiles`). They are never committed, and they are hashed while they are written.
    - **The 5 MiB image:** a PNG of pseudo-random RGB pixels, 1280 × 1364, in stored (uncompressed) deflate blocks, padded to exactly 5 242 880 bytes by a private ancillary `nsTt` chunk.
      - Both sides are at most 1920 px. So upstream's `imageResizing: alwaysAsk` prompt never appears (`Note.tsx:882-925`, `Resource.IMAGE_MAX_DIMENSION`), and the bytes are stored unchanged.
      - A larger image would be offered a resize, and "Yes" re-encodes it, which would correctly fail the sha256 check.
    - **The 100 MiB binary:** 104 857 600 bytes of a ChaCha20 keystream.
    - **Storage:**
      - The files live in `os.tmpdir()`, outside `test-results/`, so nothing large is attached or uploaded. They are removed at fixture teardown.
      - A failing test attaches only `test-files.json` (names, seeds, sizes, sha256).
    - **Measured on this Pi** (Node 24.17): the 100 MiB keystream with its sha256 in 1.0 s, and the 5 MiB PNG in 0.15 s.
    - **Memory on the Pi:**
      - `/tmp` is a tmpfs (3.9 GB, 3.4 GB free), so the files cost about 105 MiB of RAM, which is acceptable with 6.1 GB available.
      - Chromium keeps a Playwright context's OPFS in memory (off-the-record), so the resource (100 MiB) and its encrypted copy (about 134 MiB) sit in the browser's RAM.
  - **Flow:**
    1. A new note in the seeded notebook, with the title typed like a user.
    2. Attach the image, then the binary. Each attach is done when the Markdown editor holds upstream's link: `![<name>](:/<id>)` for the image, `[<name>](:/<id>)` for the binary (`Resource.markupTag`, inserted by `editorRef.insertText`). The **resource id is read from the editor**.
    3. One cycle, with bounds from measurement (D7).
  - **Data level:**
    - **REST:**
      - The note has exactly these two resources. Their ids equal the editor's, and title, size and `file_extension` match; the image also has `mime: image/png`.
      - The body links both.
      - `GET /resources/:id/file`, streamed into a sha256 **inside** the headless container, gives status 200, the generator's sha256 and its size.
      - The binary's `mime` is recorded, not asserted (F7).
    - **Server:**
      - `<id>.md` (the resource metadata) has `encryption_applied: 1`.
      - The blob `.resource/<id>`, streamed into a sha256, starts with upstream's encrypted-data header `JED01` (`EncryptionService.encodeHeader_`), differs from the plaintext and is larger.
      - The blob-to-plaintext ratio is recorded in an `e2ee-overhead` annotation. That is the first measurement of S6's "≈ 1.34×", which L16's 74 MB figure rests on.
    - **"Through the proxy":**
      - For each resource the network log has a `PUT /joplin-server/api/items/root:/.resource/<id>:/content` with status 200, and none with a status of 400 or more.
      - No request goes to the server's own port, and the network policy holds.
      - The headless read-back then crossed `web`'s internal listener, the only egress of `headless` (ADR-0006).
  - **In-test NEG:** before the cycle, REST has no resource with either name and no note with the title. After it, it has exactly one note and exactly the two resources.
- **D5. Attachment added through the headless API, viewed in the web UI (M2-AC7b).**
  - **"Viewable", proven by the bytes:**
    - The note viewer's `img[data-resource-id="<id>"]` is `complete`, its natural size is 96 × 64, and its source is a `blob:` URL.
    - The bytes it shows, fetched **inside the sandboxed viewer frame** from its own `blob:` URL, hash to the file's sha256 with the same length.
    - **How the bytes get there:** on web, upstream hands each resource to the viewer frame as a `File`, which the frame shows through its own `blob:` URL (`useWebViewSetup.ts:176-195`, `Renderer.setResourceFile`). The page's CSP allows `connect-src blob:` (`web/public/index.html`).
    - **Why "loaded" is unambiguous:** a resource that is not available yet renders upstream's placeholder `.not-loaded-resource[data-resource-id]` instead (`renderer/utils.ts`).
  - **Why viewable rather than downloadable:** the AC says "or", and viewable with the bytes proves arrival, decryption and rendering. Downloading would add a popup (upstream's `showResource` opens a `blob:` URL in a new tab) and a download event, and prove nothing more about the bytes.
  - **Creation through the headless Data API** uses a new in-container probe (`tests/fixtures/m2-s3/in-container/data-api-resource.mjs`):
    1. `POST /resources` (multipart `props` + `data`) with a 96 × 64 PNG of 18 564 bytes;
    2. `POST /notes` with the body `![<name>](:/<id>)` in the seeded notebook.
    - **Why the body is safe:** it has no `file:`, `http(s):` or `data:` URL. CLI 3.7.1's `downloadMediaFile` fetches only `http:`, `https:` and `data:` URLs (`routes/notes.js:231-244`), and a `:/<id>` link has no protocol (CLAUDE.md security rules).
    - **The size limit:** the file is at most 64 KiB, because it travels base64 in `argv` (the probe itself comes on stdin, as every Data API probe does).
  - **Order:**
    1. The web app is open and unlocked.
    2. Headless creates the resource and the note.
    3. The headless sync runs.
    4. `syncWebOnce` runs.
    5. The test opens the note and polls the viewer, with an explicit 3-min timeout.
  - **Data level:**
    - **REST:** the resource's metadata, and its digest through the probe. This is the positive control of the read-back path.
    - **Server, before the headless sync:** no `.resource/<id>` (in-test NEG).
    - **Server, after it:** `<id>.md` is encrypted, and the blob starts with `JED01` and is not the plaintext.
    - **Network:** `GET …/root:/.resource/<id>:/content` with status 200, through the proxy.
- **D6. Trash and restore (M2-AC8).**
  - **UI:**
    1. Seeded note 2, made by the other device, is trashed from its note screen (`Actions` → `Delete`). It goes to the trash with no confirmation, and the screen stays (M2-S2 F4).
    2. It is listed in the side menu's `Trash` notebook, which upstream always lists (`folders-screen-utils.ts:45`, title `_('Trash')`).
    3. It is restored from its own note screen in the trash (`Actions` → `Restore`, `Note.tsx:1490-1500`). Upstream runs `restoreItems` and returns to the trash list.
    4. It is gone from the trash and back in its notebook.
  - **Data level:**
    - **After the delete cycle:**
      - The AC's literal `GET /notes?include_deleted=1` lists it once with `deleted_time > 0`, within 60 s of the press.
      - `GET /notes` without the flag does not list it.
      - Title, body, `parent_id` and `is_conflict` are unchanged.
    - **After the restore cycle:**
      - `id`, `title`, `body`, `parent_id`, `deleted_time` and `is_conflict` equal their values from before the test. So `deleted_time` is 0 and the note is in its original notebook.
      - It is listed once by `GET /notes`, so there is no conflict copy.
      - `include_deleted=1` shows `deleted_time: 0`.
    - **Note 1 (the control):** unchanged throughout, and never in the trash.
- **D7. Bounds, from measurement, inside the CI-M2-S2 limits, and CC-1(b).**
  - **Every M2-S3 spec** uses `test.describe.configure({ timeout: longSpecTimeoutMs })`, so `CI-T-03` and `CI-T-04` hold. No spec writes its own number.
  - **Every wait longer than 60 s passes its own `timeout`** (the CI-M2-S2 rule). In M2-S3 those are:
    - the search (3 min);
    - the viewer poll (3 min);
    - every phase of M2-AC7a (below).
  - **M2-AC6, M2-AC7b and M2-AC8** each have at most two cycles. Each is a subset of M2-AC3, which took 333 s on the Pi. The projection is 4–6 min, well inside 15 min.
  - **M2-AC7a is the only spec at risk.** Its projection is 5–11 min on the Pi (median about 7 min):
    - unlock about 150 s;
    - the attach copies of 100 MiB, 10–30 s;
    - encryption, about 1 070 FileV1 chunks with an animation frame each, plus the upload of 134 MiB: 1–3 min;
    - headless download and decryption: 1–2 min;
    - the digests: about 10 s.

    It is not measured yet.
  - **The phase bounds:**
    1. **WO-21 measures it once.** That run uses a temporary, uncommitted timeout edit of 40 min and a memory sampler.
    2. **Each phase's bound** becomes `max(3 × measured, floor)`. The floors are: attach 2 min, web sync 5 min, headless sync 10 min, digest 2 min, viewer 3 min.
    3. **The spec timeout** must be at least **2 ×** the Pi's measured duration. The Pi is the slowest box: on CI, x64 ran M2-AC3 in 135 s against the Pi's 333 s, and the green arm64 baseline was 1.4× slower than x64.
  - **CC-1(b) is requested** (`docs/test-plans/CI-M2-S2-x64-arm64.md` §Budget): `longSpecTimeoutMs` 25 min, `ciGlobalTimeoutMs` 55 min, and the `e2e.yml` E2E step 60 min, changed together before M2-S3's first CI run. There are two reasons, both from measured times:
    1. **15 min holds M2-AC7a only if the Pi takes 7.5 min or less.** The projection's median sits on that line, and 25 min holds up to 12.5 min.
    2. **The suite grows toward CC-1(a)'s line.** On one worker the Pi ran the 16-test suite in 2025 s (CI-M2-S2 final run), and M2-S3 adds an estimated 19–29 min of Pi time. That gives about 53–63 min in all.
       - **The x64 projection:** per-test x64 time is about 0.4× the Pi's (M2-AC3: 135 s against 333 s), on 2 workers, so about 11–13 min.
       - **The arm64 projection:** 1.4× x64, about 16–18 min, plus globalSetup. That is close to CC-1(a)'s 20-minute line, and it leaves no room for a retry of M2-AC7a inside 40 min.
  - **Order of the CC-1(b) change, so `CI-T-02` holds at every commit:**
    1. **The ci-cd-specialist's `e2e.yml` commit** (step 60 min) lands on this branch first; 40 ≤ 56 holds.
    2. **The QA executor's WO-22** sets the two constants; 55 ≤ 56 and 2 × 25 < 55 hold.

    If the ci-cd commit is not on the branch when the executor reaches WO-22, WO-22 is skipped and recorded, and **M2-S3 must not be pushed to CI until it is done**.
  - **Withdrawal:** at the planner's review CC-1(b) can be withdrawn, and 15/40/45 kept, only if WO-21 measures M2-AC7a at 7.5 min or less on the Pi **and** the CI-M2-S2 proof run's arm64 wall time plus the projected M2-S3 share stays under 20 min.
  - **The stop line:** if the Pi takes more than 12.5 min, more than 25 min can hold, so that is a **HARD STOP**. The planner then decides, for example to split the 100 MiB case into its own CI job, which would be ci-cd's work.
- **D8. Folded-in follow-ups.**
  - **C1 (`NoteScreen.waitSettled`).**
    - **Where upstream puts the focus:** on a new **note's body**, the Markdown editor, and on a new **to-do's title** (`Note.tsx:1528-1563`: `fieldToFocus = is_todo ? 'title' : 'body'`). The body's focus is a command queued to the editor's frame (`NoteEditor.tsx:140`), so it lands when that frame has loaded. That was F8's race.
    - **What `waitSettled(kind)` now does:**
      1. It waits for the editor frame.
      2. It waits for the **positive event**: the focus on upstream's target. For a note that is the `<iframe>` of the `.cm-content` frame, with the active element inside `.cm-content`; for a to-do, the title field.
      3. It keeps M2-S2's 10-poll stability count as the fallback guard.
    - **The tracker** `settleTracker(target, polls)` is pure and unit-tested, with its RED first.
    - **The measured lag:** a `settle` annotation per new note or to-do gives the editor load, the moment the focus landed, and the moment it settled, in ms. §Results gives the minimum, median and maximum over the story's runs. M2-S2's run-1 trace was not kept, so this is the measurement.
    - **Strategy §3** gets the evidence rule.
  - **C2 (the repeated hour).**
    - **The helper:** `wallClockIsUnique(epochMs, timeZone)`, pure, with its RED first. It is false when the wall clock also names an instant 30 or 60 min away.

    - **Why the hour can't be avoided:** a run in that hour cannot pass, because `datetime-local` cannot name the second occurrence. The due time cannot move either, since the NEG window is anchored to it. So this is documented and fails loudly.
    - **The run calendar:** the work orders keep every M2-AC5 run out of the window 2026-10-24 22:30 UTC to 2026-10-25 02:00 UTC.

### Disruptive tests (ADR-0007 A3)
No M2-S3 test stops, restarts or reconfigures a shared service. Every headless sync restarts the test's **own** `headlessService`, and the harness specs only read or use their own service. All specs run in the parallel `chromium` project, and `M2-S1-SER-04` must still pass.

### Windows and bounded waits
- **No new absence window.** The search NEG is anchored to an event, and M2-AC7b polls for a positive state.
- **Bounded condition waits**, each with an explicit timeout because it can exceed 60 s:
  - the search, with a 5 s attempt inside a 3-min total (D3);
  - the viewer poll, 3 min;
  - the M2-AC7a phases (measured, D7).

  Each returns as soon as its condition holds.
- **Everything else** takes the CI-M2-S2 defaults: actions 60 s, navigations 120 s, `expect` 5 s.
- **The C1 stabilisation** (10 × 100 ms) now starts from the positive event (D8).

## Findings (planning, 2026-10-21/22, from the upstream source at the pin, CLI 3.7.1, `joplin/server` 3.7.2 and the CI-M2-S2 branch)
- **F1 (upstream behaviour; a new limitation for the architect, not in M2-AC7).**
  - **The limit:** `Synchronizer.maxResourceSize()` is `100 * 1000 * 1000` bytes for `AppType.Mobile`, and the web build sets `AppType.Mobile`.
  - **What it does:** when **downloading**, the web app marks any attachment of 100 MB (decimal) or more "cannot sync" ("Beyond this limit, the mobile app would crash").
  - **What it means for M2-AC7a:**
    - Uploading from the web app is allowed below 200 MiB (`Note.tsx:1018`), so M2-AC7a's 104 857 600-byte binary uploads.
    - Headless (`AppType.Cli`, no limit) reads it back.
    - But it would **never download into another web profile**, or into the phone apps.
  - **Proposed L19** for `ARCHITECTURE.md` §9: "the web app, like the phone apps, does not download attachments of 100 MB or more; they show as 'cannot sync'". A documenting test can follow if the architect adds it to an AC.
- **F2 (upstream behaviour; D3).** Search results are not live, and the index follows a note change by about 10 s, so a test, like a user, retypes.
- **F3 (upstream behaviour; D4).** The 5 MiB image keeps its bytes only because it is at most 1920 px; a larger one triggers the resize prompt.
- **F4 (upstream behaviour; D5).** The note viewer is a sandboxed `srcdoc` iframe. On web, attachments reach it as Files and show through the frame's own `blob:` URLs, which the page's CSP lets the frame fetch.
- **F5 (upstream behaviour; C1).** A new note's focus goes to the editor, by a command queued to its frame. A new to-do's goes to the title.
- **F6 (no product limit in the test path; the SE assessment rests on it).**
  - **The proxy:**
    - `deploy/web/Caddyfile` sets no `request_body` limit.
    - Caddy streams request bodies by default, and `flush_interval -1` streams responses.
    - M1-S4 `ac10-c5` round-tripped 100 MiB under `--memory 128m` in 9.7–10.8 s.
  - **Joplin Server 3.7.2** accepts the encrypted upload of about 134 MiB:
    - formidable 2.1.2's default file cap is 200 MiB;
    - `itemSizeHardLimit` is 250 000 000 B (`packages/server/src/config.ts:241` at `server-v3.7.2`);
    - a default account has `max_item_size` 0.
  - **Minor item for the architect:** ADR-0002 rule 5 calls 200 MB "the server's hard limit". In 3.7.2 it is 250 MB; 200 MiB is formidable's per-upload cap, and also Joplin Cloud's per-account `max_item_size`. The ≈ 149 MB conclusion stands.
  - **Cloudflare (L16)** is not in the test path. A Free/Pro tunnel user could not upload the 100 MiB case; L16 already documents that.
- **F7 (browser and platform behaviour).** A `.bin` file's MIME comes from Chromium's mapping and the platform's shared MIME data, or from upstream's fallback `application/octet-stream`. M2-AC7a therefore records it and does not assert it. FILES-01 records what each runner's browser reports. This is not the locale, which CI-M2-S2 pinned.
- **F8 (harness).** `requestHashed` in `tests/contract/support/http.ts` already streams a response into a sha256. `requestDigest` adds the first bytes as a **new** function, so the contract suite's `ac10-c5` is untouched.
- **F9 (harness).** The `dataApi` probe returns a body as text (`res.text()`), which corrupts binary data. That was fine for M2-S2's text seed. The new probe hashes inside the container and returns only `{ status, sha256, size, contentType }`.
- **F10 (harness; F-H1, from CI-M2-S2).**
  - **Both layers use the same tag.** `tests/contract/support/headless.ts` `deviceImage()` always builds `localhost/notestead-test-device:<cli>`, ignoring `NOTESTEAD_DEVICE_IMAGE`. `tests/stack/images.ts` builds and keeps that same tag for E2E.
  - **The contract build moves the tag:** the image is labelled `contract`, so it is a different image, and the kept `stack` image becomes `<none>`.
  - **The teardown then removes the contract image** (`globalTeardown.ts`, `lazyImages`), and its prune (`label=…=contract`) does not reclaim the stack-labelled orphan.
  - **The other images don't collide:** the web image tags (`m1-s4-test` against `stack-test`) and the headless tags (`m1-s5-test` against `stack-test`) differ.

## Interpretations (for the orchestrator)
1. **"Found by the web UI search after both sides sync"** is D3: headless writes, the headless sync uploads, the web sync downloads, and upstream's Search screen finds the body word.
2. **"Returns no results"** is D3's NEG: the found result disappears when the NEG query has run, and none of the account's note titles is listed.
3. **"Uploaded through the proxy"** means:
   - the web app's own blob PUTs go to `/joplin-server/api/…` with status 200;
   - nothing goes to the server's port;
   - the sha256 is read back through headless, whose only sync path is `web`'s internal listener.
4. **"Viewable or downloadable"** is viewable, with a byte-level proof in the viewer (D5).
5. **"Appears in the web trash"** means listed in the side menu's `Trash` notebook. "Restoring it in the web UI" is the trashed note's `Restore`.
6. **C4.**
   - **The two readings:** the review proposed "scan results are value-free; a data diff of per-run synthetic values may print". The brief says "make … REST-diff failure output value-free".
   - **What this plan does:**
     - It makes the **seeded-value** checks of M2-AC2 value-free, including `readReference` and step 9.

## Planner decisions on the SE's WEB-SQLITE-1 investigation (2026-10-25; worklog `b0ea6a3`, `docs/worklog/WEB-SQLITE-1.md`)
**Where the SE's findings leave us:**
- **Shape A has a proven mechanism** (worklog §2, §4):
  - `@joplin/lib`'s `Database` holds its batch mutex only for batches of 2 or more queries. Single statements bypass it, on the web app's one connection;
  - so a user's `UPDATE notes` can run inside a settings batch's open transaction, and that batch's failure followed by `ROLLBACK` undoes it;
  - `tryCall`'s retry never applies on web, because the errors have no `code`.
- **What starts it is not root-caused** (§3): the `rc=-1`/`IOERR` comes from sqlite-wasm's `opfs` VFS.
  - It reproduces at about 1.3% of startups with 2 to 3 **parallel** browsers.
  - It does not reproduce with 1 browser, even under CPU load (170 runs).
- **We own nothing that mitigates it** (§5: `vfs=opfs` is hard-coded).

### D-W1. The regression test: a characterisation of limitation L20, asserting today's documented behaviour, with an explicit flip
- **Layer:** an E2E harness spec on the real served bundle. It needs `webApp` and the stack's `web`; no headless service and no sync. The file is `tests/e2e/harness/web-sqlite-scope.spec.ts`, ordered as WO-29.
- **The recipe, made deterministic** (the SE's §4 lost the edit in only 2 of 3 rounds, which would be a flaky test). An init script wraps the page's `Worker.prototype.postMessage` for the SQLite worker:
  1. **Hold:** on the next settings batch's `DELETE FROM settings`, it rewrites the statement to an invalid one, as the SE did, but holds it, without forwarding it, until the test releases it (`window.__nstReleaseFault()`). It records `held` with the batch's `BEGIN`.
  2. **The edit:** the test waits for `held`, types a title change like a user, and waits until the script has seen the note's `UPDATE notes SET title` go to the worker. That is the interleaving, observed, not assumed.
  3. **Release:** the test releases the hold. The invalid `DELETE` fails, and `ROLLBACK` follows.
- **The assertions** (`WSQ-01`):
  - **(a)** the console holds `Could not save settings` and a `ROLLBACK` after the held `BEGIN`;
  - **(b)** the UI list shows the new title;
  - **(c) the edit is lost:** `expectStoredLocally` for the new title times out, so the edit is not in the app's own database. This uses a `expectNotStoredLocally` variant: it holds for 15 s, anchored to the release, and reads the file each second.
- **Controls:**
  - **`WSQ-02`, the same fault with the edit made after the release:** the edit is stored. The harness doesn't lose edits by itself, and the timing is what matters.
  - **`WSQ-03`, no fault:** the edit is stored.
- **WS-1's rule:** `WSQ-01` and `WSQ-02` call `webApp.allowSqliteFailures('WSQ: a failing settings statement is injected on purpose (L20 characterisation)')`, the documented opt-out, with an annotation. `WSQ-03` does not call it, so WS-1 stays in force there.
- **The flip:** when upstream fixes the transaction scope, `WSQ-01`(c) fails. Its message says: "L20 no longer reproduces at this pin: the edit survived a rolled-back settings batch. Upstream may have fixed issue A. Flip WSQ-01 to assert the edit is kept, and ask the architect to update L20." This is the pattern of M2-AC20/L14 ("documents L14, so that an upstream change is noticed"): green while the documented limitation holds, red the moment it changes, never skipped.
- **Why not a known-failing test:** the suite has no expected-failure mechanism, the no-skip rule rules out `test.fail`-style quarantine in spirit, and a permanently red test would mask other failures.

## Planner ruling on the WO-29 determinism HARD STOP (2026-11-12)
**The executor's diagnosis is accepted:** the race is in the spec. WSQ-01 releases the hold at the first `update-seen`, but upstream's 500 ms save queue sends the title `UPDATE` more than once. When the first send carries a partial title, the final full-title `UPDATE` lands after the `ROLLBACK` and is stored.

**The proposed `typedAt` fix is not enough. A stronger release condition is ordered.**
- **Why `typedAt` alone fails:** upstream's queue (`AsyncActionQueue`, `scheduleSave` → `makeSaveAction(state)`) builds each save action from the state when it is pushed. An action pushed before the last keystroke can still execute after `typeTitle` returns, carrying a **partial** title. And a full-title save can still be pending in the queue when the hold is released.
- **The release condition (all four):**
  1. **The full title is inside the transaction:** an `update-seen` after `held` whose bound title equals the **full** typed title. The init script keeps each `UPDATE notes SET title` statement's bound title in page memory. The test asks, with an in-page comparison, whether one equals the expected title; the answer is a boolean.
  2. **The queue has gone quiet:** no further `notes-title-update` for **1.5 s** (3 × the 500 ms queue interval) after that full-title one. This is a stabilisation anchored to an event, allowed by strategy §3.
  3. Then release.
  4. **A guard after the release:** if any `notes-title-update` is seen after the release, before the assertions, the run is **invalid**. The test fails with `WSQ-01 invalid run: the title was sent again after the release; this run does not test L20`, which is **not** the flip message. So a timing slip can never be misread as an upstream fix.
- **The assertions (a), (b) and (c) are unchanged, and so is the flip text.**
- **WSQ-02:** its edit is still made after the `ROLLBACK`. It keeps its 3 of 3, and needs only the same in-page full-title check for its own store assertion (unchanged in effect).
- **Bound titles never leave the page:** the comparison runs in the page. The title is a per-run synthetic value (allowed by C4); it is not printed in a pass, and is printed in a failure only as a field name.
