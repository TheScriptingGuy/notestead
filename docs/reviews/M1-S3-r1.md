## Summary
The pipeline is small and least-privilege, and it is built to be checked:
- Every action is pinned to the commit of its release tag. I verified all five against upstream.
- Each workflow sets `permissions: {}`. Each job grants `contents: read` or nothing, and no job uses a secret or `pull_request_target`.
- Fork PRs run read-only on hosted runners.
- `web-bundle.yml` uploads exactly the directory T90 verified. `verify-artifact` re-checks it on both architectures.

`check:workflows` pins actionlint and shellcheck by sha256 and matches its contract. Every claim in the worklog and in QA's results matched my re-run on the Pi.

Trying to fool the checker turned up three bypasses, all outside what QA's contract requires and none present in the repo's workflows:
- YAML aliases
- `pull_request_target` variants the denylist doesn't cover
- local actions outside `.github/actions/`

These are minors, to fix before the next workflow story. Merging with M1-AC8 (x64), M1-AC9 and M1-AC27 PENDING-CI is acceptable under the conditions in § Merge policy.

Good decisions:
- shellcheck is pinned rather than disabled, and it caught a real SC2012.
- `persist-credentials: false` on checkout.
- `sha256sum --strict -c` runs after an exact file-set check.
- The NEG step tells a timeout apart from a refusal.
- The implementer reported a self-inflicted red run and found a real blind spot: node:test writes no JUnit entry for a failing hook.

## Code findings
**C1 (minor): YAML aliases bypass `[sha-pin]` and `[permissions]`.** `.github/scripts/workflowRules.ts:91` (`if (!isMap(job)) continue;`) and `:107` (`if (!isMap(step)) return;`).
- **Problem:** an aliased job (`b: *job`) or step (`- *evil`) is an `Alias` node, not a `YAMLMap`. Both loops skip it, so neither its `uses:` nor its `permissions:` is checked. The comment assumes that a non-map job is malformed and that actionlint will report it. Since GitHub Actions supports anchors, that assumption no longer holds.
- **Failure scenario:** both files pass the check (exit 0, "every uses pinned, every job declares its permissions"), and actionlint 1.7.12 is clean on both:
  - In the first, `strategy.matrix.include: [{s: &evil {uses: actions/checkout@v4}}]` defines the anchor and `steps: [*evil]` uses it.
  - In the second, a job `b: *job` takes an anchor defined inside a matrix value; that job has a tag-pinned step and no `permissions:`.

  In this repo, QA's T11 line scanner would still flag the tagged `uses:` text. The `--dir` mode and the missing-permissions case have no such backstop.
- **Expected fix:** fail closed. Either resolve aliases before applying the rules (`isAlias(n) ? n.resolve(doc) : n`, or check `doc.toJS()`), or reject any alias in a workflow with its own rule ID. In both loops, report a job or step that is not a mapping instead of skipping it. QA adds the two cases as invalid fixtures.

**C2 (minor): the `[pull-request-target]` denylist misses common ways to check out PR code.** `.github/scripts/workflowRules.ts:30`, `:88`, `:111`.
- **Problem:** the rule only inspects `actions/checkout` `with.ref`/`with.repository` against three substrings.
- **Failure scenario:** each of these passes the check (exit 0):
  - `on: pull_request_target` with `ref: ${{ github.event.pull_request.merge_commit_sha }}`. The merge commit contains the attacker's code.
  - `ref: ${{ env.PR_REF }}`, where the workflow-level `env` holds `head.sha`.
  - A `run:` step doing `git fetch origin "pull/$N/head" && git checkout FETCH_HEAD && make`.

  Each runs fork code with the base repo's secrets and token. No current workflow uses the trigger, so nothing is exposed today. The risk is false assurance later.
- **Expected fix:** ban the `pull_request_target` trigger outright, and `workflow_run` too; the test plan's contract already allows this. QA's two fixtures (`head-sha`, `head-ref`) still fail, and a future label or title workflow can be allowed explicitly when it is reviewed. If the targeted rule is kept, at minimum add `merge_commit_sha`, `github.event.number` and `pull/` refs, and any `ref:` that is an `env.`/`steps.`/`needs.` indirection.

**C3 (minor): local actions outside `.github/actions/` are never scanned.** `.github/scripts/check-workflows.ts:73`.
- **Problem:** `uses: ./…` is accepted as pinned, but only `<dir>/../actions/**/action.y{a,}ml` is checked.
- **Failure scenario:** `uses: ./tools/evil`, whose `action.yml` contains `uses: actions/setup-node@v4`, passes (exit 0).
- **Expected fix:** for each `./` step `uses:`, resolve `<base>/<path>/action.y{a,}ml` and run `checkAction` on it, failing if it is missing. Alternatively, fail any local action outside `.github/actions/`.

**C4 (nit): a cached tool binary is trusted on its version string alone.** `.github/scripts/pinnedTools.ts:94-96`.
- **Problem:** the sha256 is checked only on download. Afterwards, any file at `~/.cache/notestead/tools/<name>-<version>/<name>` that prints the right version is run.
- **Failure scenario:** a corrupted or replaced cached binary keeps running unnoticed on the Pi. CI is unaffected: that path is not in any `actions/cache`, so every run downloads and verifies.
- **Expected fix:** pin the extracted binary's sha256 in `pinned-tools.json` and verify it on every run. That is cheap: shellcheck is 55 MB.

**C5 (nit): the tool download has no timeout.** `.github/scripts/pinnedTools.ts:46`.
- **Problem:** `fetch(asset.url)` has no deadline.
- **Failure scenario:** a stalled connection hangs `check:workflows` until the 60-minute job timeout, instead of failing with the offline hint.
- **Expected fix:** `fetch(asset.url, { signal: AbortSignal.timeout(120_000) })`.

**Checked and fine:**
- **Pins.** `git ls-remote` on upstream gives exactly the pinned commit for each lightweight tag:
  - checkout v7.0.1 → `3d3c42e5`
  - setup-node v7.0.0 → `82076278`
  - cache v6.1.0 → `55cc8345`
  - upload-artifact v7.0.1 → `043fb46d`
  - download-artifact v8.0.1 → `3e5f45b2`

  Upstream GitHub rejects 40-hex branch and tag names (GH002), and the checker rejects uppercase hex. The `@<40-hex>` rule therefore can't be satisfied by a tag that only looks like a SHA.
- **Tool checksums.** All four sha256 values in `pinned-tools.json` equal the release assets I downloaded. The two actionlint values also equal `actionlint_1.7.12_checksums.txt`.
- **Download path.** The whole buffer is verified before anything touches disk. Extraction runs in a `mkdtemp` (0700) directory inside the target dir, takes the named member only, and ends in an atomic same-filesystem `rename`. There is no TOCTOU window between verification and extraction.
- **Permissions rule.** Permissions set only at workflow level, and a reusable-workflow job with a tag and no `permissions:`, are both caught.
- **Cache poisoning.** The yarn cache key includes `runner.arch`, so the two architectures never share an entry. GitHub scopes caches to the branch, so a fork PR can only write in its own merge-ref scope. `.yarn/cache` zips are checksum-verified by yarn against the lockfile. The bundle cache is save-only, after a green T90, and keyed by the pin and `packages/web-build/**` (which has no npm dependencies).
- **Injection.** `needs.build.outputs.tag` reaches the script through `env`, not through `${{ }}`. Only static matrix values are interpolated.
- **Least privilege.** `verify-artifact` has `permissions: {}`, which is correct: same-run artifact download uses the runtime token. Hidden files (`test-results/.cache`) are excluded from the uploads.
- **Upgrade safety and licences.** The upstream tag comes only from `upstream/joplin-version.json`. Tool versions are kept out of it, as the contract requires. No upstream code was copied (`check:no-upstream-copy` passes). `yaml` 2.9.1 is ISC with no dependencies, actionlint is MIT, and shellcheck (GPL-3.0) is run, never shipped.
- **CI step versus `test:acceptance`.** The step's options and glob currently equal the script's (`ci.yml:74-77`, `package.json:17`). The drift risk QA noted remains a follow-up.

## Process findings
**P1 (minor): ADR-0009 A2 and the repo now disagree on where check scripts live.** `docs/adr/0009-repository-layout-and-tooling.md:43,72` versus `.github/scripts/`.
- **Problem:** A2 says repo-wide check scripts live in `packages/**`. `check:workflows` and `junit-summary.ts` live in `.github/scripts/`. The deviation is recorded and justified in the worklog, it came from the orchestrator's routing, and QA raised it in advance (test plan, Interpretations 1).
- **Judgement on the placement:** acceptable; it does not need to move. ADR-0009's binding principle holds:
  - The script runs identically on the Pi and in CI through a root `corepack yarn` script, and the workflows only orchestrate it.
  - It checks files the ci-cd specialist owns (`.github/**`), so keeping it there avoids a cross-owner edit loop.
  - It is eslinted (I confirmed that `.github/scripts/*.ts` are linted, 0 findings) and type-checked (`tsc -p .github/scripts/tsconfig.json` in `lint`).
  - QA's 24 black-box tests cover it.
- **Failure scenario:** a later agent reads A2 literally and either moves the scripts or puts build logic in `.github/scripts/`.
- **Expected fix:** the architect adds an amendment, A7. Pipeline-only tooling (`check:workflows` and CI report helpers) may live in `.github/scripts/`, owned by the ci-cd specialist, run through a root script and covered by `lint`. Anything shared with the build, images or other checks stays in `packages/**`.

**Process checks that passed:**
- **Test-first:** QA's `7efe03d` and `3f0b296` come before the implementation commits `984e480`, `1c1f950`, `a9ac43b` and `eba6596`.
- **Ownership:** no ci-cd commit touches `tests/**`, `docs/test-plans/**` or `docs/testing/**`. The root `package.json` and `yarn.lock` edits were permitted by the orchestrator.
- **Trailers and subjects:** every commit carries the correct `Agent:` trailer and an imperative subject.
- **Discipline:** no `.only`, no skips, no sleeps. Nothing was pushed, and the branch has no upstream.
- **Disputes:** none.
- **Honesty:** the worklog reports the red run its own tree write caused, and why.

## Merge policy (orchestrator question 3)
M1-S3 **may merge** with M1-AC8 (x64), M1-AC9 and M1-AC27 PENDING-CI, as M1-S2 did with M1-AC5. These ACs can only be produced by the user-approved first push, which comes after the merge. Everything checkable before the push is green on arm64:
- M1-AC8 passes.
- QA's requirements 1–6 are met statically.
- The arm64 interlock NEG step passes.

Conditions:
1. `STATUS.md` lists M1-AC8-x64, M1-AC9, M1-AC27 and, through it, M1-AC5 as PENDING-CI, closed by QA's V1–V8 on the first green run.
2. The architect amends the M1.md sentence "If T90 fails there, the fix … lands on the M1-S3 branch". After the merge, a CI failure is fixed on a follow-up branch (`fix/M1-S3-<slug>`), reviewed as a continuation of M1-S3, and M1-S2 still isn't reopened.
3. The orchestrator doesn't stack more workflow stories (M1-S8) on unproven CI. C1–C3 should be fixed, with QA adding fixtures for them, before or in M1-S8, the next story that adds a workflow.
