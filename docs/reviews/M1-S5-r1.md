# Review: M1-S5 `headless` container (minimal supervisor), round 1

Verdict: APPROVE

- **Scope:** branch `feat/M1-S5-headless-container` at `f451d16` (`git log main..HEAD`, 11 commits).
  - Implementer: senior-engineer (`939dbef`, `6223723`, `6360bff`, `bbc6f0a`; worklog `2445c69`; dispute D1 `d902870`, `0937066`).
  - QA RED: `59641b3`, `8565eb7`. QA harness fixes: `12f52a4`, `254f3d7`. QA results: `f451d16`.
- **Summary:**
  - Every M1-S5 criterion (M1-AC14 to M1-AC17 and M1-AC23, with their NEGs) is met on arm64.
  - Secrets go only on a stdin pipe. The CLI children get an allow-listed environment. The Data API token is fresh on every start and redacted, along with query strings.
  - The install-script allow-list sits in one place: root `package.json` `dependenciesMeta`. The lockfile check is sound; I re-proved this independently.
  - No blocker or major finding. Four minors and two nits are follow-ups, mostly for the architect and for M1-S6/M3.
  - **Merge policy:** M1-S5 may merge with x64 at PENDING-CI (M1-S8), as M1-S4 did. M1-AC23's amd64 half must be closed with CI evidence in M1-S8, not with a local stand-in.
- **Credit:**
  - **The sync-success judgement fails closed** (`syncOutcome.ts`). It pings the target before starting a sync, so a refused target never starts a 3.5-minute `sync` that would exit 0 anyway. The residual window is written down rather than hidden.
  - **Defence in depth on secrets:** the child environment is an allow-list (`cliRunner.ts:40-48`), so an operator who adds unrelated variables can't leak them into a CLI child either.
  - **A runtime pin check:** `findPinnedCli` exits 70 if the installed CLI differs from the exact pin, so a mismatched image can't serve.
  - **Image hygiene:**
    - the base is pinned by its multi-arch index digest
    - `/app` is root-owned and `/data` is `0700` uid 1000
    - there is no `VOLUME` and no `HEALTHCHECK`, following the ADR-0006 amendment
    - `enableScripts: false` is stated explicitly
  - **Facts proven before relying on them:** the engineer tested in a scratch project that `workspaces focus` ignores immutability and that `dependenciesMeta.built` is honoured while scripts are off.
  - **A harness race raised properly:** D1 went to the test plan as a dispute, with a root-cause analysis and a suggested fix, instead of being worked around.

## Code findings

1. **minor:** the README describes the install order the wrong way round (`packages/headless/README.md:14`).
   - **Problem:** the README says "an immutable check of `yarn.lock`, then `yarn workspaces focus`". Since `bbc6f0a` the Containerfile does the opposite (`packages/headless/Containerfile:26-37`): it runs the focused install first and the check second. The worklog (§Image, step 3) is correct; the README went stale.
   - **Failure scenario:** someone reasons from the README about a security property, for example the ci-cd specialist writing provenance claims in M5, or a reviewer of a later allow-list change. They conclude that nothing from a drifted lockfile is ever fetched or built during the image build. In fact, with a `package.json` that has drifted from `yarn.lock`, the focus step fetches the drifted tree and runs any allow-listed install scripts. Only then does the check fail the build.
     - No image is produced, so this is not a hole. I verified that the check catches drift (see Verification).
     - The documentation still states a stronger property than the build has.
   - **Expected fix:** reword the line, for example: "a focused production install from `yarn.lock`, then a lockfile check that fails the build if `yarn.lock` doesn't match the manifests". It can ride along with any M1-S6/M3 headless change.

2. **minor (ADR gap, architect first):** the sync-success judgement consumes three upstream interfaces that ADR-0003's "Upgrade impact" doesn't list.
   - **Where:** `packages/headless/src/syncOutcome.ts:22-33`, `packages/headless/src/stopTheWorldStrategy.ts:45-54` and `:110-117`.
   - **Problem:** the supervisor now depends on:
     - the `Completed:` and `Last error:` report lines of `joplin sync`
     - the `locale` setting, fixed to `en_GB`
     - the Joplin Server's `GET /api/ping` response, called directly by the supervisor

     ADR-0003 doesn't cover how the supervisor detects a successful sync, and its consumed-interface list omits all three. The worklog records the gap, justifies it (§How sync success is detected) and routes it to the architect, so this is not an undocumented change. However, `docs/worklog/M1-S5.md:56-57` says "ADR deviations: None", which understates it: extending the list of consumed upstream interfaces is an architectural change.
   - **Failure scenario:** a CLI bump within 3.7.x rewords or re-localises the sync report. The supervisor then never becomes ready. This fails safe, and `ac15` catches it. But the person doing the bump follows ADR-0003/ADR-0005's upgrade checklist, which doesn't mention these strings, and loses time finding the cause.
   - **Expected fix:**
     - **Architect:** amend ADR-0003 with the detection rule, the three interfaces under "Upgrade impact", and the residual window.
     - **Orchestrator:** file the upstream-first proposal (`joplin sync` should exit non-zero on any failed sync, retryable network errors included).
     - **Engineer, in future worklogs:** list such additions under "ADR deviations", not only under a separate gap heading.

3. **minor (supply chain, architect / ci-cd follow-up):** the sqlite3 native binding is downloaded at build time without an integrity check (`packages/headless/Containerfile:26`, via `sqlite3`'s `"install": "node-pre-gyp install --fallback-to-build"`).
   - **Problem:** `yarn.lock`'s checksum covers sqlite3's npm tarball, not the prebuilt `node_sqlite3.node` that node-pre-gyp fetches from GitHub releases. node-pre-gyp verifies no hash. This is the mechanism ADR-0009 A4 chose ("sqlite3's own install"), so it isn't a deviation. But A4 exists for supply-chain safety, and it doesn't record this residual.
   - **Failure scenario:** a replaced release asset (`sqlite3-v5.1.6-napi-v6-linux-{arm64,x64}…`) is built into the image unnoticed. That native code is then loaded into the process that holds the plaintext sync and master passwords and the decrypted notes. `ac23-no-other-builds` and `ac23-sqlite3` would both still pass.
   - **Expected fix:**
     - **Architect:** record the residual in ADR-0009 A4 and decide between two options. Option one: pin the binding's sha256 per architecture and verify it in the Containerfile right after the focus step. Option two: build sqlite3 from source in the install stage, which needs a toolchain in that stage only.
     - **ci-cd specialist:** make sure the M5 SBOM and provenance name the binding.

4. **minor (M1-S6 follow-up):** nothing notices when the image runs without a reaping init (`packages/headless/bin/supervisor.ts:12-36`).
   - **Problem:** ADR-0006 and ADR-0003 Decision 1 require `--init` (or tini). The image can't enforce this, and the README and Containerfile header document it, which is right. Started without `--init`, the supervisor becomes PID 1 and runs without a word. The direct-child design means it reaps its own CLI children. Orphaned grandchildren, though, would become zombies, which was S3's finding.
   - **Failure scenario:** a user runs the image with plain `docker run …` or a catalog template that has no `init:` key. A zombie later hangs a cycle (M3), and nothing in the log points to the missing init.
   - **Expected fix:**
     - M1-S6's compose file sets `init: true`, which ADR-0006 already requires.
     - The supervisor logs one warning at startup when `process.pid === 1`, which is cheap. It shouldn't exit, because some runtimes inject an init differently.
     - QA can add a NEG to the M1-S6 or M3 plan: no `--init` → the warning is logged.

5. **nit:** a redaction comment overstates what `JSON.stringify` escapes (`packages/headless/src/redact.ts:17`).
   - **Problem:** the comment says the escaped form covers "a non-ASCII password inside logged JSON". `JSON.stringify` doesn't escape non-ASCII characters: `JSON.stringify("a Δ$x!\"b")` gives `"a Δ$x!\"b"`. Only `"`, `\` and control characters change. The behaviour is right, and the unit test checks the `"` case. Only the comment is wrong.
   - **Failure scenario:** someone later relies on the comment and assumes `Δ`-style escapes are covered. A logger that escapes non-ASCII would then leak a password containing `Δ`.
   - **Expected fix:** correct the comment (quotes, backslashes and control characters). Optionally, also add the `\uXXXX` form of non-ASCII secrets.
