All four acceptance criteria are met on arm64. My re-runs of install, lint, unit and the acceptance suite reproduce the worklog's and QA's numbers exactly.
- `check:pin` validates every pin field with dotted paths and fails closed on unknown `@joplin/*` packages.

- The findings below are minor or nit only, so they are follow-ups. The most useful one: `check:pin` accepts non-npm (git or `patch:`) resolutions of `joplin`/`@joplin/*`.

## Code findings

### C1 (minor): `check:pin` accepts forked or patched resolutions of the pinned packages
- **Where:** `packages/web-build/src/lockfile.ts:62-82` (`checkLockfile`). It compares only the lockfile's `version:` field and ignores the protocol in `resolution:`.
- **Problem:** a `@joplin/lib` resolved from a git URL, or a `joplin` resolved through yarn's `patch:` protocol, still has `version: 3.7.1`, so the check passes. I confirmed this with a probe. `valid.yarn.lock` was edited so that:
  - `@joplin/lib` resolves to `"@joplin/lib@https://github.com/someone/joplin-fork.git#commit=0123…"`
  - `joplin` resolves to `"joplin@patch:joplin@npm%3A3.7.1#~/local-hack.patch::…"`

  `check:pin` then printed `OK … resolves joplin to 3.7.1 and every lockstep @joplin/* package to 3.7.x` and exited 0.
- **Failure scenario:** someone runs `yarn patch joplin`, or adds `"resolutions": {"@joplin/lib": "github:…"}`. The fork reaches the headless image with `check:pin` green. That silently bypasses the golden rule that upstream changes live only in `patches/` with a justification and an upstream link, and it bypasses ADR-0005's exact published-CLI pin.
- **Expected fix:** for `cli.npm` and every `@joplin/*` entry, the exempt forks included, require `resolution` to be `<name>@npm:<version>`. Reject `patch:` until a reviewed patch exists in `patches/`, then allow only patch paths under `patches/`. QA should add a NEG fixture lockfile. This fits naturally with M1-AC26 (M1-S9), which already extends `check:pin`. It is not required for this merge.

### C2 (nit): the fixed-sleep lint ban only catches `waitForTimeout`
- **Where:** `eslint.config.js:172-181`.
- **Problem:** the ban covers only `waitForTimeout`. `await new Promise(r => setTimeout(r, 500))` in a Jest, node:test or Playwright test passes lint, while CLAUDE.md and ADR-0007 forbid any fixed sleep. The M1-S1 command contract only asked for `waitForTimeout`, so this is not a defect of this story.
- **Expected fix (M1-S6, with a QA NEG fixture):** extend the `no-restricted-syntax` selectors for test files to cover `setTimeout` inside a `new Promise(...)`, and `timers/promises` `setTimeout`.

**Credit:**
- Process spawning uses argument arrays, never a shell.
- A `web.repo` starting with `-` is rejected (option injection), and `GIT_TERMINAL_PROMPT=0` is set.
- The upstream cache is filled through a temp directory and a rename, so a partial cache is never trusted.
- A non-git `--root` fails closed (exit 1, with git's message).
- `installedCli.ts` is real code that M1-S5 needs, not a placeholder written only to satisfy M1-AC1.

## Process findings

### P1 (minor): the engineer authored QA-owned harness config
- **Where:** `931355c`, files `jest.config.js` and `playwright.config.ts`.
- **Problem:** CLAUDE.md gives QA ownership of "test fixtures and harness config", but the engineer wrote both files.
- **Mitigations, all in place:**
  - The engineer disclosed it (worklog, deviation 7).
  - The architect accepted it (ADR-0009 amendment, "Root configuration files").
  - QA reviewed and adopted both files (test plan, "Test integrity").
  - The content is sound: `testMatch` excludes `tests/acceptance/**` and `tests/fixtures/**`, and Playwright sets `forbidOnly: true`.
- **Failure scenario if this becomes habit:** the implementer can narrow `testMatch` or `testPathIgnorePatterns` so that failing tests silently drop out of `corepack yarn test`.
- **Expected fix (no change on this branch):** from M1-S6 on, either QA commits harness config in its RED commit, or the test plan explicitly delegates it *before* implementation starts.

### P2 (minor): an unrelated architecture decision rides on the story branch, bundled into one commit
- **Where:** `4277bff`, plus `a5365ca`.
- **Problem:** `4277bff` mixes the M1-S1 alignment (M1-AC3, ADR-0005, ADR-0009 A1–A6) with an unrelated, security-relevant decision. That decision publishes the MCP server via tunnel + Access and touches ADR-0006, ADR-0008, ARCHITECTURE, M4-AC18, M5-AC14 and O4.
- **Failure scenario:**
  - Reverting the M1-S1 merge, or bisecting it, also reverts the MCP exposure decision.
  - An approval of M1-S1 can be read as approval of ADR-0008 changes that nobody reviewed here. I did not review that content; it is out of scope for this story.
- **Expected fix:** commit cross-cutting architecture decisions on `main` or on their own branch, at minimum as a separate commit per concern. This finding is for the orchestrator and architect, not the engineer.

### P3 (nit): `corepack yarn test` exits 1 at `931355c`
- **Where:** `931355c` adds `"test": "jest"` before any test file exists, so `corepack yarn test` exits 1 at that commit. The worklog discloses this (line 42), but its line "Root scripts are added in the commit that implements them" isn't accurate for `test`.
- **Judgement:** acceptable. Under test-first, every commit between QA's RED commit and the last engineer commit fails the acceptance suite anyway. The `--no-ff` merge keeps `main`'s first-parent history green for bisect. `passWithNoTests` would have been the wrong fix, because it weakens M1-AC1.
- **Expected fix next time:** add the `test` script in the commit that adds the first test (`91f046e` here).

**Credit:**
- Test-first order is clean: QA's RED commit `9b0fb8e` precedes every engineer commit.
- `git log 9b0fb8e..HEAD -- tests/` contains only QA commits.
- Engineer commits are small, focused, imperative Conventional Commits with correct `Agent:` trailers.
- The worklog reports its failures honestly (eslint 22 → 5 → 0, Jest 1 failed twice, and the spend-limit interruption).
- The `sqlite3`/`enableScripts` discovery was surfaced rather than worked around, which led to A4 and M1-AC23.
- There are no disputes, and none was needed.
