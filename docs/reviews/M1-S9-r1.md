## Summary
All four ACs are met on arm64, and every number in the worklog and in QA's results matched my re-run.
- The SPDX evaluator is correct: `AND` binds tighter than `OR`, parentheses work, and `WITH`, `+`, `-only`/`-or-later` and the legacy forms behave as A9 says. Every malformed or lower-case form fails closed. I couldn't fool it into "allowed".
- The three exceptions have exact versions and evidence that I verified independently. The new dependency `spdx-license-list@6.12.0` (CC0-1.0, no dependencies) is pinned exactly and by its lockfile checksum.
- No upstream text is committed: the AC25 header and holder are read from `upstream:LICENSE` at run time.

The findings are four minors and two nits, all fit for follow-up:
- the `resolutions`-alias hole in `check:pin` (minor, as the engineer judged);
- an exception-versus-standard-text order that differs from the ADR-0010 amendment and isn't recorded as a deviation;
- two pin-bump drift cases that are reported as notes instead of failures;
- a wrong "none at the pin" premise.

Merging with x64 and T90 PENDING-CI is acceptable (§ Merge policy).

Good decisions:
- Upstream's header is derived, never hard-coded, and the unit tests use an invented licence.
- The exception schema fails closed (unknown keys, duplicates, ranges, `UNKNOWN` without `prepublishBlocker`).
- A licence text or `noticeText` that contains a `Package: x@y` line fails the step, so no entry can be forged.
- Notices are written to a temp file and renamed, and nothing is written on failure.
- The standard texts come from an offline CC0 package that `check:licenses` also gates, instead of vendored texts.
- The engineer found and reported the alias hole on their own, and every red run is logged honestly (rows 7, 12, 14, 18, 22).

## Code findings
**C1 (minor): a `resolutions` npm alias bypasses the npm-source rule for transitive `@joplin/*` packages.** `packages/web-build/src/lockfile.ts:107-108`.
- **Problem:** the rule takes the name from `resolution:`. An alias entry is therefore checked under the alias target's name and skipped as "not `@joplin/*`".
- **Failure scenario:** I probed `checkLockfile` with the key `"@joplin/lib@npm:other-pkg@3.7.1"`, resolution `other-pkg@npm:3.7.1`, and a `joplin` entry that depends on `"@joplin/lib": "npm:other-pkg@3.7.1"`. It returned `[]`.
- **Why minor, not major:**
  - The CLI itself is protected: an aliased `joplin` leaves no `joplin` entry, and the existing "no entry for the pinned CLI" problem fires.
  - Exploiting the hole needs a deliberate edit to our own root `resolutions`, which is reviewed code.
  - `check:licenses` still gates whatever gets installed.
- **Expected fix:** the engineer's and QA's proposal: any lockfile key with a `joplin`/`@joplin/*` descriptor must resolve to that same name, plus a QA NEG fixture.
  - I'd ask the architect to schedule it concretely, for example in the next story that touches `check:pin` or in M1-S8. "The first `patches/` story" has no date.

**C2 (minor): notices precedence differs from the ADR-0010 amendment, and the difference isn't recorded.** `packages/web-build/src/notices.ts:250-262`, asserted by `src/notices.test.ts:131`.
- **Problem:** the amendment lists the standard SPDX text (rule 3) before "otherwise, an exception with `noticeText`" (rule 4), with "the first matching rule applies". The code applies an exception's `noticeText` before the standard text.
  - The worklog presents this as "by the ADR-0010 precedence" (`docs/worklog/M1-S9.md:46`) and records "ADR deviations: None" (`:80`).
- **Failure scenario:** none at the pin. `onenote-converter` ships a `LICENSE`, and `node-bitmap` and `tkwidgets` declare nothing, so I counted 0 exception entries in the generated file.
  - It matters for a future exception on a package that declares `MIT` but whose real licence, established from its repo, differs. The code would use the reviewed text, while the ADR text calls for the standard MIT text.
- **Expected fix:** record it in the worklog as a deviation, and have the architect amend ADR-0010 to the implemented order. I recommend keeping the code's order, because a reviewed exception is more specific than a declared field.

**C3 (minor): pin-bump drift in the notices produces notes, not failures.** `packages/web-build/src/notices.ts:301-302` and `:308-309`.
- **Problem 1, uninstalled closure packages:** these are skipped with a note, whatever their lockfile entry says. At the pin, all 11 are platform-conditional. I checked that `fsevents` (`os=darwin`) and `lightningcss-*` (os/cpu/libc) carry `conditions:` in upstream's `yarn.lock`, but nothing enforces it.
- **Problem 2, unresolved banners:** banner comments that name no installed package are also only notes.
- **Failure scenario:** a pin bump brings a webpack-injected polyfill whose banner names its package only in prose, like the two Feross banners the phrase map covers today.
  - `build` passes with a note, and `third-party-notices.txt` omits that package. M1-AC29 says "omission is not".
  - The banner text itself still reaches users through the linked `*.LICENSE.txt`, which is why this is minor.
- **Expected fix:**
  - Fail when an uninstalled closure entry has no `conditions:` line.
  - Fail on an unresolved banner unless its first line is on a short reviewed list. Today that list would hold one entry: the inline coi-serviceworker notice at v3.7.21.
  - QA adds a NEG for each.

**C4 (nit): a plain-string `licenses` field counts as "no licence".** `packages/web-build/src/spdx.ts:116`.
- **Problem:** `requireg@0.2.2` in the S1 tree declares `"licenses": "MIT"`. That is neither A9 form, so its entry reads `License: UNKNOWN`, even though the entry contains its full MIT `LICENSE` text.
- **Impact:** nothing is omitted, and `check:licenses` would deny such a package, which is fail-closed.
- **Expected fix:** optional. The architect may extend A9 so that a `licenses` string is read as its value.
