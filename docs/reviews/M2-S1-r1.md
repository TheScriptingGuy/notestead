## Code findings

**C1, minor.** `tests/e2e/m2-s1/e2ee-unlock.spec.ts`, M2-AC2 step 3 and NEG step 2: `expect(noSeedIn(...)).toBeUndefined()`.
- *Problem:* `noSeedIn` returns the first seeded value found (the tag, folder name, title or body). When the check fails, Playwright prints that value as `Received`. Step 6's `toContain(body)` also prints the whole frame text.
- *Scenario:* a failing CI run on the public repo prints the seeded strings. They are synthetic, not secrets, but the plan says the scan helpers are value-free, and the NEG window already returns a generic message for the same condition.
- *Fix:* return a boolean or a label such as `'folder'`, `'title 2'`, `'body 3'`, as the step-5 window does.
- *Where:* follow-up in M2-S2, the next touch of these helpers. Not a blocker.

**C2, minor.** `tests/e2e/m2-s1/sync-through-proxy.spec.ts`, steps 4 and 6.
- *Problem:* the policy is evaluated once, after the first sync completes, and a poll is only used for the planted control. A cross-origin request made later (for example the app's periodic re-sync) is not seen by M2-AC1.
- *Mitigation:* M2-AC2 step 8 evaluates the policy again after a much longer session.
- *Fix:* ideal is to assert in a fixture teardown, or to re-run `classifyRequests` at the end of every `webNetwork` user. Follow-up in M2-S2.

**C3, minor.** `tests/e2e/support/projects.ts` and the A3 serial rule.
- *Problem:* `chromium-serial` has `dependencies: ['chromium']`. In Playwright, a failure in the parallel project means the serial specs do not run. When the first disruptive spec arrives (expected in M2-S5), a red parallel run will hide it as "did not run".
- *Rule check:* no serial spec exists yet, so the project is exercised only by the static SER-01 to SER-04 tests. The rule is applied in `playwright.config.ts` via `e2eProjects`, and `playwright test --list` is unchanged for the existing tests.
- *Fix:* M2-S5 (QA) should state in its plan that "not run" counts as failed in CI. Alternatively use `teardown` semantics or check the skipped count in `e2e.yml`.

**C4, nit.** The NEG's strength under D1 depends on L18.
- Before the password nothing is downloaded, so "no seed text in the profile" is partly true by upstream design. The test still has real discriminating power:
  - S4 and S4b prove the window sees a real decryption.
  - Step 7 of the positive test proves the scan sees the seed tag in a real profile.
  - The NEG also asserts `files > 0`.
- If upstream fixes U13, the server's copies will download encrypted. The same assertions then become stronger without any change, because the tag only appears decrypted.
- No action needed; this is recorded so it isn't lost.

**C5, nit.** The header comment of `e2ee-unlock.spec.ts` (lines 4 to 6) has an over-long line after the D1 edit. Tidy it at the next touch.

Good decisions, briefly:
- The recorder only observes (no routing), and the classifier decodes the path, so an encoded `/joplin-server/...` request cannot slip past.
- `connection_check` is matched as an exact URL string plus the `HEAD` method.
- The control request uses `.invalid`, so nothing leaves the machine.
- The OPFS scan returns paths and counts only, and fails rather than passes on unreadable files.
- `describeField` checks the rendered element (C-N1).
- Query strings are removed from `network.log`, and the fixture redacts it with the worker secrets.
- The wrong passwords are registered as secrets before use.
