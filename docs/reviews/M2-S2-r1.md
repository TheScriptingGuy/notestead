## Code findings

**C1, minor. `tests/e2e/support/pages/joplinWebApp.ts:383-392` (`NoteScreen.waitSettled`) and `docs/testing/strategy.md` §3, "Absence over a window", last sentence.**
- *Verdict on F8:* accepted, with the gaps below. The window is short, it is anchored to an observed event (a frame with `.cm-content`), it goes through `waitFor` (the sole allowed timer), it applies only to a **new** note or to-do, and it is written in the strategy and the plan.
- *The failure mode is safe.* A steal that comes later than the window can only produce a false **failure**, never a false pass. In M2-AC3 the REST body or title would differ (`readNote` poll). In M2-AC5 `notesTitled(TD)` or `todoCheckbox(TD)` would never match. So this is a flake risk, not an unsound assertion.
- *Gaps against §3.* The rule says a window needs "its reason written" and "a sensitivity run [that] proves the window would catch the bug".
  - The new sentence says a stabilisation is "the same rule at a small scale" but names no evidence. For F8 there is none: run 1 shows the race exists, not that one second covers it.
  - The plan records no measured lag between `.cm-content` appearing and the focus moving, so 10 x 100 ms is a guess.
  - A positive event may exist. After the editor loads, the main document's `activeElement` becomes the `<iframe>`. Waiting for that is an event wait with no duration.
  - The count logic (reset on a change, done at 10) is pure and could have a fake-driven unit test, which the P2 "when feasible" wording fits.
- *Scenario:* a loaded x64 CI runner delays the focus move by more than a second after the frame appears. The first title characters land in the editor, and M2-AC3 or M2-AC5 fails on a retry-able flake. The strategy's flake policy (§6) then asks for a root cause that the plan has not recorded.
- *Fix (QA):*
  - take the lag from the run-1 trace and write it in the plan;
  - if the trace shows the focus always ends in the iframe, wait for that and keep the count only as a fallback;
  - amend the strategy sentence to say what evidence a stabilisation needs (a measured lag, or the failing run it fixes).
- *Where:* M2-S3 QA (next touch of `NoteScreen`), or at the first flake. Not a blocker.

**C2, nit. `tests/e2e/m2-s2/todos.spec.ts:71-74` (the due time typed in the `Europe/Amsterdam` context).**
- *Problem:* when the due time falls in the repeated hour at the end of summer time, the typed digits (for example `02:30`) are ambiguous, and Chromium resolves them to the first occurrence (CEST). I confirmed this with `TZ=Europe/Amsterdam node`: `new Date('2026-10-25T02:30')` is one hour earlier than the epoch whose Amsterdam wall clock is `02:30` CET.
- *Scenario:* a run that picks a due time between 01:00 and 02:00 UTC on Sunday 2026-10-25 (or 2027-10-31) fails `todo_due` with a difference of exactly one hour. This is a rare false failure that looks like a product timezone bug. No schedule triggers E2E, so only an on-demand run in that hour is affected.
- *Fix:* before `Save alarm`, assert in the page that `new Date(datetimeLocalValue(...)).getTime() === due`, with a message naming the ambiguous hour. Or move `due` out of that hour. The in-page control of S5 can carry it.
- *Where:* M2-S3 QA, next touch of `todos.spec.ts`. Not urgent.

**C3, nit. `tests/e2e/m2-s2/todos.spec.ts:90-103` and `tests/e2e/support/notificationSpy.ts` (frame coverage of the NEG).**
- *Problem:* the NEG asserts that the spy is installed in the **main** frame. `readNotificationSpy` returns `frames` and `framesWithSpy`, but the real-app test never looks at them. SPY-03 proves a plain same-origin iframe. If the app's editor or viewer frame ran without the init script, a notification from there would be missed silently.
- *Mitigation:* upstream's `app-mobile` source has no `new Notification` or `showNotification` at the pin (I grepped the reference clone at v3.7.21), and the header comment says service-worker-scope notifications are out of reach.
- *Fix:* attach `frames` and `framesWithSpy` as an annotation at the end of the window, so the coverage is visible, or assert that they are equal.
- *Where:* M2-S3 QA. Not a blocker.

**C4, nit. Failure output and seeded values (`tests/e2e/m2-s1/e2ee-unlock.spec.ts:173-174`; the REST diffs in the M2-S2 specs).**
- *What I checked:* the M2-S1 r1 C1 fix is complete for what it named (`noSeedIn` is `seedLabelIn`, step 6 polls a verdict, the scans return labels). No password, master password, token or `token=` appears in `test-results/verify/m2-s2/**`. The only identifier is the throwaway user's e-mail in upstream's own console line `userFetcher: Got user`.
- *Residual:* `expect(readReference(...)).toEqual(reference)` and the message `exactly one note titled "${n.title}"` print the seeded bodies and titles on failure. The M2-S2 `toEqual` diffs print typed titles, bodies and ids (for example the `s1b`, `s1d`, `s4` logs).
- *Why this is only a nit:* all of it is synthetic and random per run, a diff is the point of a REST assertion, and these are not scan helpers. But the strategy does not say where the line is.
- *Fix:* one sentence in strategy §5 next to "Seed scans report a label": "scan results are value-free; a data diff of per-run synthetic values may print". Optionally drop `${n.title}` from the step-9 message.
- *Where:* M2-S3 QA, next touch of `docs/testing/strategy.md`.
