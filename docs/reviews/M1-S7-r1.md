## Rulings on the focus questions
**1. Does M1-AC21 test what the backlog says? Yes.**
- **Step 1:** `POST /notes` through the in-container probe, then read back with `GET` (`walking-skeleton.spec.ts:71-77`).
- **Step 2:** a real sync cycle, proven both by the supervisor's `lastSync` and by the server holding the encrypted item (`:78-86`).
- **Step 3:** a fresh context and OPFS, the real wizard, and a URL that matches `http://127.0.0.1:<port>/joplin-server`.
  - The access log proves `POST /joplin-server/api/sessions` → 200 from the browser's Host.
  - The positive control shows the title is absent before the unlock.
- **Step 4:** the master password goes into the masked field, and "(Master password)" is shown.
- **Step 5:** `expect.poll`, 1 s interval, 3 min.
- **Step 6:** another headless sync, then `GET /notes/:id` equals the created body, with `is_conflict: 0` and exactly one note of that title.
- **No sleeps.** The only fixed duration is `holdsFor`, the NEG's absence window. It sits in the exempt `tests/support/poll.ts` and is the "absence over a window" form that strategy §3 allows. The window is anchored to the observed sync error.

**2. QA's interpretations.**
- **"Run one headless sync" as a restart: faithful for M1.**
  - In M1 the supervisor syncs only in its start cycle (`stopTheWorldStrategy.ts:96-129`).
  - `lastSync` is set only after `judgeSync` accepts the sync, `e2ee decrypt` succeeds and the Data API is up. So "healthy with `lastSync` > restart" is exactly one successful sync.
  - The rotated token is registered at once, which closes C1-R6 for restarts the harness causes.
  - **For M3:** the test stays valid as long as the start cycle still syncs. Once M3 has a manual trigger, the helper's body should switch to it, as the plan already lists. A restart also rotates the token and restarts the Data API. That would break any long-lived Data API client attached to the same service, such as the M4 MCP server. So M3 or M4 must make the switch before a test combines a sync with an MCP session.
- **"as user1" read as a fresh per-test E2EE user: accepted.**
  - `user1@example.com` has no E2EE, so step 4 could not run as written.
  - A shared user would also break ADR-0007's per-test isolation.
  - The AC text should be reworded (nit P-N1).
- **NEG through a second web container with `JOPLIN_SERVER_HOST` set to the browser's Host: it proves the same thing.**
  - Caddy v2's `reverse_proxy` passes the incoming Host through when no `header_up Host` is set. The server therefore receives byte-for-byte the Host it would see with the rewrite removed. The other `header_up` rules are identical because it is the same image.
  - The in-test positive control (`/api/ping` → 200 through the stack's `web`, and → 404 `Invalid origin: http://<neg host>` through the NEG container) pins the single difference.
  - The sensitivity run (the positive test against the NEG container fails at step 3) shows the rewrite is what makes the skeleton work.
  - It adds no product switch, which keeps production safe. I prefer it to a disable flag.
  - The only thing it doesn't cover is a hypothetical future Caddy that changes its default Host handling. That is irrelevant to the AC, which is about the server refusing a foreign Host and the app surfacing it.

**3. C1-R1 completeness: met for today's flows, with two gaps (C1-R1a, C1-R1b).**
- **(1) Guard:** `typeLikeUser` refuses a known or marked secret unless the field is `type="password"`, checks both before and after typing, and presses no key when it refuses. This is proven on a fake Locator (7 cases) and on a real DOM.
  - The page objects type only through it.
  - The sync password and master password fields are masked in upstream's app at the pinned ref.
- **(2) Credential headers learnt from the trace:** the reporter learns them in `onTestEnd` before it redacts anything, and then applies them to every attachment and, in `onEnd`, to every output file.
  - I checked the passing run's stack logs (`test-results/e2e/stack/*_web_1.log`): every `X-Api-Auth` is already `REDACTED` by Caddy, so passing tests, which have no trace and learn nothing, leave no session id there.
- **(3) No pixels:** screenshots, video and screencast frames are all off. The C1-R1 trace has no `.jpeg` entry.
- **Leak-scan NEG:** genuine. With the feed off, the summary shows the account password and both session ids in `resources/*.json`, both passwords in `trace.trace`, and the account password in `error-context.md` and the HTML report.
- **Remaining paths to a CI upload:**
  - The worker writes `trace.zip` unredacted, which is C1-R2 (M1-S8, unchanged).
  - A "marked secret" that no registry knows (C1-R1a).
  - A session id that is only ever in a response body (C1-R1b).
  - Data API token: the browser never talks to the Data API. The probe keeps the token inside the container, and the `?token=` pattern backs up any error text.

**4. The Node 24 trace-merge workaround: acceptable everywhere, and I would not make it Pi-only.**
- **What CI (Node 22) loses:**
  - the runner's test-level trace: the `test.step` boundaries, non-locator `expect`s and the fixture/hook timeline;
  - traces of contexts other than `webApp`. No spec uses the built-in `page` or `context` today, but a future spec that does would get no trace at all (nit C-N3).
  - Step names and timings stay in the HTML, JSON and JUnit reports. Locator actions, `expect(locator)` calls, DOM snapshots and the network log stay in the fixture's trace.
- **Why not CI-only `use.trace`:**
  1. The C1-R1 scan proved the fixture's trace path. A different path on CI, where artifacts are uploaded, would be the one configuration nobody scanned.
  2. Two recorders on one context duplicate work.
  3. CI's runners may move to Node 24.
- The loss is small. Report F2 upstream and revisit when Playwright fixes it.

**5. Process: clean (see below).**

## Code findings
**C1-R1a (minor; next harness story, at the latest M1-S8). `tests/e2e/support/typeLikeUser.ts:65-71`.**
- **Problem:** `secret: true` protects only the pixel channel. A text that is marked secret but is not in any registry is typed with `pressSequentially(text)`. Playwright records that value in clear in the trace action's params (`trace.trace`, which `c1r1-planted` shows to be a real channel), and in the report's step title. Because nothing registered the value, the redacting reporter cannot remove it.
- **Failure scenario:** an M4 test types a freshly generated MCP bearer token or a new E2EE password into a password field with `{ secret: true }` and forgets `registerSecrets`. The guard passes, and the CI trace and HTML report carry the value in clear.
- **Expected fix (QA):** on the secret path, register the text (`registerSecrets([{ label: 'typed_secret', value: text }])`) before the first key. Add a unit case asserting that a marked, unregistered text ends up in `registeredSecrets()`.

**C1-R1b (minor; with C1-R2 in M1-S8, or the next harness story). `tests/e2e/support/redactingReporter.ts:130-150`, `tests/support/redact.ts:114`, `tests/harness/selftest/realflow-secrets.spec.ts:165-169`.**
- **Problem:** both the reporter and the scan's oracle learn session ids only from **request** headers (`X-API-AUTH` that the browser sent). A session id that appears only in a `POST /api/sessions` **response body** is invisible to both:
  - the reporter does not redact it;
  - the leak scan does not know to look for it.

  Because the fix and its proof share one source, this blind spot cannot show up as a test failure.
- **Failure scenario:** the test fails, or the app re-logs in, between a login response and the next request that uses that session. For example, a 403 makes upstream's `JoplinServerApi` create a new session just before the failure, and the trace then keeps an unused session id in `resources/<sha1>.json`. It is a live credential of a server that is throwaway, so the impact is low, but C1's claim ("no credential in any artifact") is broken.
- **Expected fix (QA):**
  - The reporter also learns the `id` of each `…/api/sessions` response, found through that network entry's response `_sha1` resource.
  - The inner spec collects session ids independently with `page.on('response')` on that URL.
  - Add a unit case with a login response whose id is never sent in a later request.

**C-N1 (nit). `tests/e2e/support/typeLikeUser.ts:54-61`.**
- **Problem:** `requireMasked` checks the `type` **attribute**, not what the element renders. A `<textarea type="password">` or a custom element carrying that attribute would pass, yet show its text.
- **Failure scenario:** unlikely with react-native-web, but the guard would silently accept such a field.
- **Expected fix:** `field.evaluate(e => e instanceof HTMLInputElement && e.type === 'password')`.

**C-N2 (nit; M2 cross-surface flows). `tests/e2e/m1-s7/walking-skeleton.spec.ts:127-132`.**
- **Problem:** step 6 meets the AC's wording, but the headless body it reads is the one the headless profile always had. Nothing checks that the **web app** decrypted the body correctly: the UI side only checks the title in the list.
- **Failure scenario:** a web-side decryption bug that garbles the body but not the title would pass M1-AC21.
- **Expected fix (QA, in M2):** open the note in the web app and compare the rendered body, or add an edit made in the web app and read it back through the Data API (ADR-0007 cross-surface).

**C-N3 (nit). `tests/e2e/support/fixtures.ts:197-216`, `docs/testing/strategy.md` §4.**
- **Problem:** with `use.trace: 'off'`, only `webApp` records a trace. A spec that uses Playwright's built-in `page` or `context` fixture gets no trace on failure, with no warning.
- **Failure scenario:** an M2 spec written with `async ({ page })` fails on CI, and the uploaded artifacts hold no trace.
- **Expected fix (QA):** override `page` and `context` in `fixtures.ts` so they throw and point to `webApp` (or delegate to it), and add one line to strategy §4.
