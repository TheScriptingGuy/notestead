## Approach
### Install-script allow-list (M1-AC23, ADR-0009 A4)
- **Mechanism: the per-package yarn setting.** A scratch project (`~/joplin-web-app-work/spikes/m1-s5-yarn`, two `file:` packages with a `postinstall` each) showed that yarn 4.16 honours `dependenciesMeta.<name>.built: true` while `enableScripts` is false: the allowed package's script ran (`YN0007 must be built`), the other was skipped (`YN0004 … all build scripts have been disabled`).
- So the **one reviewed place** is the root `package.json` `"dependenciesMeta": {"sqlite3": {"built": true}}`. `.yarnrc.yml` now says `enableScripts: false` explicitly (yarn 4.16's default is already false, `ac23-static`), so a change of yarn's default can't turn every script back on. `yarn.lock` records the setting on the root workspace entry (3 lines).
- Consequence: host and CI installs (`corepack yarn install --immutable`) now also build sqlite3, i.e. download its prebuilt N-API binding from GitHub releases. The host CLI now runs (`joplin version` on a temp profile works), which the M3 integration layer (real CLI profile) needs anyway. `keytar` and `sharp` stay unbuilt (`ac23-no-other-builds`).

### Image: `packages/headless/Containerfile`
- **Base:** `docker.io/library/node:22.23.3-bookworm-slim@sha256:43ac6c60…772c`, the OCI index digest (podman `RepoDigests`; the index lists linux/amd64, arm64, arm, ppc64le, …). `22.23.3-bookworm-slim` and `22-bookworm-slim` resolve to the same index today. Node 22 LTS per ADR-0009; ≥ 22.19 runs the supervisor's TypeScript by type stripping (checked: no warning on 22.23.3).
- **Install stage** (context = repository root, as the contract says):
  1. `COPY` the root `package.json`, `yarn.lock`, `.yarnrc.yml`, `packages/web-build/package.json` (yarn needs every workspace manifest to match the lockfile) and the whole `packages/headless/` (the NEG adds `test-fixtures/` there).
  2. `corepack yarn workspaces focus --production headless`: only the headless workspace's production tree, from the lockfile; install scripts off except the allow-list.
  3. **Immutable check.** `yarn workspaces focus` ignores immutability (scratch test: a new dependency was resolved and installed without a complaint), and `--immutable` can't be combined with `--mode=update-lockfile`. So the next step runs `corepack yarn install --mode=update-lockfile` (resolution only, no link, no builds) and fails the build if `yarn.lock` changed (`cmp` against the committed copy; scratch test: drift detected, clean tree unchanged). It runs **after** the focus install: with a cold project cache, `--mode=update-lockfile` fails on a `file:` dependency (`ENOENT` on its cache zip; found by `ac23-neg`, run 13). Then `rm -rf .yarn` (the project cache).
- **Final stage:** the same base; `COPY --from=install /app /app` (root-owned, so the runtime user can't modify code); `/data` created `1000:1000`, mode `0700`; `ENV NODE_ENV=production`; `USER 1000:1000` (the base's `node`); `WORKDIR /data`; `EXPOSE 8090`; `ENTRYPOINT ["node", "/app/packages/headless/bin/supervisor.ts"]`, `CMD []`. No `VOLUME` (no anonymous volumes), no `HEALTHCHECK` (compose supplies it, ADR-0006 amendment).
- **`.containerignore`** (repository root): `**/node_modules`, `.git`, `.yarn/cache`, `.yarn/install-state.gz`, results dirs, and the supervisor's unit tests and test fixture. It doesn't touch `packages/headless/test-fixtures/` (contract). The `web` image builds use their own context (`deploy/web`) and are unaffected.

### Supervisor: `packages/headless/{bin,src}`
- `bin/supervisor.ts`: resolves the CLI with `findPinnedCli` (the installed `joplin` must equal the exact version `packages/headless/package.json` pins, else exit 70), then `runSupervisor`. `SIGTERM`/`SIGINT` stop the children and exit 0.
- `src/config.ts`: `JOPLIN_SERVER_URL` (http/https, no credentials, query or fragment; trailing `/` removed), `JOPLIN_USERNAME`, and the two secret files with exactly one trailing `\n`/`\r\n` stripped. Errors name the variable or file, never a value (exit 64).
- `src/supervisor.ts`: creates `/data/profile` with mode `0700` (exit 73 if it can't), starts the health endpoint, then the strategy.
- `src/cliRunner.ts`: every CLI run is `node <bin> --profile /data/profile <command…>` as a **direct child**; input goes to a stdin pipe (Node uses a socketpair, which the watcher accepts as `socket:[…]`), never argv. The child environment is an allow-list (`PATH`, `HOME`, `TMPDIR`, `TZ`, `LANG`, `LC_ALL`, `NODE_ENV`, `NODE_OPTIONS`, `NODE_EXTRA_CA_CERTS`). Each output line is redacted, labelled (`[joplin sync] …`) and relayed to stdout. `stop()` = SIGTERM, then SIGKILL after a grace period.
- `src/redact.ts`: replaces the secrets and the current `api.token` (raw and JSON-escaped), drops query strings (`?a=b…` → `?[redacted]`) and masks any `token=` value.
- `src/syncStrategy.ts`: the ADR-0003 seam, M1 subset (`start`, `status`, `stop`; M3 adds `requestSync` and `withApi`).
- `src/stopTheWorldStrategy.ts`: the initial cycle: `config --import` (settings, secrets, a fresh `randomBytes(32)` hex `api.token`, `api.port` 41184, `locale` en_GB, on stdin) → sync target preflight → `sync` → judgement → `e2ee decrypt --force` (exit 0 required) → empty `log-clipper.txt` → `server start --quiet` → poll `http://127.0.0.1:41184/ping` for `JoplinClipperServer` (deadline 120 s; aborts if the server exits). A failed attempt is logged and retried after 30 s with the state left at `starting` (M3-AC1 replaces this with backoff and `degraded`). If `server start` exits after ready, the state drops to `starting` and the supervisor exits 1.
- `src/healthServer.ts`: `0.0.0.0:8090`, `GET`/`HEAD /healthz` only (`application/json; charset=utf-8`, `Cache-Control: no-store`), 405 for other methods, 404 for every other path. `lastSync` is the time the successful `sync` process ended (`Date#toISOString`).

### How sync success is detected (ADR gap, for the architect)
ADR-0003 doesn't say how the supervisor knows a `sync` worked, and the CLI doesn't tell it: QA found that `joplin sync` 3.7.1 exits 0 on failure, and with a target that refuses connections prints only `Completed: … (112s)` (upstream drops "retryable" network errors from the report: `packages/lib/Synchronizer.ts`, the `fetchRequestCanBeRetried` branch of the catch in `start()`; `command-sync.ts` never sets an exit code from the report).

Options considered (all must work with ADR-0003's command list, which `ac15` enforces):
- `sync.9.context` / `syncInfoCache` settings: written only on success, but they live in the profile's SQLite `settings` table (not `settings.json`); reading them means the CLI's internal DB schema or a `config <key>` CLI run outside the allowed list. Rejected (internals; and on a restart the old value is still there).
- The CLI's `log.txt`: internal message texts. Rejected.
- `e2ee decrypt --force` failing when no key was synced: true only for a fresh profile of an E2EE account. Kept as a separate requirement, not as the sync signal.

**Chosen, behind the `SyncStrategy` (`src/syncOutcome.ts`), failing closed:**
1. the sync target's public `GET <JOPLIN_SERVER_URL>/api/ping` answers `{"status":"ok"}` right before the sync (otherwise no sync is started at all) and right after it;
2. `sync` exits 0;
3. its output has the report's `Completed:` line and no `Last error:` line. The profile's `locale` is set to `en_GB` by the import so the strings don't depend on `LANG`.

Interfaces this adds to ADR-0003's "Upgrade impact" list: the Joplin Server `GET /api/ping` response, the `Completed:`/`Last error:` report lines of `joplin sync`, and the `locale` setting. If a CLI bump changes the report text, the supervisor never becomes ready and the M1-S5 contract suite fails on the bump (fail-safe, not silent).

**Residual gap:** a target that drops out and comes back strictly within the sync window (retryable errors swallowed, pings fine before and after). The next sync (M3 loop) repairs the data; the initial `ready` could be early in that window. **Upstream-first:** `joplin sync` should exit non-zero (or print the error) when the sync failed, including retryable network errors; that would replace rules 1 and 3. To be filed upstream by the orchestrator/architect (I can't open issues: no `gh`, no push).

## Upstream-first notes
- **No `patches/`, no upstream source copied.** Upstream is consumed as the npm `joplin@3.7.1` package from `yarn.lock` and its public commands only.
- **Shim 1, the sync-success judgement** (`src/syncOutcome.ts`): exists because `joplin sync` exits 0 on failure (see above). Upstream-first: non-zero exit status from `joplin sync` on any failed sync.
- **Shim 2, the supervisor itself** is ADR-0003's documented shim; its upstream-first fix (a CLI daemon mode with sync, decrypt and indexing while serving, an `api.bindHost` setting and header token auth) is recorded in ADR-0003 Alternatives. Nothing new.

## ADR deviations
None. Within the ADRs:
- ADR-0003's `SyncStrategy` interface is delivered as the M1 subset (`start`, `status`, `stop`); `requestSync` and `withApi` come with the M3 cycle loop. Incremental, not a change.
- ADR-0009 A1 says `data-api-client` is created "in M1-S5 (the internal REST client) or else M3". Not created: the supervisor only needs `GET /ping`, and the test plan reaches the Data API with QA's own in-container probe. M3 (queueing, `withApi`) is the first real consumer.
- `api.token` rotation per cycle, `/status`, crash backoff and `degraded` are M3 (test plan §Out of scope). The token is fresh on every container start, and `log-clipper.txt` is emptied before every `server start` (ADR-0008).
