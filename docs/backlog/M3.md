# M3: Headless Data API service

**Goal:** the `headless` container keeps a CLI profile in sync with the user's Joplin Server, decrypts E2EE data, keeps search fresh and serves the REST Data API to MCP. It optionally serves an authenticated gateway to LAN clients. It does all this without clobbering settings, without leaking secrets, and with egress limited to the Joplin Server.

Owners: **SE** = senior-engineer, **QA** = qa-specialist. QA writes the failing tests first. ADRs: 0003, 0005, 0006, 0008.

Order: S1 → S2 → S3 → S4 → S5 → (S6, S7, S8, S9).

---

## M3-S1: Supervisor process manager
- **Owner:** SE · **Size:** M · **Depends on:** M1-S5

**Acceptance criteria:**
- **M3-AC1:** The supervisor state machine (`starting → syncing → serving ⇄ cycling → stopping`, plus `degraded`) is unit-tested with fake timers. *(unit)*
  - Transitions, crash restart with exponential backoff (1 s → 60 s cap) and graceful shutdown (SIGTERM → stop the CLI server → exit 0 within 10 s) all behave as specified.
  - **NEG:** a CLI that crashes 5 times in 2 minutes puts the supervisor in `degraded` with `/healthz` 503. It does not loop forever.
- **M3-AC2:** On SIGTERM from podman, the supervisor stops the CLI child cleanly, with no orphan or zombie (`Z` state) `joplin` process (checked through `/proc`), and the profile opens cleanly on the next start (`joplin version` exits 0). *(integration)*
  - The image runs with a reaping init (S3 zombie finding).
  - **NEG:** a cycle against a fixture child that exits immediately completes and doesn't hang in "stop".

## M3-S2: `SyncStrategy`: stop-the-world default
- **Owner:** SE · **Size:** L · **Depends on:** M3-S1

**Acceptance criteria:**
- **M3-AC3:** One cycle runs strictly in this order:
  1. take the mutex
  2. drain in-flight Data API requests (bounded wait)
  3. stop `server start`
  4. `joplin sync`
  5. `joplin e2ee decrypt --force`
  6. `server start --quiet` with a new token
  7. wait for `/ping`
  8. release the mutex

  Cycles are triggered by a timer (`SYNC_INTERVAL`, default 300 s), by a debounce after writes (default 30 s) and by `sync_now`. Concurrent triggers coalesce into one cycle. *(unit with fake timers + integration with the real CLI)*
- **M3-AC4:** Data API, gateway and MCP requests that arrive during a cycle are **queued** (not failed) and complete after it, up to `CYCLE_QUEUE_TIMEOUT` (default 60 s); after that they return 503 with `Retry-After`. *(contract)*
  - Measured on the Pi with the S3 fixture (small delta): the p95 outage per cycle is **≤ 34 s**, which is 2 × the S3 median of ~16.6 s. No queued request is lost.
  - **NEG:** with `CYCLE_QUEUE_TIMEOUT=1s` and an artificially slow sync, queued requests get 503 with `Retry-After`.

## M3-S3: E2EE decrypt and search freshness
- **Owner:** SE · **Size:** M · **Depends on:** M3-S2

**Acceptance criteria:**
- **M3-AC5:** After one cycle, notes, notebooks, tags and attachments created on another E2EE device are returned **decrypted** by the REST API, and attachments have their files (`GET /resources/:id/file` returns the original bytes). *(contract)*
  - A note written through the REST API is stored **encrypted** on the server after the next cycle (server item content has `encryption_applied: 1`).
  - **NEG:** with a wrong master password secret, items stay encrypted, `/healthz` reports `degraded: e2ee-password`, and the supervisor neither crash-loops nor logs the password.
- **M3-AC6:** A note synced from another device in cycle N is found by `GET /search?query=<unique word>` once `/status.searchReady` is true after cycle N (≤ 15 s after `/ping`; S3 measured ~10 s from upstream's `scheduleSyncTables` timer). MCP `search_notes` calls made before then wait for readiness. A note created through REST before cycle N is found after cycle N. *(contract)*
  - **NEG** (documents limitation L6): between cycles, a REST-created note is not yet found by search, because the CLI in command mode doesn't index. The test asserts the current behaviour so that an upstream change is noticed.

## M3-S4: Secrets, configuration, token rotation, redaction
- **Owner:** SE · **Size:** M · **Depends on:** M3-S1 · **ADR:** 0008

**Acceptance criteria:**
- **M3-AC7:** Secrets are read from `/run/secrets/*` and applied with `config --import` on stdin. *(integration)*
  - No secret value appears in any `/proc/*/cmdline` or `/proc/*/environ` in the container, in the supervisor's stdout/stderr, or in the image layers.
  - Plaintext secrets exist only in the profile DB (an upstream limitation), and the profile directory is mode `0700`.
  - **NEG:** a planted marker passed in argv is found by the same probe.
- **M3-AC8:** Each CLI start uses a fresh random `api.token` (32 bytes). *(integration)*
  - Every line relayed from the CLI and from `log-clipper.txt` has `token=` values redacted, and `log-clipper.txt` is truncated at each start.
  - **NEG:** the previous token is rejected (403) after a restart.

## M3-S5: Health and status endpoints
- **Owner:** SE · **Size:** S · **Depends on:** M3-S2

**Acceptance criteria:**
- **M3-AC9:** `/healthz` (liveness/readiness) and `/status` work as follows: *(integration)*
  - `/status` returns `{state, cliVersion, syncVersion, searchReady, lastSync:{startedAt,finishedAt,result,error?}, nextSyncAt, queuedRequests, outageMsP50, outageMsP95}`.
  - Both require no auth on the backend network and **are not** published by `web`, unless the user explicitly opts in.
  - The supervisor refuses to start (exit code 3, clear message) if the CLI's `syncVersion` differs from `upstream/joplin-version.json` (ADR-0005).
  - **NEG:** a fixture pin with `syncVersion: 4` triggers the refusal.

## M3-S6: Data API gateway (opt-in)
- **Owner:** SE · **Size:** L · **Depends on:** M3-S2, M3-S4 · **ADRs:** 0003, 0008

**Acceptance criteria:**
- **M3-AC11:** With `DATA_API_GATEWAY=true`, `web` publishes `/api/*` → supervisor → CLI `127.0.0.1:41184`. *(contract)*
  - Clients authenticate with the **gateway token** as `Authorization: Bearer` or as `?token=` (for compatibility with existing Data API clients). The supervisor swaps it for the internal token.
  - Response bodies and status codes equal a direct call (the `rest-shape` snapshots are shared).
  - **NEG:** the internal `api.token` sent by a client is rejected (403). A missing or wrong gateway token gets 403.
- **M3-AC12:** The gateway rejects `POST /notes` whose body, `body_html`, `image_data_url` or `base_url` references `file:` (400, with the reason). It accepts the same note without that reference. `GATEWAY_ALLOW_FILE_URLS=true` disables the check. *(contract)*
  - **NEG:** with the check disabled, the upstream behaviour (the file is attached) is observed with a harmless fixture file. This proves the guard is what blocks it.
- **M3-AC13:** Gateway access logs contain no token values (redaction test with a known token). *(contract)*

## M3-S7: Profile snapshots and version guard
- **Owner:** SE · **Size:** M · **Depends on:** M3-S1 · **ADR:** 0005

**Acceptance criteria:**
- **M3-AC14:** When the CLI version differs from the one recorded in `/data/profile-version.json`, the supervisor writes `/data/snapshots/profile-<old>-<ts>.tar.zst` before starting, and keeps the last 3. Restoring a snapshot with the documented command gives a profile that the old image opens and syncs. *(integration)*

## M3-S8: Conflicts and settings integrity
- **Owner:** QA · **Size:** M · **Depends on:** M3-S2

**Acceptance criteria:**
- **M3-AC15:** The same note is edited through headless REST and on another device between two syncs. *(contract)*
  - After both sync, upstream's conflict handling applies: one version wins, and the other is kept as a conflict note (`is_conflict=1`, visible via `include_conflicts=1`) on both sides.
  - Neither edit is lost (data assertion on both texts).
- **M3-AC16:** After 20 cycles: *(contract)*
  - `settings.json` differs from its initial content only in keys the supervisor sets on purpose (`api.token`).
  - `mcp.enabled` and the `ai.tool.*` settings are unchanged.
  - `sync.9.path` and the username are unchanged.
  - **NEG:** the documented anti-pattern (running `joplin sync` in parallel with a live `server start`) is shown by the test to change or lose settings, or to fail on the sync lock. This justifies the mutex.

## M3-S9: Egress confinement
- **Owner:** SE · **Size:** S · **Depends on:** M1-S4, M1-S5 · **ADR:** 0006

**Acceptance criteria:**
- **M3-AC10:** From inside `headless`: *(contract)*
  - `curl https://example.com` and `curl http://<LAN host>` fail.
  - `GET http://web:8089/joplin-server/api/ping` succeeds (positive control).
  - A note body with `![](https://<test-http-server>/x.png)` sent through the **un-guarded** upstream `POST /notes` (test-only bypass) doesn't reach the test HTTP server (its request log stays empty).
