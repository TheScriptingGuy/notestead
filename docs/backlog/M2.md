# M2: Web app

**Goal:** the upstream web UI, served by our `web` container and synced through our proxy, is covered end to end. It covers what the user does daily: sync, E2EE unlock, notes, notebooks, tags, to-dos with due dates, search, attachments, trash, plugins, offline use and upgrades. Every UI assertion is paired with a data assertion through the headless Data API.

**Conventions:**
- Owners: **SE** = senior-engineer, **QA** = qa-specialist, **CI** = ci-cd-specialist. QA writes the failing tests first.
- Layers: E2E = Playwright against the `web` container, with `joplinServer`, `headless` and `e2eeAccount` fixtures. `NEG:` marks the negative control.
- Most M2 stories add tests over unmodified upstream behaviour. SE work is limited to the `web` image, the overlay and the proxy. A test that fails because of an *upstream* bug is reported to the orchestrator, which records it under Known limitations or files it upstream. The test is never weakened.

Order: S1 → S2 → S3 → S6 → (S4, S5, S7, S8, S9, S10).

## M2-S1: Sync through the proxy and E2EE unlock
- **Owner:** QA (+SE for fixes in `web`) · **Size:** M · **Depends on:** M1 · **ADRs:** 0001, 0002

**Acceptance criteria:**
- **M2-AC1:** In a fresh browser context, the user configures the Joplin Server target with URL `<origin>/joplin-server` and the test user's credentials. "Check synchronisation configuration" succeeds, and a full sync completes. *(E2E)*
  - The network log shows only same-origin requests to `/joplin-server/api/*`. The single known exception is upstream's `HEAD https://joplinapp.org/connection_check/` (L15, S4); any other cross-origin request fails the test.
  - The server's `info.json` `version` is still `3` afterwards (data assertion through the server API).
- **M2-AC2:** For an `e2eeAccount`, the app reports encrypted items. After the master password is entered, every seeded note title and body is shown decrypted. *(E2E)*
  - A data assertion compares them with the seed through the headless REST API.
  - **NEG:** a wrong master password leaves the items encrypted and shows upstream's error. Nothing is decrypted.

## M2-S2: Notes, notebooks, tags and to-dos
- **Owner:** QA · **Size:** L · **Depends on:** M2-S1 · **ADRs:** 0001

**Acceptance criteria:**
- **M2-AC3:** Creating, editing (typed like a user), moving and deleting (to trash) a note in the web UI is reflected exactly in the headless REST Data API after one web sync and one headless sync (`expect.poll`). This covers title, body, `parent_id` and `deleted_time`. *(E2E)*
- **M2-AC4:** Notebook create/rename/nest and tag add/remove/rename in the web UI are reflected in the REST API (`/folders`, `/tags`, `/tags/:id/notes`). *(E2E)*
- **M2-AC5:** A to-do created in the web UI with a due date has the right `is_todo` and `todo_due` in the REST API, with the timezone handled: the browser context timezone is `Europe/Amsterdam`, and the assertion is on the epoch value. *(E2E)*
  - Marking it done sets `todo_completed > 0`.
  - **NEG:** the web UI shows no notification at the due time. This documents limitation L1, verified by asserting that no `Notification` was constructed (an init script spies on `window.Notification`).

## M2-S3: Search, attachments, trash
- **Owner:** QA · **Size:** M · **Depends on:** M2-S2

**Acceptance criteria:**
- **M2-AC6:** A note created through the headless API with a unique word is found by the web UI search after both sides sync. *(E2E)*
  - **NEG:** a word that appears in no note returns no results.
- **M2-AC7:** Attachments.
  - A 5 MiB image and a 100 MiB binary attached in the web UI are uploaded through the proxy. Their sha256 read back through `GET /resources/:id/file` on the headless API is equal. *(E2E)*
  - An attachment added through the headless API is viewable or downloadable in the web UI. *(E2E)*
- **M2-AC8:** A note deleted in the web UI appears in the web trash and in `GET /notes?include_deleted=1` with `deleted_time > 0`. After restoring it in the web UI, `deleted_time` is 0 in the REST API. *(E2E)*

## M2-S4: Plugins (repository and `.jpl`), including repeating-todos
- **Owner:** QA · **Size:** M · **Depends on:** M2-S1 · **ADRs:** 0001

**Acceptance criteria:**
- **M2-AC9:** With plugin support enabled in settings, uploading the user's repeating-todos plugin `.jpl` (pinned release, a fixture in `tests/fixtures/plugins/`) installs and enables it, and it survives a reload. Its core behaviour works on web. *(E2E)*
  - The behaviour is defined with the user at the start of the story, for example: completing a repeating to-do creates or reschedules the next occurrence, with a data assertion through REST.
  - **NEG 1:** the plugin's `views.menus` entry is absent on web. This is documented limitation L2, and the test asserts the absence so that a future upstream change is noticed.
  - **NEG 2:** a desktop-only fixture plugin (`platforms: ["desktop"]`) is refused or marked incompatible.
- **M2-AC10:** Installing a plugin from the official repository works. *(E2E, tagged `@network`; runs nightly and on bump PRs, not on every commit, because it needs internet access to github.com/raw.githubusercontent.com)*

## M2-S5: Offline reload and bundle upgrade
- **Owner:** QA + SE · **Size:** M · **Depends on:** M2-S1 · **ADRs:** 0001, 0005

**Acceptance criteria:**
- **M2-AC15:** After a successful load and sync, setting the context offline and reloading opens the app from the service-worker cache, with the notes readable from OPFS. *(E2E)*
  - Going back online, an edit made offline syncs (data assertion through REST).
- **M2-AC16:** Upgrade: the app is loaded with bundle A and synced. Then the `web` container is redeployed with bundle B (the next pin, or a fixture rebuilt with a changed `bundle-manifest.json`). One online reload serves bundle B (network-first service worker), the local profile opens and the data is intact. *(E2E)*
  - **NEG:** downgrading to an older bundle whose database version is lower shows upstream's "profile is newer" refusal. The rollback runbook's "clear site data and re-sync" step then recovers all synced data. Verified by data comparison.

## M2-S6: Branding overlay and source offer
- **Owner:** SE · **Size:** M · **Depends on:** M1-S2 · **ADRs:** 0010

**Acceptance criteria:**
- **M2-AC11:** The served `manifest.json` name, the page `<title>` and every icon come from our overlay. No served file matches an upstream icon hash. *(E2E + unit)*
- **M2-AC12:** `/source.html` (also linked from the overlay's "Source" link, which is reachable by keyboard and has an accessible name) states the upstream repo and exact commit, our repo and exact commit, and links the licences. *(E2E)*
- **M2-AC13:** On an origin containing "localhost", the served bundle runs with `__DEV__ === false`. *(E2E)*
  - **NEG:** the un-overlaid bundle on the same origin has `__DEV__ === true`, which proves the test can see the difference.

## M2-S7: Cross-origin isolation modes and browser matrix
- **Owner:** QA · **Size:** M · **Depends on:** M2-S1 · **ADRs:** 0001, 0006

**Acceptance criteria:**
- **M2-AC17:** With `COEP=credentialless` and with `COEP=require-corp`, `crossOriginIsolated === true`, the OPFS-backed database opens and a sync succeeds in Chromium. *(E2E, both modes)*
  - The test asserts the **effective** policy after the upstream service worker takes control. The service worker rewrites COEP itself (`credentialless` unless it degrades), so the server header only governs the first load (S4).
  - A note body with an external `https:` image renders the image under `credentialless`.
  - Under `require-corp`, the image is blocked unless it carries CORP. The behaviour is documented and the default stays `credentialless`.
- **M2-AC18:** A Firefox smoke test (load, sync, open a note) runs in CI if Firefox is available on the runner. Safari is a documented manual checklist. *(E2E/manual)*

## M2-S8: Published-note links
- **Owner:** QA · **Size:** S · **Depends on:** M2-S1 · **ADRs:** 0002

**Acceptance criteria:**
- **M2-AC14:** Publishing a note from the web UI produces a link under `<origin>/joplin-server/shares/<id>`. Following it gives a 302 to `JOPLIN_SERVER_PUBLIC_URL/shares/<id>`, and the server renders the note there. *(E2E + contract)*
  - **NEG:** the app origin never returns the note's HTML: `GET <origin>/joplin-server/shares/<id>` without following redirects has no body content from the note.
