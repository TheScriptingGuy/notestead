# M2: Web app

**Goal:** the upstream web UI, served by our `web` container and synced through our proxy, is covered end to end. It covers what the user does daily: sync, E2EE unlock, notes, notebooks, tags, to-dos with due dates, search, attachments, trash, plugins, offline use and upgrades. Every UI assertion is paired with a data assertion through the headless Data API.

**Conventions:**
- Owners: **SE** = senior-engineer, **QA** = qa-specialist, **CI** = ci-cd-specialist. QA writes the failing tests first.
- Layers: E2E = Playwright against the `web` container, with `joplinServer`, `headless` and `e2eeAccount` fixtures. `NEG:` marks the negative control.
- Most M2 stories add tests over unmodified upstream behaviour. SE work is limited to the `web` image, the overlay and the proxy. A test that fails because of an *upstream* bug is reported to the orchestrator, which records it under Known limitations or files it upstream. The test is never weakened.

Order: S1 → S2 → S3 → S6 → (S4, S5, S7, S8, S9, S10).

## M2-S1: Sync through the proxy and E2EE unlock
- **Owner:** QA (+SE for fixes in `web`) · **Size:** M · **Depends on:** M1 · **ADRs:** 0001, 0002

**Acceptance criteria:**
- **M2-AC1:** In a fresh browser context, the user configures the Joplin Server target with URL `<origin>/joplin-server` and the test user's credentials. "Check synchronisation configuration" succeeds, and a full sync completes. *(E2E)*
  - The network log shows only same-origin requests to `/joplin-server/api/*`. The single known exception is upstream's `HEAD https://joplinapp.org/connection_check/` (L15, S4); any other cross-origin request fails the test.
  - The server's `info.json` `version` is still `3` afterwards (data assertion through the server API).
- **M2-AC2:** For an `e2eeAccount`, the app reports that the account's data is end-to-end encrypted and asks for the master password: the decryption banner shows, and the encryption screen shows encryption enabled with the account's master key (the `info.json` `activeMasterKeyId`) not unlocked. No seeded content is readable in the app, and the server's copies are all encrypted (`encryption_applied: 1`). After the master password is entered, every seeded note title and body is shown decrypted. *(E2E + data assertion)*
  - A data assertion compares them with the seed through the headless REST API, before and after one headless sync (no conflict copy; `info.json` stays version 3 with E2EE on).
  - **NEG:** a wrong master password shows upstream's error, and no seeded item becomes readable: none of its text reaches the page or the web app's local profile (OPFS), and the server's copies are unchanged (byte-identical, none added or removed).
  - *Why not "the app lists encrypted items" (amended 2026-10-21, M2-S1 F5/D1):* before the master password a fresh web profile downloads **no** item, so there are no encrypted placeholders to count. Its first sync aborts while uploading its own welcome notes, which it can't encrypt yet (limitation L18, linked to L14).

## M2-S2: Notes, notebooks, tags and to-dos
- **Owner:** QA · **Size:** L · **Depends on:** M2-S1 · **ADRs:** 0001

**Acceptance criteria:**
- **M2-AC3:** Creating, editing (typed like a user), moving and deleting (to trash) a note in the web UI is reflected exactly in the headless REST Data API after one web sync and one headless sync (`expect.poll`). This covers title, body, `parent_id` and `deleted_time`. *(E2E)*
- **M2-AC4:** Notebook create/rename/nest and tag add/remove/rename in the web UI are reflected in the REST API (`/folders`, `/tags`, `/tags/:id/notes`). *(E2E)*
- **M2-AC5:** A to-do created in the web UI with a due date has the right `is_todo` and `todo_due` in the REST API, with the timezone handled: the browser context timezone is `Europe/Amsterdam`, and the assertion is on the epoch value. *(E2E)*
  - Marking it done sets `todo_completed > 0`.
  - **NEG:** the web UI shows no notification at the due time. This documents limitation L1, verified by asserting that no `Notification` was constructed (an init script spies on `window.Notification`).

## M2-S5: Offline reload and bundle upgrade
- **Owner:** QA + SE · **Size:** M · **Depends on:** M2-S1 · **ADRs:** 0001, 0005

**Acceptance criteria:**
- **M2-AC15:** After a successful load and sync, setting the context offline and reloading opens the app from the service-worker cache, with the notes readable from OPFS. *(E2E)*
  - Going back online, an edit made offline syncs (data assertion through REST).
- **M2-AC16:** Upgrade: the app is loaded with bundle A and synced. Then the `web` container is redeployed with bundle B (the next pin, or a fixture rebuilt with a changed `bundle-manifest.json`). One online reload serves bundle B (network-first service worker), the local profile opens and the data is intact. *(E2E)*
  - **NEG:** downgrading to an older bundle whose database version is lower shows upstream's "profile is newer" refusal. The rollback runbook's "clear site data and re-sync" step then recovers all synced data. Verified by data comparison.

## Cross-cutting: proxy DNS reliability in CI (found during M2)
These stories came out of the CI-M2-S2 fix-forward (`docs/test-plans/CI-M2-S2-x64-arm64.md`, finding I). They touch the `web` proxy (ADR-0002) and the CI environment (ADR-0006, ADR-0007), not a single M2 feature, so they sit here and keep their own IDs.

### DNS-1: the web proxy intermittently fails to resolve `server` (502)
- **Owner:** SE (`deploy/web/**`) + QA (harness) · **Size:** M · **Depends on:** M1-S4 · **ADRs:** 0002, 0007
- **Plan and evidence:** `docs/test-plans/DNS-1.md` (the ACs as proposed, the "Amendment after DNS-1-r1", and "Results (CI, proof run 5 …)": e2e run 40102184409, head `2cc2932`); `docs/worklog/DNS-1.md`.
- **The fix:** `transport http { dial_timeout 10s }` in the `(joplin_server_proxy)` snippet of `deploy/web/Caddyfile`. Go's resolver waits 5 s per `resolv.conf` nameserver, and Caddy's default 3 s dial timeout turned one silent first nameserver into a 502.
- **Scope decision (user, 2026-10-25): re-scope and merge** (option B of the proof run 5 results). DNS1-AC5 is split. AC5a stays here; AC5b moves to DNS-2. DNS-1 is done on AC1 to AC4 plus AC5a, and CI-M2-S2 and DNS-1 merge to `main` together.

**Acceptance criteria:**
- **DNS1-AC1:** A proxied request survives a first nameserver that never answers. Through `web`'s public listener (`:8080`) and its internal listener (`:8089`, the headless sync path), with a `resolv.conf` whose first nameserver is silent and whose next one is the network's real DNS, `GET /joplin-server/api/ping` returns 200 `{"status":"ok"}` within **9 s**, and `web` logs no proxy error for it. *(contract: `dns1-c0`, `dns1-c1`, `dns1-c1b`)*
  - **NEG:** `dns1-c1-neg`, the same fault with Caddy's default dial timeout, gets a 502 at about 3 s.
- **DNS1-AC2:** No regression for POST and PUT under the same fault. A login (`POST /joplin-server/api/sessions`) that is the first upstream request of a fresh `web` returns the server's 200 and a session. A sync upload (`PUT /joplin-server/api/items/root:/<name>:/content`) made with that session lands on the server **exactly once** with the exact bytes, checked on the server directly, not through the proxy. *(contract: `dns1-c2`, `dns1-c2b`)*
  - **NEG:** `dns1-c2-neg`, the same first POST without the fix, gets a 502, and the server's item list is unchanged.
- **DNS1-AC3:** A genuinely unreachable server still fails, boundedly and clearly. For "name does not exist", "connection refused", "address with no host" and "every nameserver silent", the proxied request ends with **502 or 504 within 15 s** (no hang, no 200), and `web` logs an error line for it. *(contract guards: `dns1-c3a` to `dns1-c3d`; the bound is the negative control)*
- **DNS1-AC4:** The E2EE test device fails fast and loudly when its seed sync fails (harness hardening, QA-owned). A seed sync that reports `Last error` makes the device exit non-zero within 150 s, with no `RESULT` line, and names the error. The stack harness also checks on the server that the seed uploaded a master key before it hands the account to a test. *(contract + unit: `dev1-c1`, `dev1-neg`, `dev1-u1`)*
- **DNS1-AC5a:** The single-silent-nameserver failure is gone in CI. In an e2e run that contains the fix, on both `ubuntu-24.04` (x64) and `ubuntu-24.04-arm` (arm64), the DNS-1 file set has **0** `lookup server … i/o timeout` lines with a duration under 9 s (this includes the old 2.5 to 4.5 s signature), and **0** device logs with `Last error` apart from the deliberate `device-dev1-neg.log`. Every other `lookup server` line is listed with its duration. *(CI evidence: `dns1-c5`, `scan-proxy-dns.ts`; unit: `dns1-u5`)*
  - **NEG:** the scan, run over the five pre-fix runs, reproduces their 225 old-signature lines.
  - **PASS** in proof run 5 on both runners: 0 lines at about 3 s, and none between 3 and 10 s.
- **DNS1-AC5b: moved to DNS-2 (user decision, 2026-10-25).** As written, it said "no proxy lookup failure in CI at all": 0 `lookup server … i/o timeout` lines of any duration on both runners. Proof run 5 **failed** it, with 2 lines on x64 and 3 on arm64, all at 10.0 s. Both aardvark gateways were silent, which is a different mechanism that the dial timeout can't cover within AC3's 15 s. It is DNS2-AC4 now.

### DNS-2: aardvark-dns stalls on the CI runners' podman 4.9.3 (both nameservers silent for 10 s or more)
- **Owner:** SE, with the ci-cd-specialist (runner evidence) and QA (probe, scan) · **Size:** M (investigation first; the fix part is sized after DNS2-AC3) · **Depends on:** DNS-1 and CI-M2-S2 merged to `main` · **ADRs:** 0002, 0006, 0007
- **Goal:** explain and remove the remaining proxy lookup failures in CI. After the DNS-1 fix, every remaining failure is a `lookup server` timeout at **10.0 s**. So both nameservers of `web`'s `resolv.conf` were silent back to back, and both are served by one aardvark-dns process. All five failures in proof run 5 were the **first** request of a headless container that had just joined `back`. That fits the hypothesis "aardvark on podman 4.9.3 stalls when a container joins a network", which is not proven yet. The Pi (podman 5.4.2, aardvark-dns 1.14.0) has never shown it.
- **The rule while DNS-2 is open, and after it:**
  - The 10 s lines stay **visible** in every scan, on every run and both runners, each listed with its duration.
  - **No allowance:** no tie rule, no exclusion and no retry-until-green covers a `lookup server` line.
  - A test failure with a `lookup server` line in its window is a FAIL, and it goes to the planner.

**Acceptance criteria (investigation first: AC1 and AC2 come before any mitigation):**
- **DNS2-AC1:** Runner evidence (ci-cd proposal P1, read-only). Before the tests start, `e2e.yml` logs on both runners:
  - `podman version`;
  - `podman info --format '{{json .Host.NetworkBackendInfo}}'`, which gives the netavark and aardvark-dns versions and paths;
  - `dpkg-query -W podman netavark aardvark-dns`;
  - one throwaway container's `/etc/resolv.conf`.

  The step changes no configuration: it writes no `containers.conf` and installs nothing. *(acceptance, static: the step exists and has no write or install command; CI evidence: the values for both runners recorded in the DNS-2 test plan)*
- **DNS2-AC2:** A DNS probe tells whether a stall follows a container start. A QA `dns-watch` container on `front` and `back` in the e2e stack resolves `server` every 0.5 s, separately against each nameserver in its `resolv.conf`, with the Go resolver (the one Caddy uses). It logs each lookup's duration and result. The harness logs `podman events` container starts and network connects on the same clock. A tool joins the two logs into one timeline and reports, for each stall of 1 s or more, the nearest container event before it. *(unit: the timeline join on fixed samples; contract: the probe sees a planted stall; CI evidence: at least two e2e runs per runner)*
  - **NEG:** in a contract test, a planted silent nameserver (DNS-1's sink) shows up as a stall in the probe log, and a run with no fault shows none.
  - **The outcome is a written finding** in the DNS-2 test plan: the hypothesis confirmed or refuted, per runner, with the timeline excerpts.
- **DNS2-AC3:** A mitigation is chosen from the AC2 evidence, and its trade-off is recorded before any implementation. The candidates are below. A choice that changes DNS1-AC3's 15 s cap needs an ADR-0002 amendment with the new bound, approved before work starts. *(review: the architect records the decision; the lead checks it)*
- **DNS2-AC4 (was DNS1-AC5b):** No proxy lookup failure in CI. Each of **three consecutive** e2e runs on `main` with the mitigation, on both runners, has:
  - 0 `lookup server … i/o timeout` lines **of any duration**;
  - 0 Caddy `dial tcp` 502/504 lines outside the tests that stop `server` on purpose, each named in the results;
  - 0 device logs with `Last error` apart from `device-dev1-neg.log`.

  It uses DNS-1's amended file set and rule. Three runs, because one run doesn't prove a reduction: before the fix, runs had anywhere from 5 to 92 lines. *(CI evidence: `scan-proxy-dns.ts`)*
  - **NEG:** the scan still reports the five 10 s lines of proof run 5 (e2e 40102184409).
- **DNS2-AC5:** No regression of DNS-1's guarantees. DNS1-AC1 to AC4 stay green, and the bound in force for "a dead server fails" holds: 15 s, or the bound set by the ADR-0002 amendment of DNS2-AC3. A POST whose lookup failed is still never applied twice (`dns1-c2`'s exactly-once check). *(contract: `tests/contract/dns-1`)*

**Mitigations to weigh in DNS2-AC3** (from the proof run 5 results, option 4):
- **Caddy dial retries** (`lb_try_duration` / `lb_try_interval` on the proxy). These are safe for POST, because a failed lookup means nothing was sent. But a dead server is then reported only after the try duration, which **means revisiting DNS1-AC3's 15 s cap**. To cover a stall of 10 s or more, the cap has to grow, and every real outage gets slower for users.
- **A faster first retry in the headless supervisor's readiness and sync loop** (DNS-1 worklog follow-up d). Today every transient 502 costs about 30 s plus the dial. This shrinks the visible window and the test time. It does not stop the 502, and it does not help the browser path.
- **A newer aardvark-dns on the runner** (ci-cd P4). The Ubuntu 24.04 archive doesn't have one for podman 4.9.3. A source or PPA install is a supply-chain change that needs hash pinning, and it changes the environment under test. The CNI experiment (P3) is for diagnosis only, not a fix.
- **Already rejected in DNS-1:**
  - a longer `dial_timeout`, because it only helps stalls of 10 to 15 s and conflicts with AC3;
  - `dns_opt timeout:1`, because a stall of the shared aardvark silences both gateways.

  `dns_opt` stays an M5 compose option for users.
