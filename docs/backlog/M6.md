# M6: Upgrade automation

**Goal:** new upstream Joplin releases within the pinned minor reach the user as reviewed, fully tested bump PRs, never as silent drift. Minor upgrades are a deliberate, user-approved step (ADR-0005).

Owners: **CI** = ci-cd-specialist, **SE** = senior-engineer, **QA** = qa-specialist, **A** = architect.

---

## M6-S1: Upstream watcher and bump PR
- **Owner:** CI · **Size:** M · **Depends on:** M1-S3 · **ADRs:** 0005

**Acceptance criteria:**
- **M6-AC1:** A scheduled `upstream-bump.yml` (daily) detects, **within the pinned minor**:
  - a new `release-<minor>` head commit and the newest tag on it
  - a new npm `joplin` version
  - a new `joplin/server` tag

  It opens one PR that updates `upstream/joplin-version.json` and `yarn.lock`, and lists the equivalent `android-v*` tag and the upstream changelog links. *(unit: detection logic against recorded fixtures of `git ls-remote`, the npm registry and Docker Hub responses)*
  - **NEG:** a fixture with only a new minor (`release-3.8`) opens **no** patch PR. Instead it opens an issue "minor upgrade available, needs user decision".

## M6-S2: Bump PR gates
- **Owner:** CI (workflow) + SE (check scripts) + QA (suites) · **Size:** L · **Depends on:** M6-S1, M1–M4 suites · **ADRs:** 0005, 0007

**Acceptance criteria:**
- **M6-AC2:** A bump PR fails when the `syncVersion` read from the new web ref (`packages/lib/models/Setting.ts`) or from the CLI's installed `@joplin/lib` differs from the pin's `syncVersion`. *(contract)*
  - **NEG:** a fixture bump with `syncVersion: 4` fails with a message pointing at ADR-0005.
- **M6-AC3:** A bump PR runs the full suite on x64 and arm64: lint, unit, integration, contract (`proxy`, `rest-shape`, `mcp-upstream`, `headless`) and E2E. It posts the `rest-shape` and `mcp-upstream` snapshot diffs in the PR body. *(CI)*
- **M6-AC4:** If `patches/` is non-empty, every patch must apply cleanly to the new ref, otherwise the PR fails. *(contract)*
  - **NEG:** a fixture patch that no longer applies fails, naming the patch.
- **M6-AC5:** The overlay's expected-file check (M1-AC6) runs on the newly built bundle, so a renamed upstream static file fails the PR. *(integration)*

## M6-S3: Minor upgrade procedure
- **Owner:** A (ADR amendment) + U (decision) · **Size:** S · **Depends on:** M6-S1

**Acceptance criteria:**
- **M6-AC6:** `docs/architecture/upgrade-minor.md` describes the steps for a minor upgrade: *(review)*
  1. the user confirms that their server and clients are on the new minor
  2. an ADR-0005 amendment
  3. a compatibility-matrix update (S5 format)
  4. a bump PR with all gates
  5. a release with a note about browser and headless profile migration (one-way) and backup steps, versioned as our **MAJOR** (MINOR while 0.x) and moving the floating `joplin<new minor>` tag, while `joplin<old minor>` stays on the last release for the old minor (D7, gate 1; ADR-0006, checked by M5-AC12)

## M6-S4: Upstream-first ledger
- **Owner:** A · **Size:** S · **Depends on:** none

**Acceptance criteria:**
- **M6-AC7:** `docs/architecture/upstream-first.md` lists every local shim with its proposed upstream change, the issue or PR link (once the user approves filing it), and the test that will tell us when the shim can be removed. *(review)*
  - The list is from ARCHITECTURE.md §10.
  - Each bump PR template asks "did any upstream-first item land?"
