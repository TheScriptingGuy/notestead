# M5: Release (public delivery)

**Goal:** trustworthy, versioned, multi-arch artifacts that anyone can run, and a first release the user has smoke-tested against their real server.

**Channel selection** comes from `docs/delivery/channels.md`, approved at gate 1 (2026-10-04): Phase 1 = GitHub Releases, GHCR, npm and the MCP Registry; Docker Hub in Phase 2; catalogs in Phase 3. Release tooling is release-please with Conventional Commits (D5).

**Public name (gate 1): Notestead** ("Notestead for Joplin (unofficial)"). Artifact names: ADR-0006.

**Hard precondition (ADR-0010):** no artifact is published on any channel until M5-S1 is green **and** the user has completed the EUIPO TMview check for "Notestead" (ARCHITECTURE §14, O1). Each first publish per channel, the repo rename and the first push need the user's separate approval.

**Out of scope here: Phase 3 self-hosting catalogs** (Umbrel, Unraid, TrueNAS, Helm). **Pre-condition** before any catalog story is written: an ADR-0006 amendment decides whether that catalog's package may ship without the `internal` backend network, and with which compensating control (ADR-0006, "Self-hosting catalogs").

Owners: **SE** = senior-engineer, **CI** = ci-cd-specialist, **QA** = qa-specialist, **U** = user.

## M5-S1: Pre-publish gate
- **Owner:** CI (checks) + SE (fixes in `packages/**`) · **Size:** M · **Depends on:** M2-S6, M4 · **ADRs:** 0006, 0010

**Acceptance criteria:**
- **M5-AC1:** `corepack yarn check:prepublish <artifact>` runs on the `web` image, the `headless` image, the MCP npm tarball and the bundle tarball. *(integration)* It fails if any of the following holds:
  - (a) a file's sha256 equals an upstream icon (`upstream:packages/app-mobile/web/public/icons/*`, `upstream:Assets/ImageSources/**` icons)
  - (b) `LICENSE` (AGPL-3.0-or-later) is missing
  - (c) the "unofficial, not affiliated with Joplin / JOPLIN SAS" notice is missing from the README or the package description
  - (d) the artifact name or `name` field starts with a bare "joplin"
  - (e) the bundle tarball or the `web` image lacks `third-party-notices.txt`, or `source.html` doesn't link it (ADR-0010; generated by M1-AC29)

  **NEG:** one fixture per rule fails with that rule's message.
- **M5-AC2:** `source.html` in the `web` image and the OCI labels (`org.opencontainers.image.source`, `.revision`, `.licenses`, upstream web ref, CLI version) name the exact commits that were built. *(contract: inspect the image, then fetch `/source.html`)*
- **M5-AC3:** The public name chosen by the user (**Notestead**, recorded in the `docs/architecture/ARCHITECTURE.md` decision log, §14) is used consistently in every artifact name and listing (ADR-0006 table), and M5-AC1 (d) passes on all of them. *(review + the M5-AC1 check)*

## M5-S2: Multi-arch images
- **Owner:** CI · **Size:** L · **Depends on:** M1-S3, M1-S4, M1-S5 · **ADRs:** 0006

**Acceptance criteria:**
- **M5-AC4:** `images.yml` builds `web` and `headless` natively on x64 and arm64 runners and merges a multi-arch manifest. *(CI)*
  - The images run non-root with a read-only rootfs and contain no secrets (secret scan step).
  - **NEG:** a fixture image with `USER root` fails the inspect step.
- **M5-AC5:** Each image carries an SBOM and a provenance attestation, and is signed keylessly (cosign). Verification commands are documented and run in the release smoke test (M5-S5). *(CI)*

## M5-S3: Release workflow
- **Owner:** CI · **Size:** L · **Depends on:** M5-S1, M5-S2, approved channel plan · **ADRs:** 0006

**Acceptance criteria:**
- **M5-AC6:** The release tooling (release-please, per the channel plan) produces a GitHub Release containing:
  - the bundle tarball
  - `SHA256SUMS`
  - the SBOM
  - the source offer

  Publish jobs run only in the `release` environment, which requires the user's approval. *(CI; dry-run locally: `npm pack`, `actionlint`)*
- **M5-AC7:** The MCP package `notestead-mcp` is published to npm with trusted publishing and provenance (after the one bootstrap publish, channels.md F4), and its stdio entry starts with `npx notestead-mcp --help`. *(CI + release smoke)*
- **M5-AC12:** Image tags and version bumps follow ADR-0006 (D7). *(unit: the tag-computation script on fixtures; CI: dry run)*
  - `0.3.1` with pin minor 3.7 → `0.3.1`, `0.3.1-joplin3.7`, `0.3`, `joplin3.7`, `latest`; `1.2.0` additionally gets `1`.
  - **NEG:** `0.1.0-rc.1` gets only its exact tag (no floating tag moves).
  - **NEG:** a release whose pin `minor` differs from the previous release's `joplin.minor` label but whose version is only a PATCH bump fails (MAJOR required, MINOR while 0.x).

## M5-S4: Deployment files and operator docs
- **Owner:** SE · **Size:** M · **Depends on:** M3, M4 · **ADRs:** 0002, 0005, 0006, 0008

**Acceptance criteria:**
- **M5-AC8:** `deploy/compose.yaml` brings the stack up with both `podman compose` and `docker compose`, using compose secrets and the two-network topology. *(contract: the harness runs the stack from the deploy file, not from the test file)*
- **M5-AC9:** The docs (in the senior engineer's `deploy/README.md`; the user-facing per-channel install docs belong to CI in `docs/delivery/`) cover:
  - TLS options: **Cloudflare Tunnel** (default: the `tunnel` profile, the zone-settings checklist, the body limit L16 and the plaintext-at-Cloudflare note L17), the existing reverse proxy (alternative: body size, client-IP header, ≥ 125 s timeout), Caddy ACME (option)
  - that `JOPLIN_SERVER_URL` must be a direct address of the server, not a Cloudflare-proxied hostname
  - backup and restore of `headless-data`
  - the rollback runbook (image digest rollback, profile snapshot restore, browser "clear site data + re-sync")
  - the known limitations

  *(review)* QA executes the rollback runbook once on the Pi and records the result.

- **M5-AC13:** *(gate 1)* `deploy/compose.yaml` has a `tunnel` profile with a `cloudflared` service: image pinned by digest, a fixed address on `frontend`, the token from the secret `cf_tunnel_token` via `TUNNEL_TOKEN_FILE`, and `web`'s `TRUSTED_PROXIES`/`CLIENT_IP_HEADER` set to that address and `CF-Connecting-IP`. *(contract: `podman compose --profile tunnel config` inspection, then the M1-AC11 tunnel-mode test run against the deploy file with the fixture peer at cloudflared's address)*
  - **NEG:** a fixture compose variant that attaches `cloudflared` to `backend`, or passes the token as an environment value, fails the topology check.
- **M5-AC14:** *(2026-10-04 L17 decision)* Publishing MCP through the tunnel is documented and opt-in. *(contract: config inspection + review)*
  - `deploy/.env.example` ships `MCP_PUBLIC=false`.
  - `deploy/README.md` has a "Publish MCP through the tunnel" section: `MCP_PUBLIC=true`, a Cloudflare Access application on `<host>/mcp` (the policy type follows the O4 outcome), `access.required` on the `/mcp` ingress, the tunnel hostname in `MCP_ALLOWED_ORIGINS` where needed, and the L17 text in full before the steps.
  - The user's own settings live in their untracked `.env` and never in the repo.
  - **NEG:** a fixture `.env.example` with `MCP_PUBLIC=true` fails the deploy-file check.

## M5-S5: Release smoke tests
- **Owner:** QA · **Size:** M · **Depends on:** M5-S3

**Acceptance criteria:**
- **M5-AC10:** `tests/release/**` pulls every published artifact on amd64 and arm64 and checks that: *(release smoke; CI)*
  - the images start and the healthchecks pass
  - `/source.html` names the release commit
  - the signatures and attestations verify
  - the MCP stdio package answers `initialize` + `tools/list`

## M5-S6: User smoke test against the real server
- **Owner:** U (guided by the orchestrator) · **Size:** S · **Depends on:** M5-S4

**Acceptance criteria:**
- **Prerequisites (deploy-time details, collected from the user in M5-S4):** the server's `APP_BASE_URL`, a **direct** address for `JOPLIN_SERVER_URL` reachable from the `web` container's host, whether `USER_CONTENT_BASE_URL` is set, the Cloudflare plan of the zone, and a tunnel token created by the user.
- **M5-AC11:** Before anything touches the real server, the user confirms that **their Joplin Server database is backed up**. Then, following `deploy/README.md`: *(manual, recorded in `docs/worklog/M5-S6.md`)*
  1. stack up with the `tunnel` profile
  2. web app through the tunnel hostname (HTTPS): sync `/joplin-server`, unlock E2EE, existing notes visible
  3. zone checklist: COOP/COEP present on `/`; `cf-cache-status` is not `HIT` for `index.html` and `*.bundle.js`; `index.html` contains no `email-decode` script; Rocket Loader and Bot Fight Mode are off; the `web` access log shows the real client IP, not cloudflared's
  4. install repeating-todos from `.jpl`
  5. `claude mcp add --transport http …` with the bearer token, then "create a to-do 'Test' due tomorrow 9:00 in notebook X with tag Y". Then the same through the tunnel hostname (`MCP_PUBLIC=true`, Access on `/mcp`) from the user's cloud client (a claude.ai connector), as settled by O4. **NEG:** through the tunnel, a request without Access credentials is stopped by Cloudflare and never shows up in `web`'s access log, and a request with Access credentials but no bearer token gets 401 from us (unless O4 decided otherwise).
  6. the to-do appears in the web UI
  7. the alarm fires on the user's phone or desktop after it syncs
  - **NEG:** the sync-target `info.json` version on the real server is unchanged (3) before and after.
