# M1: Walking skeleton and test harness

**Goal:** the smallest end-to-end slice runs on the Pi (arm64) and is ready for x64 CI. A note created through the headless REST Data API appears in the upstream web UI, served by our `web` container and synced through our proxy from a throwaway Joplin Server.

**Exit criteria:**
- All M1 acceptance criteria are green on the Pi.
- The CI workflows exist and pass `actionlint`.
- The CI runs on GitHub start only after the user approves the first push.

**Conventions:**
- Every criterion names its test layer.
- `NEG:` marks the negative control.
- Owners follow `CLAUDE.md`: **SE** = senior-engineer, **CI** = ci-cd-specialist, **QA** = qa-specialist.
- QA writes the failing tests first for every story.

Order: S1 → S2 → (S3, S4, S5 in any order) → S6 → S7 → S8. S9 (added 2026-10-04) can run any time after S2 and should land before S3's CI is pushed.

## M1-S4: `web` container (Caddy + bundle + proxy)
- **Owner:** SE · **Size:** M · **Depends on:** M1-S2 · **ADRs:** 0002, 0006, 0008
- **Goal:** a multi-arch-capable image that serves an overlaid bundle with the S2 header and proxy rules. The bundle comes from the build artifact, or from a local `dist/` for development.

**Acceptance criteria:**
- **M1-AC10:** The proxy contract suite passes against the built image. *(contract; real `joplin/server:<pin>` container)*
  - C1: ping through `/joplin-server/api/ping`.
  - C2: login with a foreign `Origin` header.
  - C3: item round trip.
  - C4: `/joplin-server/login`, `/admin`, `/` and `/users/me` return 404.
  - C5: a 100 MiB attachment round-trips with an equal sha256.
  - C6: `/joplin-server/shares/<id>` returns a 302 to `JOPLIN_SERVER_PUBLIC_URL/shares/<id>`.
  - C8: no `X-API-AUTH`, `Cf-Access-Jwt-Assertion` or `CF-Access-Client-Secret` value appears in the access log.
  - C9: `Cf-Access-Jwt-Assertion` and `Cf-Access-Authenticated-User-Email` sent by the client are not forwarded upstream (checked against an echo upstream in place of the server).
  - C10: responses under `/joplin-server/*` carry `Cache-Control: no-store, no-transform`.
  - **NEG:** C1-neg: the same image with `JOPLIN_SERVER_HOST` unset (Host not rewritten) gets `404 Invalid origin`.
- **M1-AC11:** Rate limiting behind the proxy (server without `JOPLIN_IS_TESTING`). *(contract)*
  - 11 bad logins from one client get a `429` on the 11th, even when the client spoofs a different `X-Real-IP` each time.
  - A second client is unaffected (`200`).
  - **NEG:** a proxy variant that passes `X-Real-IP` through never returns 429.
  - **Tunnel mode** (gate 1; ADR-0002 rule 4): with `TRUSTED_PROXIES` set to a fixture container's fixed address (standing in for cloudflared; no Cloudflare account needed) and `CLIENT_IP_HEADER=CF-Connecting-IP`, 11 bad logins from that peer with the same `CF-Connecting-IP` get a `429` on the 11th, and a 12th request from that peer with a different `CF-Connecting-IP` gets `200`.
  - **NEG (R5):** a second fixture container (not the trusted address) rotating `CF-Connecting-IP` on every request still gets a `429` on the 11th: the header is ignored from untrusted peers.
- **M1-AC12:** Responses from `/` carry `Cross-Origin-Opener-Policy: same-origin` and `Cross-Origin-Embedder-Policy` equal to `$COEP` (default `credentialless`). `*.wasm` is served as `application/wasm`. The image runs as a non-root uid with a read-only rootfs. *(contract)*
  - Static files (`index.html`, `serviceWorker.js`, `environment.js`, `*.bundle.js`) carry `Cache-Control: no-cache, no-transform` and an `ETag`; a request with `Accept-Encoding: zstd, gzip` for a bundle gets a compressed response (gate 1: Cloudflare must neither cache stale unhashed bundles nor rewrite HTML, S6).
  - **NEG:** a conditional request with the returned `ETag` gets `304`, and none of these responses carries `max-age` > 0.
- **M1-AC13:** The internal listener `:8089` proxies only `/joplin-server/api/*`. *(contract)*
  - **NEG:** `GET :8089/` and `GET :8089/joplin-server/login` return 404.
- **M1-AC28:** `corepack yarn workspace web-build import <artifact-dir> --out <dist>` installs a packaged bundle (a CI-built artifact, or one written by `package` locally) as the `dist/` the `web` image is built from, so the Pi never needs the 43-minute build. *(integration; fixture: M1-S2's `package` output on F1. Before the first push the real-dist variant uses a locally packaged artifact of the S1 dist)*
  - Before extracting anything, it checks: `SHA256SUMS` verifies the tarball and `bundle-manifest.json`; `bundle-manifest.json` `upstream.{repo,tag,commit}` equals `upstream/joplin-version.json`; every tar entry is a regular file or directory, has a relative path without `..`, and is listed in `files`.
  - After extracting, each file's sha256 equals its `files` entry, nothing outside `files` exists, and `verify` passes on the result.
  - The `web` image built from the imported `dist/` passes the M1-AC12 header checks (same image path as a local `dist/`).
  - **NEG:** each of these fails, names the reason and leaves `--out` absent or empty: a tampered tarball (`SHA256SUMS` mismatch); a manifest whose `upstream.commit` ≠ the pin; a tar entry not in `files`; a tar entry that is a symlink or contains `..`.

*Gate 1 note:* the `cloudflared` service itself is not part of M1 (no Cloudflare account in tests). M1 only builds and tests the `web` side of the tunnel contract (M1-AC10 C9/C10, M1-AC11 tunnel mode, M1-AC12 headers). The `tunnel` compose profile arrives in M5-S4.

- **M1-AC16:** A note created on the throwaway server by another client (the CLI "other device" fixture, E2EE on) is returned **decrypted** by the internal `GET /notes/:id` after the initial sync. *(contract)*
- **M1-AC17:** The CLI's Data API isn't reachable from outside the headless container's network namespace. *(contract)*
  - **NEG:** `curl http://headless:41184/ping` from the `web` container fails.
  - **Positive control:** `curl http://127.0.0.1:41184/ping` inside `headless` succeeds.
- **M1-AC23:** The image gets the CLI's native `sqlite3` binding from this repo's `yarn.lock`, without turning install scripts back on for everything (ADR-0009 amendment A4). *(contract: inspect the built image)*
  - Inside the image, `require('sqlite3')`, resolved from the installed `joplin` package, loads, and `joplin version` prints `cli.version`. This holds for the arm64 build on the Pi and for the amd64 build.
  - The image's `joplin` and `@joplin/*` versions equal the ones in `yarn.lock`. The test compares the installed `package.json` versions with the lockfile, so no npm resolution can slip in.
  - Install scripts run only for allow-listed packages (`sqlite3` today). The allow-list sits in one reviewed place (the `.yarnrc.yml`/`package.json` setting or the Containerfile step).
  - **NEG:** a fixture dependency with a `postinstall` script that writes a marker file is installed in the same build, and the marker is absent from the image.

## M1-S9: License and provenance checks
- **Owner:** SE · **Size:** M · **Depends on:** M1-S1, M1-S2 · **ADRs:** 0009, 0010
- **Goal:** the dependency-licence and upstream-licence-header checks that ADR-0009 requires but M1-S1 didn't cover, plus the bundle's `third-party-notices.txt` that ADR-0010 requires but M1-S2 deferred (M1-AC29). `ci.yml` (M1-S3) runs them on both architectures once they exist. This story doesn't block the walking skeleton.

**Acceptance criteria:**
- **M1-AC24:** `corepack yarn check:licenses` lists the declared licence of every package in the installed dependency tree. It exits 0 only when each licence (or SPDX expression) is on ADR-0009's allow-list or on a reviewed per-package exception list that carries a reason. *(integration)*
  - Yarn 4 has no `yarn licenses` command (verified with yarn 4.16.0), so the check reads the installed manifests itself.
  - It reports the package name, the version and the offending licence.
  - **NEG:** a fixture tree containing a `SSPL-1.0` package and a package with no licence field fails and names both.
  - SPDX expressions are evaluated properly: an `OR` expression passes if any branch is allowed, an `AND` expression only if every branch is; `-only`/`-or-later` variants of an allowed licence are allowed. A package with no `license` field (or the legacy `licenses` array) is never silently passed.
  - **Known exceptions in the real tree (review M1-S1-r1).** A scan of the installed tree found five transitive packages of `joplin@3.7.1` that QA and the engineer must plan for. Each entry in the exception list names the package, an exact version (no ranges, so a bump forces a re-review), the licence as established, the evidence (licence file in the tarball or upstream repo URL at a tag) and the reason:
    - `@img/sharp-libvips-linux-arm64@1.2.4`: LGPL-3.0-or-later. Covered by the allow-list's LGPL-3.0 family once `-or-later` is handled, so it needs no exception; QA asserts that.
    - `@joplin/onenote-converter@3.7.1`: MPL-2.0-no-copyleft-exception. Needs an exception, because that SPDX ID differs from the allow-listed `MPL-2.0`.
    - `json-schema@0.4.0`: `AFL-2.1 OR BSD-3-Clause`. Passes through the `OR` rule via BSD-3-Clause; no exception needed.
    - `node-bitmap@0.0.1` and `tkwidgets@0.5.27`: no `license` field. Each needs an exception that records the licence actually found in the package or its source repo. If no licence can be established, the entry says so, the check still passes for local and CI use, and the package is listed as a blocker for the M5 pre-publish gate, to be resolved upstream or with the user before any image is published.
  - **Architect's position on compatibility.** Both copyleft licences are compatible with our AGPL-3.0-or-later aggregate, as long as we ship the packages unmodified from npm:
    - LGPL-3.0 is GPL-family and explicitly combinable. Its obligations are met by the image's source offer (ADR-0010) and by keeping libvips a separately replaceable shared library.
    - MPL-2.0 without the copyleft exception (Exhibit B) only stops MPL files from being *relicensed* under the GPL family. A Larger Work that combines them, with the MPL files under MPL and their source available (MPL §3.3), is allowed.
    - If either package is ever patched (`patches/`), the exception is re-reviewed.
  - **NEG (exceptions):** an exception entry with no reason, or with a version that doesn't match the installed one, fails.
- **M1-AC25:** `check:no-upstream-copy` also fails on any tracked file that carries upstream's licence header together with upstream's copyright line, whatever the file's size. *(unit)*
  - **NEG:** a fixture file of less than 1 KiB with upstream's header fails and is named, and the same file with our own AGPL header passes.
- **M1-AC26:** `check:pin` also checks that `packages/headless/package.json` depends on `joplin` at exactly `cli.version`, with no range. *(unit)*
  - **NEG:** fixtures with `"joplin": "^3.7.1"` and with `"joplin": "3.7.0"` each fail, naming the manifest and the field.
  - **Lockfile source (review M1-S1-r1, C1).** For `joplin` and **every** `@joplin/*` lockfile entry (the lockstep packages and the exempt forks alike), `check:pin` also requires the `resolution:` to be the npm registry form `<name>@npm:<version>`, in addition to the existing `version:` check. Any other protocol fails, naming the entry and its protocol: `git:`/`git+…`, `github:`, `https://…`/`http://…` tarballs or `.git` URLs, `file:`, `link:`, `portal:`, `exec:` and `patch:`. *(unit, on fixture lockfiles)*
    - `patch:` stays rejected until a reviewed patch exists in `patches/` (golden rule: justification + upstream link). The story that adds the first patch extends this AC to allow `patch:` only when the patch path is under `patches/`; that is out of scope here.
    - The check reads `resolution:`, not the entry key, because `"resolutions"` in `package.json` rewrite the resolution while the key keeps the requested range.
    - **NEG 1:** a fixture lockfile where `@joplin/lib` resolves to `@joplin/lib@https://github.com/someone/joplin-fork.git#commit=…` (version still `3.7.1`) fails.
    - **NEG 2:** a fixture lockfile where `joplin` resolves to `joplin@patch:joplin@npm%3A3.7.1#~/local-hack.patch::…` fails.
    - **NEG 3:** `file:` and `link:` resolutions of an `@joplin/*` package each fail. The valid fixture (all `npm:`) keeps passing.
- **M1-AC29:** `build` writes `third-party-notices.txt` into the dist before `package`, so it is in the tarball and in `bundle-manifest.json` `files`, and `source.html` links it (alongside the webpack `*.LICENSE.txt` links). It is generated from the upstream checkout at `web.commit` after the recipe's `yarn install`. A separate seam command over an upstream tree is fine, as long as `build` uses the same code path. *(unit on a fixture lockfile and installed tree; integration on a real upstream install: on the Pi the S1 spike tree at `~/joplin-web-app-work/spikes/S1/joplin`, in CI inside T90)*
