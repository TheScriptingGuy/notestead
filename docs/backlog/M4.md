# M4: MCP server

**Goal:** AI clients can manage notes, to-dos with alarms (`todo_due`), notebooks and tags, reorganise them, attach files, use the trash and trigger sync. This goes through one authenticated MCP endpoint (streamable HTTP via the headless service, and stdio for local use), built on upstream's `/mcp` tools plus REST gap tools, with the security guards of ADR-0008.

Owners: **SE** = senior-engineer, **QA** = qa-specialist. QA writes the failing tests first. ADRs: 0004, 0008.

Order: S1 → S2 → S7 → S3 → S4 → S5 → S6 → S8 → S9. The sanitizer comes before any write tool beyond upstream's.

---

## M4-S1: Server skeleton, transports and auth
- **Owner:** SE · **Size:** M · **Depends on:** M3-S2

**Acceptance criteria:**
- **M4-AC1:** Using the official `@modelcontextprotocol/sdk` client: *(contract)*
  - `initialize`, `tools/list` and `ping` succeed over streamable HTTP at `/mcp` (stateless, JSON responses).
  - The same calls succeed over stdio (`bin`) configured with a Data API URL and token. In tests, the stdio target is a CLI `server start` standing in for desktop Joplin.
- **M4-AC2:** Auth and limits. *(contract)*
  - Requests without a bearer token, or with a wrong one, get 401.
  - A request with `Origin: https://evil.example` gets 403, while no `Origin` or an allow-listed origin is accepted.
  - More than the configured calls per minute get 429 with `Retry-After`.
  - With `MCP_READ_ONLY=true`, write tools are absent from `tools/list`, and calling one returns a tool error.
  - **NEG:** the positive controls are a correct token without `Origin` (200) and a call under the limit (200).
- **M4-AC18:** Exposure gate (2026-10-04 L17 decision: opt-in for the product, on in the user's deployment). *(contract; fixture "cloudflared" peer at the trusted address as in M1-AC11, no Cloudflare account)*
  - With the default `MCP_PUBLIC=false`, a request to `web`'s `/mcp` from the tunnel peer gets 404 even with a valid bearer token. The host-local `http://127.0.0.1:8080/mcp` with the token gets 200.
  - With `MCP_PUBLIC=true`, the same tunnel-peer request with the token gets 200, and the response carries `Cache-Control: no-store, no-transform`.
  - The bearer token, the Origin check and the rate limits apply on both paths. Cloudflare Access is never accepted in place of the bearer token unless O4 is decided otherwise.
  - **NEG:** `MCP_PUBLIC=true` without a token from the tunnel peer gets 401, and with a forged `Cf-Access-Jwt-Assertion` but no bearer token also 401.

## M4-S2: Upstream `/mcp` passthrough
- **Owner:** SE · **Size:** M · **Depends on:** M4-S1 · **Spike:** S4

**Acceptance criteria:**
- **M4-AC3:** At startup, the supervisor enables `mcp.enabled` and exactly the allow-listed `ai.tool.<id>.enabled` settings through `config`. Our `tools/list` contains each allow-listed upstream tool with upstream's name, description and input schema, plus our annotations. *(contract)*
  - **NEG:** `semantic_search_notes` and the editor tools are absent, and calling them returns "unknown tool".
- **M4-AC4:** The `mcp-upstream` snapshot of the allow-listed tools' `tools/list` entries is committed. A bump that changes any of them fails until the snapshot is reviewed and updated. *(contract)*
  - When upstream `/mcp` is unavailable (`mcp.enabled` forced false in a test), the same tool names are served by the REST fallback and pass the same functional tests.

## M4-S7: Body sanitizer and the file:// guard
- **Owner:** SE · **Size:** M · **Depends on:** M4-S1 · **ADR:** 0008

**Acceptance criteria:**
- **M4-AC7:** The sanitizer (unit, table-driven):
  - accepts `:/<32hex>`, `#anchor` and plain text
  - rejects `file:`, `data:`, `http:`, `javascript:` and `//` targets in Markdown images and links, reference-style links and HTML `<img>`/`<a>`/`<source>`, with case and whitespace variants and percent-encoding
  - accepts `https:` only with `MCP_ALLOW_REMOTE_LINKS=true`

  *(unit)* **Contract:** `create_note`/`update_note`/`create_todo` with `![](file:///data/profile/database.sqlite)` fail with a tool error naming the target. No resource is created (`GET /resources` count unchanged), and nothing reaches the CLI (the CLI request log has no `POST /notes` call). **NEG:** the same call with a safe body succeeds.
- **M4-AC8:** The Data API client refuses to send `POST /notes` with `body`, `body_html`, `image_data_url` or `base_url` (unit, a typed error). Every MCP note creation is observed in the CLI request log as `POST /notes` (metadata only) followed by `PUT /notes/:id`, or as an upstream `/mcp` call. *(unit + contract)*

## M4-S3: To-dos and alarms
- **Owner:** SE · **Size:** M · **Depends on:** M4-S7

**Acceptance criteria:**
- **M4-AC5:** `create_todo {title, notebook_id, due:"<tomorrow>T09:00", tags:["Y"]}` with `MCP_TIMEZONE=Europe/Amsterdam` creates a to-do whose REST fields have the following values: *(contract)*
  - `is_todo=1`
  - `todo_due` = the epoch ms of 09:00 Amsterdam time
  - `parent_id` = X
  - tag Y attached (created if missing)

  An explicit offset (`…T09:00+02:00`) is honoured as given. **NEG:** a due date in the past is accepted but flagged in the result (`warning: due date is in the past; no alarm will fire`), mirroring `Note.needAlarm`.
- **M4-AC6:** `set_todo_due` sets and clears (`null` → `todo_due=0`) the due date. `set_todo_completed` completes (`todo_completed>0`) and reopens (`0`) a to-do. Each is verified through REST. *(contract)*

## M4-S4: Notebooks, tags, ordering
- **Owner:** SE · **Size:** M · **Depends on:** M4-S7

**Acceptance criteria:**
- **M4-AC9:** Notebooks. *(contract)*
  - `rename_notebook` changes the title.
  - `move_notebook` nests a notebook and un-nests it (`parent_id=""`).
  - `delete_notebook` sends the notebook to the trash (`deleted_time>0`).
  - **NEG:** moving a notebook into its own descendant is refused. Permanent delete without `MCP_ALLOW_PERMANENT_DELETE` is refused.
- **M4-AC10:** Tags. *(contract)*
  - `list_all_tags` includes a tag with no notes (which upstream `list_tags` omits).
  - `rename_tag` renames the tag.
  - `delete_tag` is refused unless `MCP_ALLOW_PERMANENT_DELETE=true`. With the flag, it deletes the tag and the notes keep existing. Its descriptor has `destructiveHint: true`.
- **M4-AC11:** `reorder_note {note_id, before_id}` sets `order` so that, sorted by `order` descending (upstream's custom order), the note sits directly before `before_id`. *(contract)*

## M4-S5: Attachments, trash, revisions
- **Owner:** SE · **Size:** M · **Depends on:** M4-S7

**Acceptance criteria:**
- **M4-AC12:** `attach_file {note_id, filename:"a.png", mime:"image/png", content_base64, insert:"append"}` creates a resource whose `GET /resources/:id/file` bytes equal the input, and appends `![a.png](:/<id>)` to the body. *(contract)*
  - **NEG:** content above `MCP_MAX_ATTACHMENT_BYTES` is refused, and an argument named `path` is rejected by the schema.
- **M4-AC13:** Trash and revisions. *(contract)*
  - `list_trash` lists a trashed note and notebook.
  - `restore_from_trash` on a note whose notebook is also trashed restores both, and the note is visible in the normal listing again.
  - `list_note_revisions` returns the revision metadata synced from another device. Restoring a revision is documented as unsupported.

## M4-S6: Sync tools
- **Owner:** SE · **Size:** S · **Depends on:** M3-S2

**Acceptance criteria:**
- **M4-AC14:** `sync_now {wait:true}` runs, or joins, one cycle and returns its result. `sync_status` reports the same fields as `/status`. *(contract)*
  - *(gate 1)* If the cycle takes longer than `MCP_SYNC_WAIT_MAX` (default and maximum 90 s), `sync_now` returns `{state:"running", cycle:N}` at the cap and the cycle continues; `sync_status` later reports cycle N as done. **NEG:** with `MCP_SYNC_WAIT_MAX=2s` and an artificially slow sync, the call returns `running` within 3 s and no second cycle starts.
  - Every write tool's result includes `synced:false` and `next_sync_eta`, and a debounced cycle follows within `WRITE_DEBOUNCE` + cycle time.
  - **NEG:** two concurrent `sync_now` calls produce one cycle (the cycle counter increments by 1).

## M4-S8: Cross-surface E2E
- **Owner:** QA · **Size:** M · **Depends on:** M4-S3, M2-S1

**Acceptance criteria:**
- **M4-AC15:** The MCP → web flow: `create_todo` "Test <uuid>" due tomorrow 09:00 in notebook X with tag Y, then `sync_now`. After a web sync, the web UI shows the to-do in X with tag Y and the due date (E2E with a data assertion).
- **M4-AC16:** The web → MCP flow: editing a note body in the web UI and syncing, then `sync_now`. MCP `read_note` returns the new body. *(E2E)*
  - **NEG:** before `sync_now`, `read_note` returns the old body. This shows the test observes sync, not a shortcut.

## M4-S9: Prompt-injection hardening review
- **Owner:** QA + lead review · **Size:** S · **Depends on:** M4-S1 to M4-S7

**Acceptance criteria:**
- **M4-AC17:** A table-driven suite of hostile tool inputs is replayed through MCP: *(contract)*
  - file URLs in every string field
  - huge inputs
  - unicode tricks
  - ids of other users' items
  - SQL-like search strings
  - nested JSON in titles

  No input leaks a secret, crashes the supervisor, creates resources from local files or deletes permanently without the flag. The audit log records each write without content.
